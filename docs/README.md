# chat-server

> 단순 과제 수행이 아니라, **문제를 직접 겪고 → 원인을 파악하고 → 트레이드오프를 따져 해결**하는 과정을 기록하는 채팅 서버 프로젝트.

## 프로젝트 소개

HTTP 폴링에서 시작해 WebSocket, 다중 서버, Redis로 확장하며 채팅 서버를 만든다. 단계마다 일부러 장애를 내고, 원인을 분석하고, 측정값으로 결정한다.

- 기술: Java 21, Spring Boot 4.1.1, MySQL 8.4 / PostgreSQL 18 (측정 후 선택), Vite + React + TypeScript
- 목표: 고가용성 (서버가 죽어도 메시지는 결국 받아야 한다). 단, 문제는 먼저 겪고 보완한다 (ADR-034)

## 과제 원문 요약

- HTTP 폴링: 클라이언트가 주기적으로 서버에 요청. 구현이 쉽지만 실시간성이 떨어지고, 주기를 짧게 하면 서버에 부담이 된다.
- WebSocket: 개념 공부 및 구현
- 채팅 서버 HTTP API
  - 메시지 전송: 컨트롤러 수신 → DB 저장 → 채팅방 유저 id 조회 → 실시간 전송 (Redis, Hash 활용)
  - 메시지 리스트 조회
  - 채팅방 생성 / 목록 / 입장 / 나가기

## 엔지니어링 핵심 문제 (우선순위)

| 순위 | 문제 | 왜 중요한가 |
|---|---|---|
| 1 | 실시간 전달 방식 (폴링 / WebSocket / SSE) | 나머지 설계가 이 선택을 따라간다 |
| 2 | 다중 서버 환경에서의 전달 | A는 서버1, B는 서버2에 연결되어 있으면? Redis가 필요한 이유 |
| 3 | DB 저장과 전송의 순서·정합성 | 저장 성공 후 전송 실패, 또는 그 반대 |
| 4 | 메시지 순서와 중복 | 동시 전송 시 순서, 재시도 시 중복 저장 |
| 5 | 메시지 조회 성능 | offset과 cursor 페이지네이션, 인덱스 설계 |
| 6 | 연결 끊김과 재연결 | 끊긴 동안 놓친 메시지 동기화 |

- [ ] (비교용) Long Polling, SSE
- [ ] WebSocket: handshake(HTTP Upgrade), 연결 유지, ping/pong, close

### B. 채팅방 도메인 (CRUD)
- [x] 채팅방 생성 API
- [x] 채팅방 목록 API
- [x] 채팅방 입장 API
- [x] 채팅방 나가기 API
- [x] 생성자 자동 입장·멤버십·목록 정렬과 커서 검증

### C. 메시지 (핵심)
- [x] 메시지 전송 API (Step 1: 멤버 확인 → DB 저장 → 방 목록 갱신; 실시간 전송은 이후 단계)
- [x] 메시지 리스트 조회 API (커서 페이지네이션·폴링)

- [ ] Redis: 방 멤버 캐싱(Hash/Set), 서버 간 메시지 전달(Pub/Sub)

## 미결정 (다음에 의논)

### Step 1 구현 전에 정한 것
- 초기 설계 범위는 ADR-032~033, 프론트 화면 범위는 ADR-081로 결정했다. 다음 작업은 계획 5다.

### 실험 또는 이후 단계에서 정할 것
- 입장/퇴장 알림(시스템) 메시지 도입 여부 → 정렬(ADR-016)과 데드락 위험(F20)에 영향. 따로 결정
- 방금 만든 빈 방이 **메시지 있는 방들 아래**에 보이는 문제 보완 여부 (예: 메시지가 없으면 생성 시각을 대신 사용). 방 #11로 [직접 관찰](journal/2026-10-07.md#계획-4-프론트엔드-직접-확인과-마무리); 보완 여부는 미결정
- 입장 경계: F18 실험 뒤 `joined_message_id` 유지로 결정했다(ADR-100). `joined_at` 컬럼 삭제 시점은 5b 이후 별도 마이그레이션에서 다룬다.
- DB: MySQL / PostgreSQL → 계획 5b의 사전 판정 문턱을 충족하지 않아 선택 보류(ADR-106). 후속 동일 조건 재측정·정합성 보완 뒤 재판단
- Spring Security 도입 여부 → JWT 전환 시점에 재판단 (ADR-006)
- 폴링 주기 → 부하 테스트의 변수로 측정 (Step 1, Step 6)
- WebSocket 인증 방식은 핸드셰이크 쿼리 `userId`로 결정했다(ADR-130). JWT 전환 시 재검토한다.
- JPA 전환 시 도메인 객체와 JPA 엔티티를 분리할지 (ADR-038) → JPA 전환 시점
- 방 목록 갱신(R7)을 이벤트 방식으로 바꿀지 (ADR-039) → Step 2~4
- 전달 보장 원칙, 재시도 중복 방지, 격리 수준 통일, 커밋 순서 구멍 해결 → 장애 재현 후 보완 (ADR-034)
- DB 자체 장애 대비(복제, 자동 전환) → 현재 어느 Step에도 없음. 고가용성 범위에 포함할지 Step 1 이후 결정
