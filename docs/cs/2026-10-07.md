## DB (가장 중요)

| # | 개념 | 이 프로젝트에서 왜 필요한가 |
|---|---|---|
| 1 | 트랜잭션 격리 수준 | 기본값이 MySQL은 REPEATABLE READ, PostgreSQL은 READ COMMITTED로 다르다(접속해서 확인함). 같은 코드가 두 DB에서 다르게 동작하는 이유이고, 커밋 순서 역전(F22)과 나가기·전송 경쟁(F23)의 출발점이다 |
| 2 | 클러스터드 인덱스와 힙 테이블 | InnoDB는 PK 순서로 데이터를 저장하고, PostgreSQL은 힙에 쌓고 인덱스가 따로 가리킨다. messages 스키마 A(PK `id`)와 B(PK `(room_id, id)`)를 비교하는 이유다 (ADR-013) |
| 3 | 복합 인덱스와 최좌측 접두사 규칙 | `(room_id, id)` 인덱스가 어떤 조회에 쓰이고 어떤 조회에는 못 쓰이는지. 인덱스 부재 실험(F16)과 연결된다 |
| 4 | 번호 자동 생성 | MySQL `AUTO_INCREMENT`, PostgreSQL `IDENTITY`(시퀀스). 번호는 커밋 순서가 아니라 발급 순서이고 롤백하면 빈 번호가 생긴다. 커서 조회(`after`)와 F22에 직결된다 |
| 5 | 내구성: WAL/redo log와 fsync | `innodb_flush_log_at_trx_commit=1`과 `synchronous_commit=on`이 왜 같은 조건인지. 커밋 지연 측정값에 영향을 준다 (ADR-040) |
| 6 | 버퍼 풀과 캐시 적중률 | `innodb_buffer_pool_size`와 `shared_buffers`의 차이, PostgreSQL은 운영체제 파일 캐시도 쓴다는 점. 메모리 초과 조건(C1) (ADR-040) |
| 7 | 제약 조건과 인덱스의 관계 | MySQL은 FK 컬럼에 인덱스를 자동으로 만들고 PostgreSQL은 만들지 않는다(확인함). PK·UNIQUE가 중복을 막는 방식이 중복 입장 409의 근거다 (ADR-019) |

## HTTP / 웹

| # | 개념 | 이 프로젝트에서 왜 필요한가 |
|---|---|---|
| 8 | HTTP 상태 코드의 의미 | 400·401·403·404·405·409·415·500의 차이. 실패에 200을 주면 모니터링 에러율이 틀린다 (ADR-020, ADR-044) |
| 9 | 서블릿 필터와 DispatcherServlet의 예외 흐름 | 필터에서 던진 예외는 `@RestControllerAdvice`까지 가지 않는다. 작업 3의 `AuthFilter`가 401을 직접 쓰는 이유다 |
| 10 | JSON 직렬화 | Jackson이 getter·record를 필드로 바꾸는 규칙, `null` 필드 출력 여부. `ApiResponse`를 private 생성자 + getter 클래스로 만든 이유다 |

## Spring / 시간 / 테스트 / 인프라

| # | 개념 | 이 프로젝트에서 왜 필요한가 |
|---|---|---|
| 11 | 의존성 주입과 설정 바인딩 | `@ConfigurationProperties`, 설정값으로 구현체 고르기(`@ConditionalOnProperty`). `chat.message-schema`, `chat.join-boundary` |
| 12 | 시간 다루기 | UTC 저장, `Instant`와 `LocalDateTime`의 차이, 마이크로초 정밀도, `Clock` 주입. 서버 간 시계 차이 실험(F18) |
| 13 | DB 마이그레이션 버전 관리(Flyway) | 이미 적용된 스크립트를 고치면 체크섬이 달라져 기동이 실패하는 이유 |
| 14 | Docker 자원 제한(cgroup) | CPU·메모리 제한이 공정한 DB 비교 실험의 전제다 (ADR-040) |
| 15 | 테스트 종류 | 단위 테스트, 슬라이스 테스트(`@WebMvcTest`), 통합 테스트(Testcontainers)의 차이와 H2를 쓰지 않는 이유 |
