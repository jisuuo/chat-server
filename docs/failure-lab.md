## 실험 목록

각 실험은 아래 템플릿으로 기록한다.

> **가설** → **재현 방법** → **관찰한 현상/지표** → **근본 원인** → **해결책** → **트레이드오프**

### 폴링 / 조회
- **F1. 폴링 폭주로 DB 커넥션 풀 고갈 (풀 포화·대기 재현, 계획 5b)**: 500만 건에서 VU 10/50/200과 0.5/1/2/5초·무대기 폴링을 세 DB 구성에 각각 30초씩 3회 실행했다. 200 VU 무대기의 Hikari 활성 연결은 모두 최대 10개였고 대기 피크 중앙값은 MySQL-A 157개, MySQL-B 168개, PostgreSQL-A 126개였다. p99는 각각 101.3/130.6/79.7ms, 처리량은 6,714/5,863/8,748요청/초였다. 전체 135개 반복에서 HTTP 오류와 연결 획득 타임아웃은 없었으므로 **풀 타임아웃 자체는 재현되지 않았다**. 대기 주기에 따른 수치와 반복 범위는 [계획 5b 보고서](reports/2026-10-07-plan5b-load-db-comparison.md#f1-폴링풀-고갈)에 둔다. 계획 4 브라우저 확인에서는 같은 사용자의 두 탭이 각각 폴링하는 것도 관찰했다.
- **F2. "새 메시지" 조회 시 누락/중복 (재현됨, 계획 5a)**
  - **가설:** `created_at > 마지막 시각`은 같은 시각의 다른 메시지를 놓치고, `>=`는 중복한다.
  - **재현 방법:** 테스트 전용 시각 커서로 같은 마이크로초의 메시지 3건을 2건씩 읽고, 두 DB의 세 격리 조건에서 동시 작성자 1/10/50명을 5초씩 실행했다.
  - **관찰:** 세 조건 모두 결정적 재현에서 `>`는 셋째 메시지를 놓쳤고 `>=`는 첫 페이지를 반복했다. 같은 입력의 id 커서는 셋째를 읽었다. 자연 실행에서 MySQL의 누락은 모든 조합 0건이었지만 `>=` 중복은 441~1,727회였다. PostgreSQL 작성자 10/50명에서 id 누락은 3,663/5,209건, 시각 `>` 누락은 3,708/5,214건, 시각 `>=` 누락은 3,772/5,194건이었다. 시도 수와 나머지 조건은 [계획 5a 보고서](reports/2026-10-07-plan5a-consistency.md#f2-시각-커서의-누락중복)에 있다.
  - **근본 원인:** 시각만 있는 커서에는 같은 시각 안의 순서가 없다. INSERT 전 시각 부여와 커밋 순서의 차이도 별도의 누락 경로다.
  - **해결책·트레이드오프:** 현재 서비스는 id 커서를 쓴다. 같은 시각 문제는 피하지만 커밋 순서 역전(F22)은 남는다. 시각과 id의 복합 커서 및 F22 해결책은 별도 검증이 필요하다.
- **F15. offset 페이지네이션 성능 저하 (재현됨, 계획 5b)**: 방 1에 메시지 약 25,000건이 있는 500만 건 데이터에서 같은 51건 페이지를 `EXPLAIN ANALYZE`로 3회씩 비교했다. 마지막 offset 24,949의 서버 실행 시간 중앙값은 MySQL-A 1,287ms, MySQL-B 6.73ms, PostgreSQL-A 48.81ms였다. 같은 위치의 ID 커서는 각각 0.155~0.190ms 범위, 0.040ms, 0.118ms였다. MySQL-A 깊은 offset은 커서의 약 8,303배다. 이는 SQL 실행 시간이고 HTTP 왕복 시간은 아니다. DB별 계획과 50만 건 결과는 [계획 5b 보고서](reports/2026-10-07-plan5b-load-db-comparison.md#f15-깊은-offset과-cursor)에 둔다. 운영 API는 ID 커서를 유지한다.
- **F16. 인덱스 부재로 인한 풀스캔 (성능 저하 재현, 풀스캔 가설은 반증, 계획 5b)**: 격리된 500만 건 DB에서 `(room_id, id)` 인덱스를 제거하자 최신 50건 W2 API의 p99 중앙값이 MySQL-A 71.7ms→11.59초, PostgreSQL-A 58.7ms→11.73초로 급증했다. 과거 조회 W3도 느려졌고, 폴링 W4의 p99 변화는 작았지만 처리량은 감소했다. 두 DB의 `EXPLAIN ANALYZE`는 전체 테이블 스캔 대신 기본키 역방향·범위 스캔과 `room_id` 필터를 보였다. 그러므로 원래 제목의 ‘풀스캔’은 이번 입력에서 관찰되지 않았다. 인덱스는 실험 뒤 복원했고, 반복값과 실행 계획은 [계획 5b 보고서](reports/2026-10-07-plan5b-load-db-comparison.md#f16-인덱스-유무)에 둔다.

### WebSocket
- **F3. 세션 저장소 동시성 버그**: `HashMap`에 세션을 보관하면 동시 접속/해제 시 예외가 나거나 세션이 유실된다.
- **F4. 느린 클라이언트(slow consumer)**: 동기 전송 루프에서 한 명이 느리면 방 전체의 전송이 지연된다.
- **F5. half-open 좀비 연결**: 네트워크가 끊겼는데 서버는 모른다. ping/pong이 없으면 세션이 계속 쌓인다.
- **F6. 재연결 시 메시지 유실**: 끊겨 있던 동안 온 메시지를 받지 못한다.

### 다중 서버
- **F7. 다른 서버에 연결된 유저에게 메시지 미전달**: 서버 2대 + 로드밸런서 환경에서 재현한다.
- **F8. 로드밸런서 뒤 WebSocket 연결 실패/끊김**: nginx에 `Upgrade`/`Connection` 헤더 설정이 없으면 handshake가 실패하고, 기본 idle timeout(60초)이 지나면 연결이 끊긴다.
- **F17. 배포/재시작 시 재연결 폭주 (thundering herd)**: 서버 재시작으로 수천 개의 연결이 동시에 재접속한다.

### Redis
- **F9. Pub/Sub 메시지 유실**: Pub/Sub은 at-most-once라서 구독자가 잠깐 끊기면 메시지가 사라진다. (Streams와 비교)
- **F10. Redis 다운**: 실시간 전송 전체가 마비된다. fallback 전략이 필요하다.
- **F11. 멤버 캐시 정합성**: 방을 나간 뒤 캐시가 갱신되지 않아 나간 유저에게도 메시지가 간다.

### 정합성
- **F12. 유령 메시지**: 트랜잭션 안에서 전송한 뒤 롤백되면, DB에는 없는데 유저는 메시지를 받은 상태가 된다.
- **F13. 재시도로 인한 중복 메시지**: 클라이언트 타임아웃 후 재전송하면 같은 메시지가 두 번 저장된다. (멱등성 키)
- **F14. 메시지 순서 역전**: 동시 전송이나 서버 간 시계 차이로 순서가 뒤바뀐다.
- **F18. 입장 경계 오판 (시각 기준 재현됨, 계획 5a)**
  - **가설:** 시각(`joined_at`)과 메시지 id(`joined_message_id`)가 입장 전후 메시지를 다르게 분류한다.
  - **재현 방법:** MySQL 기본/READ COMMITTED와 PostgreSQL 기본에서 두 경계를 각각 실행했다. 입장 시계를 ±50ms 어긋나게 하거나 동일 마이크로초를 강제했다. 자연 실행은 작성자 1/10/50명, 시계 차이 −50/0/+50ms, 조합별 새 입장 300회다.
  - **관찰:** 결정적 재현에서 시각 기준은 과거 메시지 유출과 입장 뒤·동일 시각 메시지 유실을 보였다. id 기준은 세 사례에서 유출·유실이 없었다. 자연 실행의 2,700회 입장/조건에서 id 기준의 유출·유실은 세 조건 모두 0건이지만 불일치 사용자는 MySQL RR 5명, MySQL RC 10명, PostgreSQL RC 1,798명이었다. 시각 기준의 유출/유실 합계는 각각 MySQL RR 10,794/11,105, MySQL RC 11,061/11,030, PostgreSQL RC 61,442/74,315건이다. 상세 조합은 [보고서](reports/2026-10-07-plan5a-consistency.md#f18-입장-경계)에 있다.
  - **근본 원인:** `joined_at`과 `created_at`은 서로 다른 호출 시계와 마이크로초 정밀도에 의존한다. id 경계의 동시 진행 메시지는 커밋 선후를 단정할 수 없어 별도로 세지 않는다.
  - **해결책·트레이드오프:** `joined_message_id`를 유지한다(ADR-100). 그 기준도 번호와 커밋 순서의 역전(F22) 때문에 실시간 폴링과 사후 목록 불일치가 생길 수 있다. `joined_at` 컬럼 삭제는 5b 이후 별도 마이그레이션에서 다룬다.
- **F20. 방 목록 정렬 컬럼 갱신 경합 (인기 방 처리량 감소·인덱스의 HOT 감소 재현됨, 계획 5b)**: 방 목록을 최근 대화순으로 정렬하기 위해 메시지마다 `rooms.last_message_id`를 갱신한다(ADR-016). 500만 건·동시 사용자 50명의 W1을 분산 방과 방 1개로 비교하자 MySQL-A 처리량 중앙값은 1,814→891/s로 약 51% 줄었다. InnoDB 행 잠금 대기 횟수의 30초 증분 중앙값은 682→26,763회로 늘었다. PostgreSQL-A도 3,820→2,312/s로 약 39% 줄었지만 잠금 대기 횟수는 직접 측정하지 않아 원인을 잠금만으로 단정하지 않는다. PostgreSQL 방 정렬값 인덱스를 격리 DB에 추가한 실험에서는 HOT 갱신 비율이 99.1%→0.9%로 줄고 `rooms` 전체 크기는 측정 구간에 2.35→4.83MB로 늘었다. 같은 실험의 p99는 악화되지 않았고 실행 순서·캐시 차이가 있어 작은 개선도 인덱스 효과로 단정하지 않는다. MySQL + `room_members` FK + 입장 알림이 겹칠 때의 데드락은 미검증이다. 수치와 반복 범위는 [계획 5b 보고서](reports/2026-10-07-plan5b-load-db-comparison.md#f20-방-정렬값-갱신-경합)에 둔다. Redis 도입 뒤 before/after 비교는 이후 단계에서 한다.
- **F27. 방 목록을 넘기는 중 순서가 바뀐 방의 누락** (예상, 미검증, 2026-10-07, 계획 1 작업 5 코드 리뷰)
  - **가설**: 방 목록 커서는 직전 페이지 마지막 방의 `(last_message_id, id)`이고, 다음 페이지는 그보다 뒤에 있는 방만 찾는다. 첫 페이지를 받은 뒤 **아직 보지 않은 방**에 새 메시지가 오면 그 방의 번호가 커서보다 커져서 목록 위쪽으로 옮겨 가고, 다음 페이지 어디에도 나오지 않는다. 정렬 기준 값이 보는 도중에 바뀌기 때문이다. ADR-016이 받아들인 대가 (3)이다.
  - **중복은 생기지 않을 것으로 예상한다**: `last_message_id`는 커지기만 하므로(조건부 UPDATE) 이미 본 방은 커서 위쪽으로만 움직인다. ADR-016의 "누락되거나 중복될 수 있다"와 다르므로 재현할 때 함께 확인한다. 중복은 OFFSET 방식에서 생기는 문제로 본다.
  - **재현 방법**: 방 4개(번호 30, 25, 20, 10), 페이지 크기 2로 첫 페이지를 받는다 → 번호 20인 방에 메시지를 보낸다(번호 40) → 커서로 다음 페이지를 받는다 → 그 방이 어느 페이지에도 없는지 본다. 이미 본 방(25)에 보냈을 때 다시 나오는지도 본다.
  - **해결 후보 (ADR-051)**: 첫 페이지를 줄 때의 기준 번호를 커서에 넣고, 다음 페이지 응답에 "기준 번호보다 큰 `last_message_id`를 가진 방(= 그사이 대화가 생긴 방)"을 따로 돌려준다. 화면은 그 방을 맨 위로 옮긴다. 비용: API 응답 모양 변경, 페이지마다 쿼리 1개 추가(`rooms`에 인덱스 없음, F20과 함께 측정), 화면 로직 추가.
  - **A안이 놓칠 수 있는 경우** (코드 리뷰, 추론, 미검증): 첫 페이지의 최고 번호가 100, 커서가 90일 때, 보지 않은 방의 메시지 95가 첫 페이지 뒤에 늦게 커밋되면 그 방은 커서 위로 옮겨 가지만 "100 초과" 조회에도 잡히지 않는다. 번호를 받는 순서와 커밋 순서가 다른 문제로, F22와 같은 원인이다. 재현할 때 동시 전송 조건으로 이 경우도 확인한다.
- **F21. `JdbcClient`와 JPA 성능 비교**: JPA 전환(ADR-025) 후 같은 서버에서 설정 값으로 구현체만 바꿔 메시지 저장(W1)과 조회(W2~W4)를 측정한다. JPA의 쓰기 지연, IDENTITY 전략의 배치 저장 제약, 영속성 컨텍스트 비용이 수치로 얼마나 차이 나는지 확인한다. 측정 조합(DB × PK 스키마 × 기술)이 크므로 실행 시 조합을 줄일 수 있다.
- **F22. 커밋 순서 역전으로 인한 영구 누락 (재현됨, 계획 5a)**
  - **가설:** 먼저 id를 받은 메시지가 늦게 커밋되면 `after` 커서가 이를 영구히 건너뛴다.
  - **재현 방법:** 첫 전송을 INSERT 뒤 커밋 전에 멈추고, 둘째 전송과 폴링을 마친 뒤 첫 전송을 커밋했다. 세 DB 조건에서 작성자 1/10/50명 × 5초 자연 실행도 했다.
  - **관찰:** 세 조건 모두 결정적으로 첫 메시지를 놓쳤다. 자연 실행은 MySQL RR에서 0/1/0건, MySQL RC에서 0/6/2건, PostgreSQL RC에서 0/5,913/5,683건(각각 작성자 1/10/50명)이었다. 시도 수와 폴링 수는 [보고서](reports/2026-10-07-plan5a-consistency.md#f22-번호-커서의-영구-누락)에 있다.
  - **근본 원인:** id는 INSERT 때 발급되지만 다른 트랜잭션이 볼 수 있는 시점은 커밋 뒤다. `after`는 받은 가장 큰 id로 단조 전진한다.
  - **해결책·트레이드오프:** 운영 코드는 장애 선행(ADR-034)에 따라 그대로 둔다. 전달 확인과 재조회 창 등의 후보는 후속 정합성 강화에서 중복·비용까지 비교한다.
- **F23. 나가기와 메시지 전송의 경쟁 (재현됨, 계획 5a)**
  - **가설:** 멤버십 확인 뒤 퇴장이 커밋돼도 메시지가 저장된다.
  - **재현 방법:** 전송의 멤버 조회 직후 멈춰 다른 스레드에서 나가기를 끝냈다. 세 DB 조건에서 자연 경쟁 1000회씩 반복했다.
  - **관찰:** 세 조건 모두 결정적으로 전송이 성공했고, 멤버 행 0개와 해당 메시지 1개가 남았다. 자연 실행 1,000회/조건에서 나가기가 끝난 뒤 전송 커밋이 시작한 확실한 위반은 MySQL RR 9건, MySQL RC 6건, PostgreSQL RC 993건이었다. 두 작업의 선후가 모호한 성공은 각각 989/994/7건이다. 현재 비멤버의 메시지는 정상적으로 보낸 뒤 나간 경우도 포함한다. 상세는 [보고서](reports/2026-10-07-plan5a-consistency.md#f23-나가기와-전송)에 있다.
  - **근본 원인:** 일반 멤버 조회는 이후의 DELETE를 막지 않으며 전송 전에 멤버십을 다시 확인하지 않는다.
  - **해결책·트레이드오프:** 의도적으로 열어 둔 경쟁이다(ADR-037). 잠금이나 전송·퇴장 순서 규칙은 후속 정합성 강화에서 비용과 함께 결정한다.
- **F19. 마지막 나가기와 입장의 경쟁 (실험용 삭제에서 재현됨, 계획 5a)**
  - **가설:** 마지막 멤버가 나갈 때 방을 삭제하면 입장과 경쟁한다.
  - **재현 방법:** 테스트 코드에서 멤버 삭제→남은 수 확인→방 삭제를 한 트랜잭션에 넣고, 입장 방 확인 직후 또는 남은 수 확인 직후에 상대를 끝까지 실행했다. 자연 경쟁은 조건별 1000회다.
  - **관찰:** 방 확인 뒤 삭제한 경우 입장은 FK 위반을 `UNAUTHENTICATED`(401)로 돌려줬다. 이는 ADR-019의 그 밖 500 설명과 다른 현재 코드 동작이다. 남은 수 확인 뒤 입장한 경우 방 DELETE는 FK 위반으로 롤백되어 두 멤버가 남았다. 자연 실행 1000회/조건에서 401은 MySQL RR 15건, MySQL RC 6건, PostgreSQL RC 9건이었다. 삭제 롤백·두 멤버 잔류는 각각 985/994/990건, PostgreSQL에서 정상 방 유지·한 멤버 잔류가 1건이었다. 고아 멤버는 모든 조합에서 0건이다. 상세는 [보고서](reports/2026-10-07-plan5a-consistency.md#f19-마지막-나가기와-입장)에 있다.
  - **근본 원인:** 방 존재 확인과 멤버 INSERT, 인원 확인과 방 DELETE 사이에 잠금으로 보호한 공통 경계가 없다. FK는 고아 행을 막지만 경쟁 자체는 막지 않는다.
  - **대량 삭제 (계획 5b):** 격리된 500만 건 DB에서 마지막 멤버 1명·방 1 메시지 25,000건·방 1개를 한 트랜잭션으로 지웠다. 1회 클라이언트 시간은 MySQL-A 3.267초, MySQL-B 0.215초, PostgreSQL-A 0.403초였고, 세 구성 모두 잔여 건수 0이다. PostgreSQL은 직후 dead tuple 25,000개와 변하지 않은 메시지 파일 크기를 보였다. MySQL history list 전후 값은 purge 때문에 undo 양으로 해석하지 않는다. 상세와 측정 한계는 [계획 5b 보고서](reports/2026-10-07-plan5b-load-db-comparison.md#f19-대량-삭제)에 있다.
  - **해결책·트레이드오프:** 실제 기능은 빈 방을 유지한다(ADR-012). 방 삭제를 도입한다면 잠금·조건부 삭제·상태 컬럼을 비교해야 한다.

### 인증
- **F24. 조작한 경로로 인증 필터 우회** (2026-10-07, 계획 1 작업 3)
  - **가설**: `AuthFilter`는 정규화하지 않은 원래 경로(`getRequestURI()`)가 `/api/dev/`로 시작하는지 보고 검사를 건너뛴다. `/api/dev/../rooms`처럼 보냈을 때 Spring MVC가 `..`를 풀어 `/api/rooms`로 해석한다면, 헤더 없이 컨트롤러에 닿는다.
  - **재현 방법**: MockMvc는 Tomcat의 경로 처리를 거치지 않아 재현할 수 없다. 그래서 `RANDOM_PORT`로 실제 내장 Tomcat을 띄우고, `..`를 정리하지 않고 그대로 보내는 `java.net.http.HttpClient`(소켓으로 직접 보낸 결과와 같음)로 헤더 없이 요청했다. curl로 확인하려면 `--path-as-is`가 필요하다. 테스트용 컨트롤러는 `@CurrentUser`가 있는 것(`/api/probe/me`)과 없는 것(`/api/probe/open`) 둘이다.
  - **관찰 (측정, Boot 4.1.1 기본 설정)**: `/api/probe/open` → 401(대조군). `/api/dev/../probe/{open,me}`, `%2e%2e`, `%2E%2E`, `..;` → 모두 404. `/api/dev;x/../`, `/api//dev/../` → 401(필터가 dev로 보지 않음).
  - **원인 해석**: 필터와 Spring MVC가 같은 원래 경로를 글자 그대로 읽는다. 그래서 필터를 건너뛴 요청은 그 글자와 같은 매핑이 없어 404가 된다. 측정 결과를 보고 한 해석이고, Spring 소스로 확인하지는 않았다.
  - **경로를 정규화했을 때 (흉내, 측정)**: 테스트에 정규화 필터를 임시로 끼워 보면 `@CurrentUser`가 없는 `/probe/open`은 200(우회 성공), 있는 `/probe/me`는 401(리졸버가 막음)이다. 경로 매칭 설정이나 버전이 바뀌면 뚫릴 수 있고, 그때는 `@CurrentUser`가 없는 `/api/**` 컨트롤러가 위험하다.
  - **지금 둔 장치**: 회귀 테스트 `AuthPathBypassTest`(404가 아니게 되면 실패한다). `@CurrentUser` 리졸버는 필터를 거치지 않은 요청을 401로 막는다. "`/api/**`(dev 제외) 핸들러는 모두 `@CurrentUser AuthUser`를 받는다"는 규칙 검사는 계획 1 작업 9에서 추가한다.
  - **고치지 않은 것 (ADR-034, ADR-047)**: 필터의 경로 정규화는 하지 않았다. 재현되지 않았기 때문이다.

### 입력 문자
- **F25. 저장할 수 없는 문자가 든 입력** (2026-10-07, 계획 1 작업 4, 사용자가 발견)
  - **재현**: `POST /api/dev/users`에 JSON 이스케이프로 보낸다.
    - `{"nickname":"\ud800"}`: 두 DB 모두 201이고 응답에는 원문 `\uD800`이 돌아오지만, DB에는 `?`(0x3F)로 저장됐다.
    - `{"nickname":"a\u0000b"}`: MySQL은 201이고 NUL을 그대로 저장했다(`610062`). PostgreSQL은 500이 났다.
  - **원인 (측정)**
    - JSON 문법은 짝 없는 서로게이트와 NUL 이스케이프도 허용해서 Jackson이 그대로 Java 문자열로 만든다. 길이 검사(`@NotBlank`, `@CodePointLength`)는 문자 종류를 보지 않는다.
    - 짝 없는 서로게이트는 UTF-8로 바꿀 수 없다. `String.getBytes(UTF_8)`는 이런 문자를 오류 없이 `?`로 바꾼다. 드라이버도 같은 방식으로 인코딩한다고 해석했지만, 드라이버 소스로 확인하지는 않았다.
    - PostgreSQL 텍스트 타입은 0x00을 저장하지 못한다(`invalid byte sequence for encoding "UTF8": 0x00`). 이 오류가 `DataIntegrityViolationException`이 되어 500이 났다.
  - **영향**: 서로게이트는 응답과 DB 값이 조용히 달라진다. NUL은 같은 요청의 결과가 DB에 따라 갈린다.
  - **해결 (ADR-050)**: DTO의 `@Pattern`과 도메인 `Nickname`이 같은 정규식 `[^\p{Cc}\p{Cs}]*`로 제어 문자와 짝 없는 서로게이트를 400으로 거절한다. 회귀 테스트는 `NicknameTest`와 `DevUserControllerTest`에 있다.
  - **메시지 적용 (ADR-052)**: 방 이름에는 닉네임과 같은 규칙을 적용했다(작업 6). 메시지는 줄바꿈을 허용하고 NUL·짝 없는 서로게이트만 거절한다(작업 8, 두 DB API 테스트 통과).
- **F26. 보이지 않는 서식 문자로 같아 보이는 닉네임** (예상, 미검증): F25의 규칙은 서식 문자(`\p{Cf}`)를 막지 않는다. 폭이 0인 공백(U+200B)이나 글자 방향을 뒤집는 문자(U+202E)를 넣으면 다른 사람과 똑같아 보이는 닉네임을 만들 수 있을 것으로 예상한다. 계획 4에서 작성자를 닉네임 대신 `사용자 #id`로 표시하기로 해서 화면 검증을 이후로 미뤘다.

### 관측으로 드러날 수 있는 문제 (계획 3)

- **F28. 비멤버 폴링의 감사 로그 폭증** (로컬 반복 기록 재현, 규모 영향 미측정): 사용자 #15가 방 #10을 두 탭에서 연 뒤 한 탭에서 나갔다. 다른 탭은 0.5초 주기로 403 `NOT_A_MEMBER`를 계속 받았고, 패널 오류 수는 0→22, 같은 사용자·방의 `audit.json` `ACCESS_DENIED` 누계는 4→26건으로 늘었다(2026-10-07 측정). 재현 뒤 폴링을 일시정지했다. 재시도 대기 증가나 자동 중단은 아직 적용하지 않는다(장애 선행, ADR-034). 다수 비멤버의 초당 감사 건수, 파일 회전, 색인 크기와 검색 영향은 별도 부하 실험에서 측정한다.
- **F29. 동기 로그 출력으로 응답 지연 증가** (가설): 요청마다 `ACCESS` 한 줄을 콘솔과 ECS 파일에 쓰고, local에서는 SQL TRACE도 남긴다. 부하 실험에서 로그 비용이 p99를 높일 수 있다. 같은 입력으로 `bench`의 `ACCESS=OFF`와 실행 중 `ACCESS=INFO`를 비교하고, CPU·디스크 쓰기량도 함께 본다. 아직 차이를 측정하지 않았다.
- **F30. 비동기 전송에서 MDC 추적 ID 유실** (가설): `requestId`와 `userId`는 요청 스레드의 MDC에 있으므로 Step 2의 별도 WebSocket 전송 스레드에는 자동으로 전달되지 않는다. 비동기 전송을 추가할 때 같은 메시지의 HTTP·전송 로그가 ID로 연결되는지 확인한다. 현재 동기 HTTP 요청에서는 연결을 확인했다.
- **F31. 히스토그램 p99와 부하 도구 p99 차이** (가설): Prometheus의 `histogram_quantile`은 버킷으로 추정하고 k6는 요청 샘플에서 계산하므로 값이 다를 수 있다. 같은 구간·같은 URI·같은 상태 코드를 대상으로 p50/p95/p99를 함께 기록해 차이를 비교한다. 대시보드 쿼리 실행은 확인했지만 이 비교는 아직 하지 않았다.
- **F32. 방 만들기 중복 제출로 중복 방 생성** (가설, 계획 4 작업 4): 방 생성 응답을 기다리는 동안 버튼을 연속으로 누르면 요청이 두 번 전송되어 이름이 같은 방이 두 개 만들어질 수 있다. 느린 응답을 주입해 연속 제출하고 응답의 방 ID와 DB 행 수를 확인한다. 아직 재현하지 않았으며, 장애 선행 규칙(ADR-034)에 따라 화면에서 미리 막지 않는다.
- **F33. 메시지 전송 연속 제출로 중복 메시지 생성** (가설, 계획 4 작업 6): 전송 응답을 기다리는 동안 같은 입력으로 다시 제출하면 메시지가 두 번 저장될 수 있다. 느린 응답을 주입하고 빠르게 연속 제출해 저장된 메시지 ID와 내용을 확인한다. 아직 재현하지 않았으며, 장애 선행 규칙(ADR-034)에 따라 화면에서 미리 막지 않는다.
