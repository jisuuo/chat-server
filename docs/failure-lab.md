## 실험 목록

각 실험은 아래 템플릿으로 기록한다.

> **가설** → **재현 방법** → **관찰한 현상/지표** → **근본 원인** → **해결책** → **트레이드오프**

### 폴링 / 조회
- **F1. 폴링 폭주로 DB 커넥션 풀 고갈**: 짧은 주기로 다수 클라이언트가 폴링하면 HikariCP 풀(기본 10개)이 고갈되어 요청이 타임아웃된다.
- **F2. "새 메시지" 조회 시 누락/중복**: `createdAt > 마지막 시각` 조건에서 같은 시각의 메시지가 누락되거나 중복된다.
- **F15. offset 페이지네이션 성능 저하**: 메시지 100만 건에서 뒤쪽 페이지 조회가 급격히 느려진다.
- **F16. 인덱스 부재로 인한 풀스캔**: `(room_id, id)` 인덱스 없이 조회하면 풀스캔이 발생한다.

### WebSocket
- **F3. 세션 저장소 동시성 버그**: `HashMap`에 세션을 보관하면 동시 접속/해제 시 예외가 나거나 세션이 유실된다.
- **F4. 느린 클라이언트(slow consumer)**: 동기 전송 루프에서 한 명이 느리면 방 전체의 전송이 지연된다.
- **F5. half-open 좀비 연결**: 네트워크가 끊겼는데 서버는 모른다. ping/pong이 없으면 세션이 계속 쌓인다.
- **F6. 재연결 시 메시지 유실**: 끊겨 있던 동안 온 메시지를 받지 못한다.

### 다중 서버
- **F7. 다른 서버에 연결된 유저에게 메시지 미전달**: 서버 2대 + 로드밸런서 환경에서 재현한다.
- **F8. 로드밸런서 뒤 WebSocket 연결 실패/끊김**: nginx에 `Upgrade`/`Connection` 헤더 설정이 없으면 handshake가 실패하고, 기본 idle timeout(60초)이 지나면 연결이 끊긴다.
- **F17. 배포/재시작 시 재연결 폭주 (thundering herd)**: 서버 재시작으로 수천 개의 연결이 동시에 재접속한다.

### Redis
- **F9. Pub/Sub 메시지 유실**: Pub/Sub은 at-most-once라서 구독자가 잠깐 끊기면 메시지가 사라진다. (Streams와 비교)
- **F10. Redis 다운**: 실시간 전송 전체가 마비된다. fallback 전략이 필요하다.
- **F11. 멤버 캐시 정합성**: 방을 나간 뒤 캐시가 갱신되지 않아 나간 유저에게도 메시지가 간다.

### 정합성
- **F12. 유령 메시지**: 트랜잭션 안에서 전송한 뒤 롤백되면, DB에는 없는데 유저는 메시지를 받은 상태가 된다.
- **F13. 재시도로 인한 중복 메시지**: 클라이언트 타임아웃 후 재전송하면 같은 메시지가 두 번 저장된다. (멱등성 키)
- **F14. 메시지 순서 역전**: 동시 전송이나 서버 간 시계 차이로 순서가 뒤바뀐다.
- **F18. 재입장 경계 오판**: 재입장 시점 경계를 시각(`joined_at`)으로 잡을 때와 메시지 id(`joined_message_id`)로 잡을 때, 동시 쓰기 중 유출/유실이 발생하는지 비교한다. (설계는 아래 "입장 경계 실험 설계")
- **F20. 방 목록 정렬 컬럼 갱신 경합**: 방 목록을 최근 대화순으로 정렬하기 위해 메시지마다 `rooms.last_message_id`를 갱신한다(ADR-016). 예상 문제(미검증): (1) 인기 방에서 같은 `rooms` 행을 고치려는 전송들이 행 락(한 행을 고치는 동안 다른 요청이 못 고치게 막는 잠금) 때문에 줄을 선다 (2) MySQL + `room_members` FK + 입장 알림 메시지가 겹치면 FK 공유 잠금과 UPDATE 배타 잠금이 엇갈려 데드락(서로의 잠금을 기다리며 둘 다 멈춤)이 날 수 있다 (PostgreSQL은 `FOR KEY SHARE`라 덜 발생할 것으로 예상) (3) PostgreSQL에서 `last_message_id`에 인덱스를 걸면 HOT 업데이트(인덱스를 건드리지 않는 갱신 최적화)가 불가능해져 테이블이 팽창한다. 측정: 동시 전송 수에 따른 전송 p99, DB별 데드락 발생 여부, PostgreSQL 인덱스 유무별 테이블 크기. Redis 이전(Step 4) 후 before/after를 비교한다.
- **F27. 방 목록을 넘기는 중 순서가 바뀐 방의 누락** (예상, 미검증, 2026-10-07, 계획 1 작업 5 코드 리뷰)
  - **가설**: 방 목록 커서는 직전 페이지 마지막 방의 `(last_message_id, id)`이고, 다음 페이지는 그보다 뒤에 있는 방만 찾는다. 첫 페이지를 받은 뒤 **아직 보지 않은 방**에 새 메시지가 오면 그 방의 번호가 커서보다 커져서 목록 위쪽으로 옮겨 가고, 다음 페이지 어디에도 나오지 않는다. 정렬 기준 값이 보는 도중에 바뀌기 때문이다. ADR-016이 받아들인 대가 (3)이다.
  - **중복은 생기지 않을 것으로 예상한다**: `last_message_id`는 커지기만 하므로(조건부 UPDATE) 이미 본 방은 커서 위쪽으로만 움직인다. ADR-016의 "누락되거나 중복될 수 있다"와 다르므로 재현할 때 함께 확인한다. 중복은 OFFSET 방식에서 생기는 문제로 본다.
  - **재현 방법**: 방 4개(번호 30, 25, 20, 10), 페이지 크기 2로 첫 페이지를 받는다 → 번호 20인 방에 메시지를 보낸다(번호 40) → 커서로 다음 페이지를 받는다 → 그 방이 어느 페이지에도 없는지 본다. 이미 본 방(25)에 보냈을 때 다시 나오는지도 본다.
  - **해결 후보 (ADR-051)**: 첫 페이지를 줄 때의 기준 번호를 커서에 넣고, 다음 페이지 응답에 "기준 번호보다 큰 `last_message_id`를 가진 방(= 그사이 대화가 생긴 방)"을 따로 돌려준다. 화면은 그 방을 맨 위로 옮긴다. 비용: API 응답 모양 변경, 페이지마다 쿼리 1개 추가(`rooms`에 인덱스 없음, F20과 함께 측정), 화면 로직 추가.
  - **A안이 놓칠 수 있는 경우** (코드 리뷰, 추론, 미검증): 첫 페이지의 최고 번호가 100, 커서가 90일 때, 보지 않은 방의 메시지 95가 첫 페이지 뒤에 늦게 커밋되면 그 방은 커서 위로 옮겨 가지만 "100 초과" 조회에도 잡히지 않는다. 번호를 받는 순서와 커밋 순서가 다른 문제로, F22와 같은 원인이다. 재현할 때 동시 전송 조건으로 이 경우도 확인한다.
- **F21. `JdbcClient`와 JPA 성능 비교**: JPA 전환(ADR-025) 후 같은 서버에서 설정 값으로 구현체만 바꿔 메시지 저장(W1)과 조회(W2~W4)를 측정한다. JPA의 쓰기 지연, IDENTITY 전략의 배치 저장 제약, 영속성 컨텍스트 비용이 수치로 얼마나 차이 나는지 확인한다. 측정 조합(DB × PK 스키마 × 기술)이 크므로 실행 시 조합을 줄일 수 있다.
- **F22. 커밋 순서 역전으로 인한 영구 누락** (예상, 미검증): 메시지 id는 INSERT 시점에 발급되고 다른 트랜잭션에는 COMMIT 시점에 보인다. id 101이 100보다 먼저 커밋되어 보이면, `after=100` 폴링이 101을 받고 다음엔 `after=101`로 조회하므로 뒤늦게 보인 100을 영원히 받지 못한다. 서버 다운이 아니라 동시 전송만으로 생기며, "메시지는 결국 받아야 한다"는 고가용성 목표를 직접 위협한다. F2(시각 기준 누락)의 id 버전이다. 측정: 동시 전송 중 폴링 클라이언트가 영구히 놓친 메시지 수, DB와 격리 수준별 비교.
- **F23. 나가기와 메시지 전송의 경쟁** (예상, 미검증, ADR-037): 메시지 전송은 "멤버십 확인 → 메시지 저장" 순서로 처리한다(R3). 확인과 저장 사이에 같은 사용자의 나가기가 커밋되면, 이미 나간 사람의 메시지가 저장된다. 멤버십과 메시지를 다른 애그리거트로 나눈 대가다. F19와 같은 확인 후 행동 사이의 경쟁(TOCTOU) 유형. 측정: 나가기와 전송을 동시에 반복할 때 비멤버 메시지가 저장되는 횟수, DB와 격리 수준별.
- **F19. 마지막 나가기와 입장의 경쟁 (TOCTOU)**: 실제 기능은 방 유지(ADR-012)지만, "마지막 멤버가 나가면 방 삭제"를 실험용으로 구현해 경쟁을 재현한다. 마지막 멤버가 "멤버 수 확인 → 방 삭제"를 하는 사이에 다른 유저가 "방 존재 확인 → 입장"하면, 삭제된 방에 입장하거나(FK 에러) 존재하지 않는 방의 멤버가 생긴다. 해결 방법(비관적 락, 조건부 DELETE, 상태 컬럼, FK 제약)을 비교한다. 대량 메시지 삭제 시 긴 트랜잭션 부하(MySQL undo log, PostgreSQL dead tuple)도 함께 관찰한다.

### 인증
- **F24. 조작한 경로로 인증 필터 우회** (2026-10-07, 계획 1 작업 3)
  - **가설**: `AuthFilter`는 정규화하지 않은 원래 경로(`getRequestURI()`)가 `/api/dev/`로 시작하는지 보고 검사를 건너뛴다. `/api/dev/../rooms`처럼 보냈을 때 Spring MVC가 `..`를 풀어 `/api/rooms`로 해석한다면, 헤더 없이 컨트롤러에 닿는다.
  - **재현 방법**: MockMvc는 Tomcat의 경로 처리를 거치지 않아 재현할 수 없다. 그래서 `RANDOM_PORT`로 실제 내장 Tomcat을 띄우고, `..`를 정리하지 않고 그대로 보내는 `java.net.http.HttpClient`(소켓으로 직접 보낸 결과와 같음)로 헤더 없이 요청했다. curl로 확인하려면 `--path-as-is`가 필요하다. 테스트용 컨트롤러는 `@CurrentUser`가 있는 것(`/api/probe/me`)과 없는 것(`/api/probe/open`) 둘이다.
  - **관찰 (측정, Boot 4.1.1 기본 설정)**: `/api/probe/open` → 401(대조군). `/api/dev/../probe/{open,me}`, `%2e%2e`, `%2E%2E`, `..;` → 모두 404. `/api/dev;x/../`, `/api//dev/../` → 401(필터가 dev로 보지 않음).
  - **원인 해석**: 필터와 Spring MVC가 같은 원래 경로를 글자 그대로 읽는다. 그래서 필터를 건너뛴 요청은 그 글자와 같은 매핑이 없어 404가 된다. 측정 결과를 보고 한 해석이고, Spring 소스로 확인하지는 않았다.
  - **경로를 정규화했을 때 (흉내, 측정)**: 테스트에 정규화 필터를 임시로 끼워 보면 `@CurrentUser`가 없는 `/probe/open`은 200(우회 성공), 있는 `/probe/me`는 401(리졸버가 막음)이다. 경로 매칭 설정이나 버전이 바뀌면 뚫릴 수 있고, 그때는 `@CurrentUser`가 없는 `/api/**` 컨트롤러가 위험하다.
  - **지금 둔 장치**: 회귀 테스트 `AuthPathBypassTest`(404가 아니게 되면 실패한다). `@CurrentUser` 리졸버는 필터를 거치지 않은 요청을 401로 막는다. "`/api/**`(dev 제외) 핸들러는 모두 `@CurrentUser AuthUser`를 받는다"는 규칙 검사는 계획 1 작업 9에서 추가한다.
  - **고치지 않은 것 (ADR-034, ADR-047)**: 필터의 경로 정규화는 하지 않았다. 재현되지 않았기 때문이다.

### 입력 문자
- **F25. 저장할 수 없는 문자가 든 입력** (2026-10-07, 계획 1 작업 4, 사용자가 발견)
  - **재현**: `POST /api/dev/users`에 JSON 이스케이프로 보낸다.
    - `{"nickname":"\ud800"}`: 두 DB 모두 201이고 응답에는 원문 `\uD800`이 돌아오지만, DB에는 `?`(0x3F)로 저장됐다.
    - `{"nickname":"a\u0000b"}`: MySQL은 201이고 NUL을 그대로 저장했다(`610062`). PostgreSQL은 500이 났다.
  - **원인 (측정)**
    - JSON 문법은 짝 없는 서로게이트와 NUL 이스케이프도 허용해서 Jackson이 그대로 Java 문자열로 만든다. 길이 검사(`@NotBlank`, `@CodePointLength`)는 문자 종류를 보지 않는다.
    - 짝 없는 서로게이트는 UTF-8로 바꿀 수 없다. `String.getBytes(UTF_8)`는 이런 문자를 오류 없이 `?`로 바꾼다. 드라이버도 같은 방식으로 인코딩한다고 해석했지만, 드라이버 소스로 확인하지는 않았다.
    - PostgreSQL 텍스트 타입은 0x00을 저장하지 못한다(`invalid byte sequence for encoding "UTF8": 0x00`). 이 오류가 `DataIntegrityViolationException`이 되어 500이 났다.
  - **영향**: 서로게이트는 응답과 DB 값이 조용히 달라진다. NUL은 같은 요청의 결과가 DB에 따라 갈린다.
  - **해결 (ADR-050)**: DTO의 `@Pattern`과 도메인 `Nickname`이 같은 정규식 `[^\p{Cc}\p{Cs}]*`로 제어 문자와 짝 없는 서로게이트를 400으로 거절한다. 회귀 테스트는 `NicknameTest`와 `DevUserControllerTest`에 있다.
  - **남은 것**: 방 이름(작업 6)에도 같은 규칙을 쓴다. 메시지(작업 8)는 줄바꿈을 받아야 하므로 그때 규칙을 따로 정한다.
- **F26. 보이지 않는 서식 문자로 같아 보이는 닉네임** (예상, 미검증): F25의 규칙은 서식 문자(`\p{Cf}`)를 막지 않는다. 폭이 0인 공백(U+200B)이나 글자 방향을 뒤집는 문자(U+202E)를 넣으면 다른 사람과 똑같아 보이는 닉네임을 만들 수 있을 것으로 예상한다. 측정: 화면(계획 4)에서 실제로 구분이 안 되는지 본다.
