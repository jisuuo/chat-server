## 계획 7: 전달 시간 지표와 부하 측정 표본

| # | 결정 | 이유 | 포기한 것 |
|---|---|---|---|
| 129 | **전달 단계 시간은 `stage`·`transport`별 표본으로, 전체 시간은 fan-out 정상 종료 시 별도 표본으로 기록한다. 부하 측정 전에는 전송 건수와 열린 수신 세션 수로 예상 표본 수를 정하고 측정 구간의 실제 `count` 증가분과 대조한다** | 단계가 중첩되고 `push`는 세션마다 한 번 기록되므로 단계 시간을 합하거나 메시지 건수만으로 표본 수를 판단하면 지연 분포를 잘못 해석한다. 표본 수 검증으로 누락·실패·연결 변화를 먼저 찾는다 | 단계 시간의 합을 전체 시간으로 보거나, 서버 기동 뒤 누적 `count`만 확인하고 p95/p99를 비교하는 방식 |

`@DeliveryStage`의 `value`는 실행 동작이 아니라 `chat.delivery.stage{stage,transport}`의 `stage` 태그다. REST 컨트롤러와 WS 프레임 핸들러는 `receive`, `MessageService.send`는 `save`, 커밋 뒤 `MessageFanout.on`은 `fanout`, 세션별 `WsFrameSender.send`는 `push`로 기록한다. `transport`는 `rest`·`ws`·`internal`로 나눈다. 현재 동기 호출에서는 `receive ⊃ save ⊃ fanout ⊃ push`로 시간이 겹치므로 네 단계의 시간을 더하지 않는다.

`total = true`는 `MessageFanout.on`에만 붙인다. `chat.delivery.total{transport}`는 진입점이 만든 `DeliveryOrigin.startedNanos`부터 fan-out 정상 종료까지의 경과 시간이며 단계 시간의 합이 아니다. fan-out에서 예외가 나면 해당 단계 시간은 남기고 `total`은 남기지 않는다. 닫힌 세션은 실제 전송이 없으므로 `push` 표본에서 제외한다. 서버의 fan-out 정상 종료는 브라우저 표시나 모든 수신자의 전달 확인을 뜻하지 않는다.

측정 전 전송에 성공해 커밋될 목표 건수를 `N`, 각 메시지를 보낼 때 열린 수신 세션 수를 `Sᵢ`로 정한다. **모든 전송과 push가 성공하고 연결 수가 유지되는 통제된 실행**에서는 `receive`·`save`·`fanout`·`total`이 각각 `N`개, `push`가 `ΣSᵢ`개 늘어날 것으로 예상한다. 예를 들어 `N=10,000`, 메시지마다 열린 세션 3개면 앞의 네 지표는 각 10,000개, `push`는 30,000개다. REST만 호출하고 열린 WS 세션이 없다면 `push=0`이다. `internal` 직접 호출에는 `receive` 단계가 없다.

실제 검증은 서버 기동 뒤 누적값이 아니라 측정 구간 시작·종료의 타이머 `count` 차이로 한다. 오류 요청, 저장 실패, fan-out 예외, 닫힌 세션, 전송 예외가 있으면 위 성공 조건의 예상치와 달라지므로 각 건수와 연결 상태를 함께 기록하고 차이를 설명한다. 특히 전송 예외가 난 열린 세션의 `push` **단계 시간**은 남을 수 있지만 성공한 메시지 프레임 카운터는 늘지 않는다. 지연 분위수를 비교할 때 각 통로의 표본 수와 실패·누락 건수도 함께 제시한다. 이 지표에는 흐름 ID가 없으므로 집계된 시계열에서 메시지 한 건의 단계 시간을 다시 묶어 조회하지 않는다.
