# 2026-10-08 결정 기록

## 계획 6: JDBC·JPA 구현 비교

| # | 결정 | 이유 | 포기한 것 |
|---|---|---|---|
| 120 | **JDBC와 JPA 구현체를 공존시키고 `chat.repository=jdbc|jpa`로 선택한다. 기본값은 `jdbc`다** | 같은 계약과 부하 조건에서 비교할 수 있고, 성능 측정 전 기본 경로를 바꾸지 않는다 | 지금 JDBC를 삭제하거나 기본값을 JPA로 바꾸는 방식 |
| 121 | **계획 5b 공식 측정이 끝난 뒤 JPA 의존성을 추가한다** | 의존성만 추가해도 Hibernate와 JPA 트랜잭션 관리자가 기동해 기존 측정 조건이 달라진다 | 계획 5b 측정 중 변경 |
| 122 | **JPA 엔티티를 `infra/jpa`에 두고 도메인 record와 분리한다** | 도메인의 프레임워크 독립성과 ArchUnit 의존 규칙을 유지한다 | 도메인 record에 JPA 어노테이션을 붙이는 방식 |
| 123 | **Spring Data JPA 저장소와 도메인 저장소 어댑터를 쓴다. 조건부 UPDATE와 목록 정렬은 JPQL로 둔다** | 두 구현의 SQL 의미를 유지하며 코드량과 실행 SQL 수를 비교한다 | EntityManager만 직접 사용하거나 조건부 UPDATE를 변경 감지로 바꾸는 방식 |
| 124 | **JPA 메시지 구현은 스키마 A와 ID·time 입장 경계를 지원한다. `jpa`와 스키마 B를 함께 선택하면 기동을 거절한다** | 계획 5b에서 A를 유지했고, 지원하지 않는 조합이 비교 대상에 섞이지 않게 한다 | 검증하지 않은 B 조합을 묵시적으로 실행 |
| 125 | **Flyway를 스키마 원본으로 두고 JPA는 `ddl-auto=validate`를 쓴다** | 매핑 불일치를 기동 시 확인한다 | JPA가 테이블을 생성하거나 변경하는 방식 |
| 126 | **Open Session In View를 끈다** | 요청 전반에 걸친 영속성 컨텍스트가 DB 연결 사용 조건을 바꾸지 않게 한다 | 기본 설정으로 요청 종료까지 세션을 유지 |
| 127 | **멤버십의 할당 복합 키는 `Persistable.isNew()`로 새 행을 표시하고 `saveAndFlush()`로 INSERT 제약 위반을 즉시 확인한다** | 일반 `save()`의 `merge`가 중복 입장 행을 UPDATE한 문제(F34)를 두 DB에서 재현했다. 수정 후 저장소·API 계약이 통과했다 | 중복 입장 시 기존 경계를 갱신하거나 서비스 커밋까지 오류를 미루는 방식 |
| 128 | **W1~W5 성능·기동 시간·힙 비교는 나머지 계획이 끝난 뒤 측정한다** | 2026-10-08 사용자 요청. 계획 6에서는 기능 계약과 요청당 SQL 수를 먼저 확인한다. 중단한 예비 실행은 공식 결과에서 제외한다 | 지금 불완전한 벤치 결과로 JDBC·JPA 우열이나 기본값을 결정하는 방식 |

`chat.repository`의 기본값 변경과 JDBC 삭제는 성능 측정 결과를 본 뒤 별도로 결정한다.
