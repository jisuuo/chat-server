## 계획 7: 전달 시간 지표와 부하 측정 표본

| # | 결정 | 이유 | 포기한 것 |
|---|---|---|---|
| 129 | **전달 단계 시간은 `stage`·`transport`별 표본으로, 전체 시간은 fan-out 정상 종료 시 별도 표본으로 기록한다. 부하 측정 전에는 전송 건수와 열린 수신 세션 수로 예상 표본 수를 정하고 측정 구간의 실제 `count` 증가분과 대조한다** | 단계가 중첩되고 `push`는 세션마다 한 번 기록되므로 단계 시간을 합하거나 메시지 건수만으로 표본 수를 판단하면 지연 분포를 잘못 해석한다. 표본 수 검증으로 누락·실패·연결 변화를 먼저 찾는다 | 단계 시간의 합을 전체 시간으로 보거나, 서버 기동 뒤 누적 `count`만 확인하고 p95/p99를 비교하는 방식 |

`@DeliveryStage`의 `value`는 실행 동작이 아니라 `chat.delivery.stage{stage,transport}`의 `stage` 태그다. REST 컨트롤러와 WS 프레임 핸들러는 `receive`, `MessageService.send`는 `save`, 커밋 뒤 `MessageFanout.on`은 `fanout`, 세션별 `WsFrameSender.send`는 `push`로 기록한다. `transport`는 `rest`·`ws`·`internal`로 나눈다. 현재 동기 호출에서는 `receive ⊃ save ⊃ fanout ⊃ push`로 시간이 겹치므로 네 단계의 시간을 더하지 않는다.

당시 `total = true`는 `MessageFanout.on`에만 붙였다. 아래 ADR-143에서 세션별 송신 큐를 도입하면서 `total`의 기록 지점을 실제 송신 완료로 옮겼다. 이 문단의 동기 fan-out 의미는 변경 전 측정에만 적용한다.

측정 전 전송에 성공해 커밋될 목표 건수를 `N`, 각 메시지를 보낼 때 열린 수신 세션 수를 `Sᵢ`로 정한다. **모든 전송과 push가 성공하고 연결 수가 유지되는 통제된 실행**에서는 `receive`·`save`·`fanout`·`total`이 각각 `N`개, `push`가 `ΣSᵢ`개 늘어날 것으로 예상한다. 예를 들어 `N=10,000`, 메시지마다 열린 세션 3개면 앞의 네 지표는 각 10,000개, `push`는 30,000개다. REST만 호출하고 열린 WS 세션이 없다면 `push=0`이다. `internal` 직접 호출에는 `receive` 단계가 없다.

실제 검증은 서버 기동 뒤 누적값이 아니라 측정 구간 시작·종료의 타이머 `count` 차이로 한다. 오류 요청, 저장 실패, fan-out 예외, 닫힌 세션, 전송 예외가 있으면 위 성공 조건의 예상치와 달라지므로 각 건수와 연결 상태를 함께 기록하고 차이를 설명한다. 특히 전송 예외가 난 열린 세션의 `push` **단계 시간**은 남을 수 있지만 성공한 메시지 프레임 카운터는 늘지 않는다. 지연 분위수를 비교할 때 각 통로의 표본 수와 실패·누락 건수도 함께 제시한다. 이 지표에는 흐름 ID가 없으므로 집계된 시계열에서 메시지 한 건의 단계 시간을 다시 묶어 조회하지 않는다.

### WebSocket 프레임, 조회, 구독 (F49)

**WebSocket 프레임이란?** WebSocket 연결로 오가는 프로토콜 단위로, 종류(opcode), 마지막 조각 여부(FIN), 길이, 데이터(payload) 등의 정보를 가진다. 하나의 논리적 메시지가 여러 프레임으로 나뉠 수도 있다. 이 실험에서 관찰한 `framereceived`는 채팅 JSON 데이터가 담긴 수신 프레임이다. 프레임 수신 사실만으로 화면 컴포넌트가 그 메시지를 표시했다는 뜻은 아니다.

**연결이 유지되는데 어떻게 오래된 조회 응답을 뒤늦게 전달하는가?** B가 방 화면을 다시 열 때 Playwright가 최신 메시지 GET의 응답을 먼저 받아 보관한다. A가 REST로 새 메시지를 저장하고 B 브라우저가 그 메시지 ID의 WebSocket 프레임을 수신한 것을 확인한 뒤, 보관한 이전 GET 응답을 B 화면에 전달한다. 실제 서버가 오래된 응답을 임의로 만든다는 뜻은 아니다. React StrictMode가 시작한 두 GET에는 같은 이전 스냅샷을 전달해 순서를 통제했다.

**화면과 소켓이 열려 있는데도 메시지가 안 보이는 이유는?** 앱 수준 WebSocket은 연결되어 있지만, 방 컴포넌트가 최초 조회를 끝내고 `ready`가 되기 전에는 해당 방의 프레임을 처리하는 구독이 아직 없다. 이 틈에 브라우저까지 도착한 프레임이 화면 상태에 반영되지 않고, 뒤이어 오래된 조회 결과로 화면을 채우면 새 메시지가 빠진다. 새로고침 뒤 새 GET으로는 보인다.

재검토 뒤 E2E는 Playwright의 프레임 수신 확인에 더해 화면의 `받은 프레임` 수 증가도 기다린다. 이 수치는 앱의 `WebSocket.onmessage`에서 갱신되므로, 네트워크 도착만 확인하고 메시지 이벤트 처리를 기다리지 않아 생기는 거짓 양성을 줄인다. 이후 짧은 렌더링 여유를 두고 화면의 메시지 부재를 검사한다.

```text
시간 ↓       A(발신자)                 서버/Playwright                  B 브라우저
             |                              |                              |
             |                              |<--- 방 최신 GET --------------|
             |                              |  이전 응답 보관                 | 방 구독 전
             |--- REST 메시지 전송 -------->| DB 저장·커밋                  |
             |<-- REST 201 -----------------|--- 새 메시지 WS 프레임 ------>| 프레임 수신 확인
             |                              |--- 보관한 이전 GET 응답 ----->| 이전 목록 표시
             |                              |                              | 새 메시지는 화면에 없음
             |                              |<--- 새로고침 GET -------------|
             |                              |--- 새 조회 결과 ------------->| 새 메시지 표시
```

### 느린 수신자와 실험용 수신 큐 (F4)

**수신 콜백 실행이란?** `WsTestClient`의 WebSocket 라이브러리가 텍스트 메시지를 애플리케이션에 넘길 때 `handleTextMessage`를 호출하는 것이다. 콜백 안에서 `System.nanoTime()`을 기록한다. 이는 테스트 클라이언트가 메시지를 처리하기 시작한 시각에 가깝지만, TCP 패킷의 정확한 도착 시각이나 화면 렌더링 시각은 아니다.

**왜 큐에 넣고, 왜 발신 쪽에서 꺼내는가?** 큐는 프로토콜이나 서버의 전송 큐가 아니라 `WsTestClient` 안의 테스트 전용 `LinkedBlockingQueue<ReceivedFrame>`이다. 빠른 수신자의 비동기 콜백이 `(payload, receivedNanos)`를 넣고, REST 전송 요청도 수행하는 **실험 진행 스레드**가 나중에 꺼내 메시지 ID와 시각을 검사한다. 큐를 꺼내는 스레드를 실제 채팅 발신자나 WebSocket 송신 콜백으로 해석하면 안 된다. 큐에서 꺼낸 시각을 도착 시각으로 쓰면 REST 응답 대기와 테스트 스케줄링 시간이 섞이므로, 콜백 시각으로 바꿨다.

```text
실험 진행 스레드                 서버                         빠른 수신자 WsTestClient
      t0 -- REST 전송 ---------> DB 저장·커밋
                                느린 소켓에 동기 전송(막힐 수 있음)
                                빠른 소켓 WS 프레임 ----------> 수신 콜백
                                                              도착 시각 기록
                                                              테스트 큐에 넣기
          <----- REST 201 ------
          큐에서 꺼내 ID·시각 검사 <--------------------------- 테스트 큐

기존 측정: 큐에서 꺼낸 시각 - t0  (REST 대기 시간이 섞임)
현재 측정: 수신 콜백 시각 - t0  (받은 프레임에 한해 계산)
```

느린 소켓에서 약 20초 쓰기 시간 초과가 난 전송은 REST 201과 DB 저장이 확인됐지만, 뒤 순서의 빠른 수신자에게 해당 ID가 오지 않았다. 표의 `fastMaxMs`는 **받은 프레임만** 대상으로 하므로 누락 건의 도착 시간이 아니다.

### half-open 연결과 종료 콜백 (F5·F3)

**출력 스트림이나 세션을 더 길게 유지하면 보완되는가?** F5 실험 프록시에서 서버 쪽 출력 스트림을 닫지 않는 것은 서버가 종료 신호를 받지 못하는 half-open 조건을 **재현**하기 위한 것이다. 운영 서비스에서 세션 수명만 늘려서는 끊긴 경로를 알아낼 수 없다. 서버가 생존 확인을 하거나 쓰기 실패를 감지하고 정리하는 방식은 별도로 결정해야 한다.

**왜 프록시가 종료 신호를 서버에 전달하지 않는가? 바로 끊김을 늦추는가?** F5는 네트워크 경로가 조용히 끊겨 서버가 FIN/EOF를 받지 못하는 상황을 만드는 실험이다. freeze 이후 클라이언트 쪽 EOF를 프록시가 서버에 전달하면 서버는 정상적인 연결 종료를 관찰하므로 half-open 조건이 사라진다. 프록시가 출력 종료를 전파하지 않는 수정은 실험 조건을 정확히 만든 것이지, 서비스의 연결 복구나 종료 감지 지연을 해결한 것이 아니다.

**왜 종료 콜백 시각을 확인해야 하는가? 실패 이유를 화면에 알려주기 위한 것인가?** F3의 서버 세션 게이지가 종료 뒤에도 남은 원인을 구별하기 위해서다. 클라이언트 `close()` 완료 및 클라이언트 종료 이벤트는 서버의 `afterConnectionClosed` 실행 완료를 증명하지 않는다. 서버 종료 콜백 시각과 세션 저장소 제거 시각을 함께 보면 콜백 지연인지, 콜백 뒤 제거 실패인지 구분할 수 있다. 현재 실험에는 서버 콜백 시각이 없으므로 잔여 세션 1개의 원인을 저장소 경쟁만으로 단정하지 않는다. 이 계측 자체는 사용자에게 종료 실패 이유를 표시하는 기능이 아니다.

## 계획 7: 세션 저장소 동시성 보완

| # | 결정 | 이유 | 포기한 것 |

## 계획 7: 느린 수신자 격리

| # | 결정 | 이유 | 포기한 것 |
|---|---|---|---|
| 143 | **커밋 뒤 멤버 조회와 세션별 큐 등록은 요청 스레드에서 하고, 실제 WebSocket 쓰기는 세션마다 직렬 송신 작업자에서 한다.** 세션당 대기 프레임은 32개까지 허용한다. 초과하면 대기 프레임을 실패로 기록하고 그 연결을 1013으로 닫는다. 오류 프레임도 같은 큐를 지난다. | F4 실험에서 읽지 않는 수신자의 20초 쓰기가 REST 응답을 막고 뒤 수신자의 프레임까지 누락시켰다. 세션별 작업자는 다른 수신자의 전송을 격리하고 같은 세션의 쓰기 경쟁도 피한다. 유한한 큐는 느린 연결의 메모리 점유에 상한을 둔다. | 동기 순차 전송, 무제한 큐, 큐가 찼을 때 기존 메시지를 조용히 버리고 연결을 유지하는 방식 |

`chat.delivery.stage{stage=fanout}`은 큐 등록까지, `stage=push`는 세션 작업자의 실제 쓰기를 잰다. `chat.delivery.total{transport}`은 해당 메시지의 모든 대상 세션 작업이 **성공**한 시점에 시작 시각부터 기록한다. 하나라도 실패하면 `chat.delivery.failed{transport}`를 올리고 완료 시간 표본에서 제외한다. 큐 초과로 버린 대기 프레임 수는 `chat.ws.outbound.dropped{reason=queue_full}`에 기록한다. 닫힌 세션은 대상에서 제외한다. 이 완료는 서버의 소켓 쓰기 완료이며 브라우저 처리 확인은 아니다.

같은 F4 실험 조건에서 읽지 않는 수신자를 붙인 400건은 REST 최대 99ms, 빠른 수신자 ID 누락 0건이었다. 느린 연결의 대기 프레임 33개가 버려졌고 해당 메시지의 전달 실패가 39건 기록됐다. 큐 초과 후 연결 종료 콜백이 오기 전에도 새 메시지가 해당 세션에서 실패할 수 있어 두 건수는 같지 않다. 이 결정을 기록할 당시 연결 종료 뒤 따라잡기는 없었으며, 아래 ADR-145에서 추가했다. 이 표본은 단일 서버·해당 메시지 크기와 전송률에서의 결과다.

## 계획 7: half-open 감지와 재연결 복구

| # | 결정 | 이유 | 포기한 것 |
|---|---|---|---|
| 144 | **서버가 10초마다 WebSocket ping을 보내고, 연결 이후 또는 마지막 pong 이후 30초 동안 pong이 없으면 그 세션을 닫는다.** ping도 세션 송신 큐를 지나고 pong은 연결별 생존 시각만 갱신한다. | F5의 조용히 끊긴 연결이 60초 이상 남았다. 브라우저는 WebSocket ping에 자동으로 pong을 돌려주므로 화면 프로토콜을 늘리지 않고 서버에서 죽은 경로를 찾는다. | 쓰기 실패가 날 때까지 기다리기, 클라이언트 JSON heartbeat |
| 145 | **방 화면은 첫 조회 전에 소켓을 구독하고 조회 중 받은 메시지를 버퍼에 담아 조회 결과와 id로 병합한다. 재연결 뒤에는 최신 메시지부터 현재 화면에서 가장 오래된 id에 닿을 때까지 페이지를 조회해 병합한다.** 일시적인 조회 오류는 연결이 열린 동안 2초 뒤 다시 시도한다. | F49에서 조회 응답 고정 중 받은 push가 화면에서 빠졌고, F6에서 끊긴 동안 저장한 메시지가 재연결 뒤에도 보이지 않았다. 현재 보이는 구간까지 다시 읽으면 단일 `after` 커서보다 커밋 순서 역전(F22)에 덜 취약하다. | 재연결 때 최신 50건만 읽기, 메시지 id 하나만 `after` 커서로 삼기, 서버 측 재전송 상태 |

F5의 기존 TCP freeze 실험을 같은 조건에서 다시 실행했다. freeze 뒤 서버 세션 증분은 0·10·30초에 각각 1, 60초에 0이었다. heartbeat 종료 시간은 스케줄러 틱에 따라 달라지므로 이 표본은 정확히 30초에 닫힌다는 뜻이 아니다. 종료 뒤 30건의 REST 전송은 모두 201이었다. 별도 정상 클라이언트 실험에서는 자동 pong을 주고받는 연결이 40초 뒤에도 열려 있고 세션 게이지에도 1개로 남았다.

F6·F49는 기존 Playwright 통제 실험을 복구 기대값으로 바꿔 각각 통과했다. 재연결 조회는 수신자의 **현재 화면에 있는 가장 오래된 id**까지만 내려간다. 그보다 작은 id가 뒤늦게 커밋된 경우와 연결이 열린 채 push만 누락된 경우(F50)는 이 결정으로 완전히 탐지하지 못한다. 재연결 전에 보인 메시지가 없고 누락분이 많으면 처음부터 끝까지 페이지를 읽어 요청량이 커질 수 있다. 표시 지연 상한과 더 강한 커밋 순서 커서는 후속 설계 과제다.

## 계획 7: 열린 연결의 누락 메시지 재대조

Playwright가 B의 WebSocket 연결을 열린 채 유지하고 A가 저장한 메시지 프레임 한 개만 버렸다. B 화면에서는 즉시 보이지 않았으나 60초 타이머를 진행한 뒤 새로고침 없이 보였고 연결 상태는 계속 `연결됨`이었다. 이 검증은 제어한 한 메시지와 성공한 조회에 대한 결과다. 조회는 완료 후 다음 60초를 예약하므로 실제 표시 지연에는 조회 소요 시간이 더해진다. 최신부터 화면의 가장 오래된 메시지까지 매번 페이지 조회하므로 표시 범위가 길거나 신규 메시지가 많으면 요청량이 커진다. 화면보다 더 오래된 낮은 id의 늦은 커밋은 여전히 놓칠 수 있으며, 이를 완전히 막으려면 커밋 순서 기준 조회 커서가 필요하다.

### Plan7 코드 리뷰 후 오류 경로 보완

옆 pane의 Codex가 현재 워킹트리를 읽기 전용으로 검토해 세 가지 오류 경로를 지적했다. ADR-144의 시간 초과 세션은 실제 종료까지 추적해 `close` 실패 시 다음 tick에 다시 닫고, 종료 콜백이 없어도 닫힌 세션의 등록을 정리한다. pong 갱신과 timeout 판정은 세션별 원자적 갱신으로 묶는다. ADR-143의 `chat.delivery.failed`는 커밋 후 멤버 조회 실패, 프레임 준비·큐 등록의 동기 실패도 메시지당 한 번 센다. 큐 등록 중 일부 완료 콜백이 먼저 와도 등록이 끝나기 전에 성공 지표를 기록하지 않는다. ADR-145의 첫 조회가 실패하면 대기 중인 push를 비우고 이후 push 버퍼링을 멈춘다. 이를 통해 오류 화면을 오래 열어 둔 동안 버퍼가 계속 자라는 경로를 닫는다.

같은 리뷰어의 재검토에서는 추가로 세 경로를 확인했다. 종료 호출이 막힌 동안 `WsOutboundQueue`는 세션당 닫기 작업을 하나만 실행한다. heartbeat는 최초 닫기 요청 후 30초가 지나도 세션이 열려 있으면 세션 저장소와 송신 큐의 등록을 해제한다. 컨테이너의 물리 연결 종료까지 보장하는 처리는 아니다. 주기 재조회에서 `NOT_A_MEMBER`를 받으면 대기 push를 비우고 버퍼링을 중단해 재입장 경계 전의 늦은 프레임을 새 조회 결과에 섞지 않는다. 첫 조회의 일시 오류 화면에는 `다시 시도` 버튼을 제공하고 최신 조회를 다시 실행한다.
