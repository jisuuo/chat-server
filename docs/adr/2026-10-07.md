# 결정 기록 (ADR) 2026-10-07

> 이날 내린 결정 (ADR-040 ~ ADR-043). 결정 기록은 날짜별 파일로 둔다 (ADR-043). 결정이 바뀌면 행을 지우지 않고 취소선과 대체 ADR 번호를 남긴다.

| # | 결정 | 이유 | 포기한 것 |
|---|---|---|---|
| 040 | **두 DB 컨테이너의 자원: 각각 CPU 2개, 메모리 1GB, 캐시 메모리 256M(컨테이너 메모리의 25%)** (`innodb_buffer_pool_size=256M`, `shared_buffers=256MB`). 내구성 설정도 명시한다 (`innodb_flush_log_at_trx_commit=1`, `synchronous_commit=on`). `infra/compose.db.yml`에 둔다 | 제한이 없으면 두 DB가 Docker 자원(CPU 8개, 약 7.6GB)을 나눠 가지려 해서 측정값이 DB 차이인지 자원 경쟁인지 구분할 수 없다. 1GB면 이후 앱 2대, nginx, Redis, 모니터링을 같이 띄워도 들어가고, 데이터를 조금만 늘려도 메모리를 넘치는 조건(C1)을 만들 수 있다. 25%는 PostgreSQL의 흔한 권장치다 | 2GB(캐시 512M)의 여유. MySQL 전용 서버 권장치(50~75%)보다 낮아 MySQL이 조금 불리할 수 있다 (예상, 미측정). PostgreSQL은 `shared_buffers` 밖에서 운영체제 파일 캐시도 쓰므로 같은 256M이어도 실제 캐시 효과가 같다고 단정할 수 없다 |
| 041 | **messages 스키마 A와 B를 바꿀 때는 DB를 비우고 다시 시작한다** (`docker compose -f infra/compose.db.yml down -v` → `up -d` → 데이터 다시 넣기). 스키마별로 방 데이터를 따로 두지 않는다. 절차는 `docs/design/experiments.md`에 둔다 (코드 리뷰 P1) | `rooms.last_message_id`와 `room_members.joined_message_id`는 두 메시지 테이블이 함께 쓰는데 `messages`와 `messages_b`는 번호를 각자 1부터 매긴다. compose MySQL에서 재현: A로 5건 보낸 뒤 B로 바꾸자 방 갱신이 매번 0행, 새로 입장한 사용자의 경계가 5로 잡혀 B 메시지 3건이 보이지 않았고 본인이 보낸 메시지도 보이지 않았다. A/B는 같은 데이터로 번갈아 재는 실험 조건이라, 두 벌의 데이터를 한 DB에 두면 같은 캐시 메모리를 나눠 써서 C1 비교가 오염된다. 측정은 원래 매번 대량 데이터를 새로 넣으므로 초기화 절차와 맞다 | 스키마를 바꿀 때마다 데이터를 다시 넣는 시간. 사람이 절차를 잊을 수 있다 (기동 시 검사 코드는 넣지 않음). PostgreSQL은 구조가 같아 같은 문제가 생길 것으로 예상하지만 재현하지 않았다 |
| 042 | **스키마 마이그레이션 테스트는 테이블 5개의 존재만 확인하고, PK·FK·인덱스 검증은 추가하지 않는다** (코드 리뷰 P2) | 장애 선행(ADR-034)에 따라 문제가 생긴 뒤 원인을 찾는다. 빠졌을 때 드러나는 곳이 있다: `(room_id, id)` 인덱스는 인덱스 부재 실험(F16)에서 일부러 없애 보고, `room_members`의 PK와 FK는 저장소 계약 테스트(계획 1 작업 5의 "중복 입장 409", "없는 사용자 401")가 실패한다 | 제약이 빠졌을 때 원인이 스키마라는 것을 스키마 테스트에서 바로 알 수 있는 점. `messages_b` PK의 컬럼 순서처럼 동작으로 드러나지 않는 차이는 측정 전까지 모를 수 있다 |
| 043 | **결정 기록(ADR)을 날짜별 파일로 나눠 `docs/adr/` 폴더에 모은다** (`adr/YYYY-MM-DD.md`, 그날 내린 결정만). 번호는 날짜와 상관없이 이어서 매긴다. ADR-035의 `adr.md` 한 파일 구조를 바꾼다 | 사용자 요청. 결정이 쌓이면서 한 파일이 길어지고, 언제 내린 결정인지 파일만 보고 알 수 있다. 일지(`journal/YYYY-MM-DD.md`)와 날짜가 같은 파일로 짝지어진다 | 한 파일에서 전체 결정을 한눈에 훑는 편의 (번호로 찾으려면 날짜를 알아야 함). 노션의 ADR 누적 문서 구조와 달라져 동기화할 때 맞춰야 한다 |
