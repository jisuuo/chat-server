# 실험 설계

> 누적 문서. 장애 실험과 비교 실험의 측정 방법과 판정 기준.

## DB 비교 실험 설계 (ADR-003)

### 워크로드 (실제 요청)
| ID | 요청 | 실제 상황 | SQL 형태 |
|---|---|---|---|
| W1 | 메시지 저장 | 메시지 전송 API | `INSERT` (동시 다발) |
| W2 | 최근 메시지 조회 | 채팅방 입장 | 방별 최신 50건 (cursor) |
| W3 | 과거 메시지 스크롤 | 위로 스크롤 | 깊은 페이지: offset과 cursor |
| W4 | 폴링 | Step 1 폴링 | `WHERE room_id=? AND id > lastId` |
| W5 | 혼합 | 실제 트래픽 | 읽기 90% / 쓰기 10%, 인기 방에 쏠림 |

데이터: 방 1만 개, 메시지 수백만~1천만 건, 방별 분포를 고르지 않게(소수 인기 방 집중).

### 운영 조건
| ID | 조건 | 목적 |
|---|---|---|
| C1 | 데이터가 메모리에 다 들어갈 때와 넘칠 때 | 성능이 꺾이는 지점 확인 (컨테이너 메모리 제한으로 재현) |
| C2 | 동시 커넥션 10 / 50 / 200 | 어느 쪽이 먼저 무너지는지 |
| C3 | 인기 방 하나에 쓰기 집중 | 인덱스 끝부분 쓰기 경합 |
| C4 | DB 재시작 직후 (cold cache) | 정상 성능까지의 회복 시간 |

### 검증 지표
- 사용자 관점: TPS, 응답 시간 p50 / p95 / p99, 에러율
- DB 내부: 실행 계획(`EXPLAIN ANALYZE`), 버퍼 캐시 적중률, 락 대기
- 자원: CPU, 메모리, 디스크 I/O, 테이블과 인덱스 크기

### 공정성 규칙
- 두 DB에 같은 CPU와 메모리 제한 (Docker)
- 내구성 설정 일치: MySQL `innodb_flush_log_at_trx_commit=1`, PostgreSQL `synchronous_commit=on`
- 메모리 설정 비율 일치: `innodb_buffer_pool_size`와 `shared_buffers`
- warm-up 후 3회 측정, 중앙값 사용
- 한계: Mac Docker는 VM 위에서 동작하므로 절대 수치가 아니라 상대 비교로만 해석한다.

## 입장 경계 실험 설계 (F18, ADR-008, 009)

### 배경
재입장한 유저에게는 재입장 이후 메시지만 보인다 (ADR-008). 경계를 무엇으로 저장할지 실험으로 결정한다.
- `joined_at` (시각): 직관적이지만 F2와 같은 함정(같은 시각, 정밀도, 서버 간 시계 차이)이 예상된다.
- `joined_message_id` (입장 시점의 마지막 메시지 id): 조회 조건이 `id > joined_message_id`가 되어 폴링과 같은 `(room_id, id)` 인덱스를 탄다. 단, id는 INSERT 시점에 발급되고 다른 트랜잭션에는 COMMIT 시점에 보인다는 차이가 있다. 이 차이의 영향은 실험으로 확인한다.

### 판정 기준 (ADR-009: 커밋 순서 기준)
- 입장이 커밋된 **뒤에** 커밋된 메시지는 반드시 보여야 한다. 안 보이면 **유실**.
- 입장이 커밋되기 **전에** 커밋된 메시지는 보이면 안 된다. 보이면 **유출**.
- 입장과 **동시에 진행 중이던** 메시지는 어느 쪽이든 허용한다. 단, 목록 조회와 폴링에서 일관되게 보여야 한다. 다르면 **불일치**.

### 방법
1. 경계 전략을 인터페이스로 추상화하고 `TimeBoundary`, `IdBoundary` 두 구현체를 만든다.
2. 한 방에 여러 스레드가 계속 메시지를 쓰는 동안, 유저 한 명이 나갔다가 재입장한다. 수천 번 반복한다.
3. 매 반복마다 판정 기준에 따라 유출 / 유실 / 불일치를 센다.

### 지표
| 지표 | 의미 | 심각도 |
|---|---|---|
| 유출(leak) | 입장 전 메시지가 보임 | 프라이버시 문제 |
| 유실(loss) | 입장 후 메시지가 안 보임 | 치명적 |
| 불일치 | 목록과 폴링 결과가 다름 | 사용자 혼란 |
| 조회 성능 | 실행 계획, 응답 시간 | 인덱스 사용 여부 |

### 바꿔 볼 조건
- 시간 정밀도: MySQL `DATETIME`(기본 초 단위) / `DATETIME(6)`, PostgreSQL `timestamp`
- 시각을 찍는 주체: 애플리케이션(`LocalDateTime.now()`) / DB(`NOW()`)
- 서버 간 시계 차이: `Clock`을 주입해 수십 ms 어긋나게 설정
- 동시 쓰기 스레드: 1 / 10 / 50
- 격리 수준: 각 DB 기본값(MySQL REPEATABLE READ, PostgreSQL READ COMMITTED)과 READ COMMITTED 통일 (ADR-034)
- DB: MySQL / PostgreSQL (ADR-003 비교 데이터로도 사용)

## PK 스키마 실험 설계 (F15, F16, ADR-013, 014)

### 비교 대상
- (A) 단일 PK `id` + 보조 인덱스 `(room_id, id)`: 새 메시지는 항상 B-tree 오른쪽 끝에 추가된다 (쓰기 지역성 좋음).
- (B) 복합 PK `(room_id, id)`: MySQL InnoDB에서 같은 방 메시지가 물리적으로 연속 저장된다 (읽기 지역성 좋음). 대신 쓰기 위치가 활성 방 수만큼 흩어진다 (페이지 분할, 메모리 압박, 랜덤 I/O).
- 즉 (B)는 읽기를 빠르게 하는 대신 쓰기를 느리게 만드는 거래다. 읽기 속도만으로 결정하지 않는다.

### 가설: (A)에서는 PostgreSQL이 구조적으로 유리하다
- PostgreSQL 보조 인덱스는 행의 물리적 위치(TID)를 직접 가리킨다.
- MySQL 보조 인덱스는 PK 값을 가리키므로 PK B-tree를 한 번 더 탄다.
- 메모리에 다 들어가면 차이는 작고, 메모리를 넘칠 때(C1) 커질 것으로 예상한다.
- (A)로만 비교하면 MySQL의 최대 무기(B)를 뺀 비교가 된다. 그래서 DB 비교를 두 종류로 나눈다.
  - 같은 스키마 비교: MySQL(A)와 PostgreSQL(A)
  - 각자 최선의 스키마 비교: MySQL(B)와 PostgreSQL(A)

### 측정 매트릭스
| 구성 | 메모리에 들어갈 때 | 메모리를 넘칠 때 (C1) |
|---|---|---|
| MySQL (A) | ✓ | ✓ |
| MySQL (B) | ✓ | ✓ |
| PostgreSQL (A) | ✓ | ✓ |

PostgreSQL (B)는 clustered 효과가 없어서 제외한다 (확인용으로 한 번만 실행 가능).

읽기/쓰기 비율은 두 가지로 측정한다.
- 폴링 시점 (Step 1): 읽기 위주
- WebSocket 시점 (Step 2 이후): 폴링 조회가 사라져 쓰기 비중 증가

### 지표
| 관점 | 지표 | 측정 방법 |
|---|---|---|
| 읽기 | W2(최근), W3(과거 스크롤), W4(폴링)의 p99 | k6 |
| 쓰기 | W1의 TPS와 p99, C3(인기 방 쏠림) 포함 | k6 |
| DB 내부 | 쿼리당 읽은 페이지 수, 디스크 읽기 횟수, 페이지 분할 수 | MySQL `Innodb_buffer_pool_reads`, `INNODB_METRICS` page split / PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` |
| 저장 공간 | 테이블과 인덱스 크기 | `information_schema` / `pg_relation_size` |
| 개발·운영 비용 | JPA 복합키 매핑, AUTO_INCREMENT 제약, DB별 스키마 분기 | 정성 평가 |

평균이 아니라 p99를 본다. 사용자가 체감하는 건 "가끔 멈칫하는 순간"이다.

### 판정 규칙 (ADR-014, 측정 전에 확정)
> **(B)를 채택하는 조건**: 메모리를 넘치는 조건(C1)에서 읽기 p99가 **30% 이상 개선**되고, 동시에 쓰기 p99 악화가 **10% 이내**일 때. 둘 중 하나라도 못 미치면 (A)를 유지한다.
