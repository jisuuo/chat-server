# 2026-10-08 작업 일지

## 계획 6 진행

- **채팅 UI 자동 확인 (측정):** 프론트 단위 테스트 17개 파일·85건, ESLint, Node 22.22.2의 프로덕션 빌드가 통과했다. Playwright Chromium E2E 4건에서 두 사용자의 대화·퇴장·재입장, 비멤버 링크, 375px 목록/대화 전환과 다크 테마 CSS, 55개 메시지의 과거 조회 위치 보존·상대 메시지 알림, Shift+Enter 줄바꿈과 Enter 전송을 확인했다. 실제 한글 IME 조합은 단위 테스트로만 확인했다.
- **JDBC 기준선 (측정):** 저장소 코드 329행, 직접 쓴 `jdbc.sql(` 13곳, `ResultSet` 변환 메서드 3곳. JPA 의존성 추가 후 JDBC 기본 경로 기동은 3.333초였고 Hibernate 및 JPA 트랜잭션 관리자가 활성화됐다. 추가 전 기동 시간은 비교 가능한 로그를 남기지 못했다.
- **JPA 계약 최초 실행 (측정):** User·Room 구현의 MySQL·PostgreSQL 계약이 통과했다. Membership은 두 DB 모두 8건 중 중복 입장 1건이 실패했다. Hibernate SQL에서 두 번째 저장이 SELECT 뒤 UPDATE를 실행했다. 당시 백엔드 테스트는 326건 중 이 2건만 실패했다. 예상했던 기본 `save()`의 복합 키 병합 문제가 재현됐다(F34). 같은 날 아래와 같이 해결했다.
- **기록:** UI 세부 결정은 전날 기록된 ADR-107~119를 재사용하고, JPA 가설 F34~39 및 화면 가설 F40~42를 장애 실험 목록에 적었다. 비교 수치와 미측정 항목은 [진행 중 보고서](../reports/2026-10-08-jdbc-vs-jpa.md)에 둔다.
- **중복 입장 해결 (F34, ADR-127):** 할당 복합 키를 `Persistable.isNew()`로 새 엔티티로 표시하고 `saveAndFlush()`에서 INSERT 제약 위반을 즉시 확인하도록 바꿨다. MySQL·PostgreSQL의 저장소와 API 계약에서 중복 409·없는 사용자 401이 통과했다.
- **JPA 기능 비교:** 메시지 스키마 A의 JPA 저장소와 ID·time 입장 경계 조회를 추가했다. `jpa+B` 기동 거절을 확인했다. JDBC·JPA의 두 DB API 계약과 전체 백엔드 테스트 373건이 통과했다. SQL 횟수 실험은 4조합에서 통과했고 방 만들기/입장/전송/최신/폴링/방 목록의 횟수가 두 구현에서 모두 2/2/3/2/2/1로 같았다.
- **성능 측정 연기 (ADR-128):** 사용자 요청으로 W1~W5 부하·기동·힙 비교는 나머지 계획 완료 후 실행한다. 시작했다가 중단한 W2 두 반복은 공식 자료에서 제외했다. 격리 벤치 컨테이너는 정지하고 볼륨은 보존했다. `chat.repository` 기본값은 `jdbc`다.
- **다음:** 나머지 계획 뒤 동일 조건으로 JDBC·JPA 성능을 비교하고 기본값 변경·JDBC 삭제 여부를 결정한다.

## 계획 7 웨이브 5: WebSocket E2E·브라우저·기록

- **E2E 측정:** MySQL 로컬 백엔드와 Vite proxy에서 Playwright Chromium 5건이 통과했다. 두 사용자 대화에서 수신 `message` 프레임을 확인했고, 같은 사용자 다른 탭의 퇴장 뒤에는 송신 `send`와 수신 `error`(`NOT_A_MEMBER`) JSON 프레임을 확인했다. 기본 WebSocket 화면의 `messages?after=` 폴링 요청은 0건이었다. `?transport=polling`에서는 폴링 요청이 1건 이상이고 채팅 소켓 송수신 프레임은 0건이었다. 비멤버 링크, 375px 화면·다크 테마, 과거 조회 위치·새 메시지 알림·줄바꿈 전송도 통과했다. Vite가 탭 종료 시 `EPIPE` proxy 경고를 출력했지만 최종 테스트 결과와 열린 화면의 전송에는 영향을 주지 않았다.
- **Chrome 직접 측정:** 로컬 `127.0.0.1:5173`에서 사용자 #78과 #79가 방 #46에 입장했다. #78의 전송이 #79 화면에 즉시 보였고 #79의 연결 패널은 `연결됨`, 받은 프레임 1이었다. #79의 다른 탭에서 방을 나간 뒤 기존 탭이 전송하자 비멤버 화면으로 바뀌었고, `WS_ACCESS`에 `frameType=send`, `result=NOT_A_MEMBER`가 남았다. `?transport=polling` 화면에는 기존 폴링 상태 패널이 보였다. 기본 통로의 폴링 요청 부재와 WS `message` JSON은 위 E2E의 네트워크 이벤트로 확인했다.
- **재시작 측정:** 백엔드를 중지하자 #78의 패널이 `끊김`, 마지막 종료 코드 `1006`으로 바뀌고 1초 고정 간격 재시도를 반복했다. 재기동 후 `연결됨`으로 돌아왔고 당시 누적 재연결 횟수는 14였다. 재연결 뒤 전송 프레임과 본인 수신 프레임 수가 각각 증가했다. 브라우저의 1초 고정 재시도는 확인했지만 대규모 재접속 집중(F47)은 가설이다.
- **재연결 누락 예비 재현(F6):** Chrome DevTools에서 #78 탭을 Offline으로 만든 상태로 백엔드를 재시작해 기존 WS를 끊고 새 연결을 차단했다. 서버가 준비된 뒤 `POST /api/rooms/46/messages`를 #78로 보내 `오프라인 동안 REST 저장`(id 395)이 201로 저장됐다. Offline을 해제하자 연결 패널은 `연결됨`(당시 재연결 26회)이 되었으나 이 메시지는 화면에 없었다. 새로고침 뒤 최신 REST 조회에서 보였다. 재연결만으로 누락분을 따라잡지 않는 경로를 브라우저에서 확인했다. 네트워크 경계와 표본을 통제한 작업 12 실험은 별도로 남긴다. Vite 프로세스를 중지했다 다시 켠 첫 시도는 HMR이 페이지를 새로고침해 메시지가 보여 F6 판단 표본에서 제외했다.
- **로그·지표 측정:** `backend/logs/app.json`에서 `/ws`의 `ACCESS` 101과 `WS_ACCESS` connect·frame·close 행을 확인했다. WS 행에는 이벤트별 `requestId`, `userId`, `sessionId`가 있었고 종료 코드 1001·1006, 비멤버 프레임 결과가 기록됐다. 재기동 뒤 `/actuator/prometheus`에서 `chat_ws_sessions=3`, `chat_ws_frames_total{type=send}=1`, `{type=message}=1`, `chat_delivery_stage_seconds_count`의 receive/save/fanout/push 각각 1, `chat_delivery_total_seconds_count{transport=ws}=1`을 확인했다. `push=1`은 그 시점에 열린 소켓 3개 중 방 멤버인 #78의 한 세션에만 보낸 결과다. 이 수치는 해당 서버 기동 이후 누적값이며 부하 지연 비교 자료는 아니다.
- **동시 접속 예비 관찰(F3):** Chrome의 여러 탭을 여는 중 `app.json`에 `ConcurrentModificationException` 1건이 났고 스택은 `HashMap.computeIfAbsent` → `WsSessionRegistry.add`였다. 이후 확장한 E2E의 초기 전체 실행 두 번에서는 빠르게 두 사용자를 여는 조건에서 전송 프레임 처리 결과는 `ok`인데 발신자 화면의 `message` push가 5초 안에 보이지 않았다. 두 현상의 인과관계와 DB 저장 여부는 확인하지 못했다. E2E는 기본 대화 검증의 연결 순서를 한 사용자씩 안정화하고 기대 시간은 유지했다. 해당 테스트 3회 반복과 최종 전체 5건은 통과했다. F3 발생률·전달 누락 여부는 작업 9에서 분리해 측정한다.
- **기록:** ADR-130~141에 인증·프로토콜·동기 fan-out·의존 방향·세션 저장소·관측·프론트 통로·Vite origin 결정을 기록했다. F43~F49는 재현 전 가설로 추가했다. 전송당 멤버 조회 1회가 늘어 기존 실험과 조건이 달라진 점도 장애 실험 문서에 남겼다. F50은 코드 검토 상태 그대로 유지했다.
- **최종 통합 확인:** 백엔드 `./gradlew test`는 72개 suite·434건이 통과했고 실패·오류·건너뜀은 0건이었다. 프론트 `npx vitest run`은 21개 파일·106건, `npx tsc -b`, `npm run lint`, Playwright Chromium E2E 5건이 모두 통과했다. 원시 프레임 검증 추가 뒤 첫 E2E만 3회 연속 통과했다. E2E의 탭 종료 시 Vite `EPIPE` 경고는 반복됐다. 커밋은 하지 않았다.

## 계획 7 웨이브 6~9: F3~F6 장애 실험

- **F3 세션 저장소 동시성 (측정):** 직접 실험 3회(8스레드·10초)에서 CME 27~41건, NPE 7,110~7,508건, 추가 직후 유실 386~552건을 관찰했다. 200개 실제 연결의 동시 접속·종료는 3회 중 2회에서 연결 뒤 2~3개 부족했고, 1회에서 종료 뒤 1개가 남았다. 종료 작업 오류는 0건이고 클라이언트 종료 이벤트는 매회 200개였다. 첫 구현은 예외 객체를 무제한 수집해 테스트 JVM의 힙을 소진했으므로 표본에서 제외했다. 종류별 카운터와 1ms 간격으로 바꿔 재측정했고, 직접 실험 저장소를 서버 저장소에서 분리했다.
- **F4 느린 수신자 (측정):** 읽지 않는 소켓을 빠른 수신자보다 멤버 순서 앞에 뒀다. 두 반복에서 정상 50건의 REST p50/최대는 11~12/36~44ms, 읽지 않음 조건 162건은 7~9/20,076~20,083ms였다. 두 번 모두 152번째 전송에서 쓰기 시간 초과가 났다. 전송 162건 모두 REST 201·DB 저장이었지만 빠른 수신자는 해당 1건을 받지 못했다. 서버는 `TransactionSynchronization.afterCompletion threw exception`과 `SocketTimeoutException: Write timeout`을 기록했다. 코드 리뷰 뒤 수신 콜백에서 실제 프레임 도착 시각을 기록하도록 바꿨다. 처음 순서가 반대였던 실행은 뒤 수신자 영향 판단에서 제외했다.
- **F5 half-open (측정):** TCP 프록시가 양방향 전달을 멈춘 뒤 0·10·30·60초에 서버 세션 1개가 계속 남았다. 코드 리뷰에서 클라이언트 EOF가 서버에 전달될 수 있는 경주를 발견해 프록시를 고쳤고, 다시 60초간 같은 잔존을 확인했다. 이후 30건 push의 REST 응답은 모두 201이었다. 이 양에서는 버퍼 포화나 전송 중단이 나타나지 않았다.
- **F6 재연결 누락 (측정):** 서버 실험에서 끊긴 동안 저장한 ID 1은 재연결 후 push에 없고 REST 조회에 있었다. 재연결 후 저장한 ID 2만 push로 받았다. Playwright에서 소켓을 닫고 재연결을 막은 동안 REST 201로 저장한 메시지도 재연결 뒤 화면에는 없었으며 새로고침 뒤 보였다.
- **F49 최초 조회와 구독 사이 (측정):** B의 App 소켓을 유지한 채 방 화면만 내려 조회 응답을 고정했다. 응답을 화면에 전달하기 전에 A가 REST 201로 보낸 메시지의 WebSocket 프레임을 B 브라우저가 받은 것을 확인했다. 그럼에도 방 화면에는 없었고 새로고침 뒤 보였다. StrictMode가 시작한 두 조회에 같은 이전 스냅샷을 전달했다. 나가기 직후 재입장 경주는 미측정이다.
- **검증·기록:** `./gradlew test` 통과, 프론트 `npx tsc -b`·`npm run lint`·Playwright E2E 7건 통과. 반복 측정의 조건과 수치, 보완 후보·미측정 범위는 [계획 7 장애 보고서](../reports/2026-10-08-plan7-websocket-failures.md)에 기록했다. 장애 선행 규칙에 따라 서비스 보완 코드는 적용하지 않았다. 커밋하지 않았다.
