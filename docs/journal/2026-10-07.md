## 계획 2: 테스트용 SQL 측정과 확인

- seed의 자동·수동 검증은 [작업 2 결과 보고서](../reports/2026-10-07-plan2-task2-seed.md)에 기록했다. MySQL·PostgreSQL의 A/B 네 조합에서 정합성과 API 결과가 같았다.
- bulk SQL은 두 DB에서 사용자 10,000명, 방 10,000개, 멤버 68,000명과 메시지를 만들었다. 메시지의 인기/중간/나머지 방 분포는 모든 조합에서 정확히 50/30/20이었고, 정합성 위반 I1~I7은 모두 0건이었다.
- 아래 시간은 compose에서 각 조합을 빈 볼륨으로 시작한 뒤 한 번 실행한 **측정값**이다. `base`와 `messages`는 컨테이너 CLI 명령의 경과 시간이다. 메시지 크기는 `sizes.sql`의 대상 메시지 테이블 값이며, MySQL의 `table_rows`와 PostgreSQL의 `n_live_tup`은 추정치라 건수 검증에는 사용하지 않았다.

|---|---:|---:|---:|---:|---:|---:|---|---|
| MySQL-A | 500,000 | 0.646 | 4.650 | 83.6 | 18.5 | 102.2 | 안 | 예 |
| MySQL-B | 500,000 | 0.606 | 6.383 | 122.7 | 10.5 | 133.3 | 안 | 예 |

| MySQL-A | 5,000,000 | 0.595 | 60.848 | 837.0 | 154.9 | 991.9 | 밖 | 예 |
| MySQL-B | 5,000,000 | 0.707 | 79.592 | 1,216.0 | 103.7 | 1,319.7 | 밖 | 예 |
| PostgreSQL-A | 5,000,000 | 0.687 | 33.305 | 845.0 | 300.1 | 1,145.3 | 밖 | 예 |

작은 크기 500,000건과 큰 크기 5,000,000건은 모든 비교 조합에서 버퍼 안/밖으로 나뉘었다. 버퍼 밖이라는 판단은 메시지 테이블+인덱스의 **저장 크기**가 256MB를 넘는다는 뜻이다. 실제 캐시 적중률이나 OS 파일 캐시의 효과를 측정한 결과는 아니다.

### 500만 건에서 실행 계획

| 구성 | W2 최근 조회 | W3 과거 조회 | W4 폴링 | 방 목록 |
|---|---|---|---|---|
| MySQL-A | `idx_messages_room_id_id` | `idx_messages_room_id_id` | `PRIMARY` 범위 스캔 | 방 10,000행 테이블 스캔 후 정렬 |
| MySQL-B | `(room_id, id)` 기본키 | `(room_id, id)` 기본키 | `(room_id, id)` 기본키 | 방 10,000행 테이블 스캔 후 정렬 |
| PostgreSQL-A | `idx_messages_room_id_id` | `idx_messages_room_id_id` | `idx_messages_room_id_id` | 방 10,000행 순차 스캔 후 정렬 |

MySQL-A의 W4는 `(room_id, id)` 보조 인덱스 대신 `id` 기본키에서 `after` 이후 10행을 읽고 방 조건을 적용했다. 이번 입력에서는 1행만 반환했고, 전체 테이블 스캔은 아니었다. 방 목록은 세 조합 모두 인덱스 없는 정렬이었다. 이는 계획된 인덱스 부재 실험(F16)과 방 목록 정렬·갱신 경합 실험(F20)에 필요한 관찰이며, 이번 작업에서 인덱스나 설정을 바꾸지 않았다.

### DB 선택에 관한 현재 판단

이번 한 차례의 SQL 대량 적재에서는 PostgreSQL-A가 가장 짧았다. 이는 요청 W1~W5의 TPS·p95·p99·오류율과 동시 접속 10/50/200, cold cache, 락 대기를 측정한 결과가 아니다. DB를 고르는 정량 판정 규칙도 아직 확정되지 않았다. 따라서 이 숫자만으로 최종 DB를 선택할 수 없다. 다음 비교에서는 MySQL-A 대 PostgreSQL-A와 MySQL-B 대 PostgreSQL-A를 각각 재고, 워밍업 후 3회 중앙값을 사용해야 한다 (실험 설계, ADR-014).

남은 결정은 `room_members.user_id` 인덱스 차이를 비교 조건으로 기록할지 맞출지, 그리고 DB 선택의 정량 판정 규칙이다.

현재 DB 후보와 최종 선택에 필요한 근거는 [DB 비교 보고서](../reports/2026-10-07-plan2-db-comparison.md)에 따로 정리했다.

- 작업 4: 성공 감사 이벤트는 커밋 후, 실패는 트랜잭션 종료 뒤 또는 트랜잭션 없이 기록한다. 방 생성·비멤버 접근·인증 실패와 롤백 시 동작을 테스트했고, `audit.json` 파일에서 요청 ID·IP·사용자 ID를 확인했다. `audit` 패키지 의존 방향도 ArchUnit으로 검사한다.
- 작업 5: Prometheus v3.14.0과 Grafana 13.2.3을 `metrics` 프로필로 띄웠다. target UP, `chat Step 1` 7개 패널 자동 등록, 14개 PromQL 실행을 API로 확인했다. MySQL과 PostgreSQL의 `db` 태그가 분리되는 것도 확인했다.
- 작업 6: Elastic 세 이미지를 9.5.4로 고정하고 `logs` 프로필과 Filebeat를 추가했다. `app-*`·`audit-*`에 로그가 수집되고 JSON 파싱 오류가 0건임을 확인했다. 새 방 생성의 `requestId`로 감사 로그 `ROOM_CREATED` 1건과 일반 로그 20건을 연결했다. Kibana 데이터 뷰 두 개도 API로 등록·조회했다.

### 예상과 달랐던 점

- Boot 4의 Actuator 테스트 모듈과 일부 메트릭 이름은 이전 버전 예시를 그대로 쓰지 않고 실제 의존성·Prometheus 출력으로 확인했다. HikariCP 획득 최대 시간은 `hikaricp_connections_acquire_seconds_max`로 조회했다.
- ECS JSON 직렬화에서 `userId`를 MDC와 SLF4J key-value 양쪽에 넣으면 같은 키가 중복돼 감사 행이 기록되지 않았다. MDC 한 곳에서만 공급하도록 고쳐 실제 파일을 확인했다.
- 전체 테스트의 여러 Spring 컨텍스트가 MySQL 기본 접속 수를 채워 `Too many connections`가 났다. 테스트 전용 Hikari `minimum-idle=0`으로 유휴 연결 수를 줄인 뒤 전체 테스트를 통과했다. 운영 풀 설정은 바꾸지 않았다.
- Elasticsearch는 Docker 볼륨 여유 공간 2.3GB에서 기본 디스크 기준에 걸려 처음에는 기본 샤드가 배치되지 않았다. 로컬 Compose에 여유 공간 기준 1GB/750MB/500MB를 명시한 뒤 기본 샤드가 배치돼 문서가 수집됐다. 단일 노드의 복제 샤드는 배치되지 않아 yellow다.
- Grafana와 Kibana UI 자동화가 응답하지 않아 화면 캡처를 얻지 못했다. 대시보드·데이터 뷰 등록과 쿼리 결과는 각 API와 Elasticsearch 조회로 확인했다.
