## 계획 2: 테스트용 SQL 측정과 확인

- seed의 자동·수동 검증은 [작업 2 결과 보고서](../reports/2026-10-07-plan2-task2-seed.md)에 기록했다. MySQL·PostgreSQL의 A/B 네 조합에서 정합성과 API 결과가 같았다.
- bulk SQL은 두 DB에서 사용자 10,000명, 방 10,000개, 멤버 68,000명과 메시지를 만들었다. 메시지의 인기/중간/나머지 방 분포는 모든 조합에서 정확히 50/30/20이었고, 정합성 위반 I1~I7은 모두 0건이었다.
- 아래 시간은 compose에서 각 조합을 빈 볼륨으로 시작한 뒤 한 번 실행한 **측정값**이다. `base`와 `messages`는 컨테이너 CLI 명령의 경과 시간이다. 메시지 크기는 `sizes.sql`의 대상 메시지 테이블 값이며, MySQL의 `table_rows`와 PostgreSQL의 `n_live_tup`은 추정치라 건수 검증에는 사용하지 않았다.

| MySQL-A | 5,000,000 | 0.595 | 60.848 | 837.0 | 154.9 | 991.9 | 밖 | 예 |

작은 크기 500,000건과 큰 크기 5,000,000건은 모든 비교 조합에서 버퍼 안/밖으로 나뉘었다. 버퍼 밖이라는 판단은 메시지 테이블+인덱스의 **저장 크기**가 256MB를 넘는다는 뜻이다. 실제 캐시 적중률이나 OS 파일 캐시의 효과를 측정한 결과는 아니다.

### 500만 건에서 실행 계획

| 구성 | W2 최근 조회 | W3 과거 조회 | W4 폴링 | 방 목록 |
|---|---|---|---|---|
| MySQL-A | `idx_messages_room_id_id` | `idx_messages_room_id_id` | `PRIMARY` 범위 스캔 | 방 10,000행 테이블 스캔 후 정렬 |
| MySQL-B | `(room_id, id)` 기본키 | `(room_id, id)` 기본키 | `(room_id, id)` 기본키 | 방 10,000행 테이블 스캔 후 정렬 |
| PostgreSQL-A | `idx_messages_room_id_id` | `idx_messages_room_id_id` | `idx_messages_room_id_id` | 방 10,000행 순차 스캔 후 정렬 |

MySQL-A의 W4는 `(room_id, id)` 보조 인덱스 대신 `id` 기본키에서 `after` 이후 10행을 읽고 방 조건을 적용했다. 이번 입력에서는 1행만 반환했고, 전체 테이블 스캔은 아니었다. 방 목록은 세 조합 모두 인덱스 없는 정렬이었다. 이는 계획된 인덱스 부재 실험(F16)과 방 목록 정렬·갱신 경합 실험(F20)에 필요한 관찰이며, 이번 작업에서 인덱스나 설정을 바꾸지 않았다.

### DB 선택에 관한 현재 판단

이번 한 차례의 SQL 대량 적재에서는 PostgreSQL-A가 가장 짧았다. 이는 요청 W1~W5의 TPS·p95·p99·오류율과 동시 접속 10/50/200, cold cache, 락 대기를 측정한 결과가 아니다. DB를 고르는 정량 판정 규칙도 아직 확정되지 않았다. 따라서 이 숫자만으로 최종 DB를 선택할 수 없다. 다음 비교에서는 MySQL-A 대 PostgreSQL-A와 MySQL-B 대 PostgreSQL-A를 각각 재고, 워밍업 후 3회 중앙값을 사용해야 한다 (실험 설계, ADR-014).

남은 결정은 `room_members.user_id` 인덱스 차이를 비교 조건으로 기록할지 맞출지, 그리고 DB 선택의 정량 판정 규칙이다.

현재 DB 후보와 최종 선택에 필요한 근거는 [DB 비교 보고서](../reports/2026-10-07-plan2-db-comparison.md)에 따로 정리했다.

### 예상과 달랐던 점

- Boot 4의 Actuator 테스트 모듈과 일부 메트릭 이름은 이전 버전 예시를 그대로 쓰지 않고 실제 의존성·Prometheus 출력으로 확인했다. HikariCP 획득 최대 시간은 `hikaricp_connections_acquire_seconds_max`로 조회했다.
- ECS JSON 직렬화에서 `userId`를 MDC와 SLF4J key-value 양쪽에 넣으면 같은 키가 중복돼 감사 행이 기록되지 않았다. MDC 한 곳에서만 공급하도록 고쳐 실제 파일을 확인했다.
- 전체 테스트의 여러 Spring 컨텍스트가 MySQL 기본 접속 수를 채워 `Too many connections`가 났다. 테스트 전용 Hikari `minimum-idle=0`으로 유휴 연결 수를 줄인 뒤 전체 테스트를 통과했다. 운영 풀 설정은 바꾸지 않았다.
- Elasticsearch는 Docker 볼륨 여유 공간 2.3GB에서 기본 디스크 기준에 걸려 처음에는 기본 샤드가 배치되지 않았다. 로컬 Compose에 여유 공간 기준 1GB/750MB/500MB를 명시한 뒤 기본 샤드가 배치돼 문서가 수집됐다. 단일 노드의 복제 샤드는 배치되지 않아 yellow다.
- Grafana와 Kibana UI 자동화가 응답하지 않아 화면 캡처를 얻지 못했다. 대시보드·데이터 뷰 등록과 쿼리 결과는 각 API와 Elasticsearch 조회로 확인했다.

다음은 계획 4다. 관측으로 찾을 수 있는 부하·비동기 로그 위험은 F28~F31에 가설로 남겼다. 최종 결과와 확인 범위는 [계획 3 보고서](../reports/2026-10-07-plan3-observability.md)에 기록했다.

## 계획 4: 프론트엔드 직접 확인과 마무리

- **한 일:** 사용자 선택·방 목록·채팅방·폴링 상태 패널을 구현했다. React 단위 테스트 59건과 Playwright E2E 2건을 추가했다. 계획 4 세부 결정은 ADR-081 ~ ADR-087에 기록했다. 설치 버전은 Node 22.22.2, Vite 8.3.3, React 19.3.0, TypeScript 6.0.3, Vitest 5.0.3, Playwright 1.63.0이다.
- **브라우저 관찰 (Chrome, local,mysql, 2026-10-07):** 사용자 #14와 #15를 별도 탭에서 만들고 방 #10에서 서로 메시지를 전송·폴링 수신했다. #15가 나간 동안 보낸 메시지와 나가기 전 메시지는 #15의 재입장 화면에 보이지 않았다. 재입장 뒤 보낸 메시지는 #14에게 도착했다.
- **요청·로그 관찰:** Chrome Network에서 `/api/rooms/10/messages?after=55` fetch 요청들이 보였고 관찰한 목록에는 `OPTIONS`가 없었다. 폴링 패널의 `X-Request-Id=1742de53-cad2-4d09-8b37-05abae006c67`로 `backend/logs/app.json`의 `ACCESS` 행을 찾았다. 그 행은 사용자 #14, GET, HTTP 200, `clientIp=127.0.0.1`이었다. 로컬 접속 결과이므로 외부 proxy 경로의 IP는 확인하지 않았다.
- **폴링 주기 관찰:** 화면에서 2초를 0.5초로 바꾸자 Grafana `chat Step 1`의 메시지 조회 요청 곡선이 상승했다. Prometheus의 전체 메시지 조회 1분 rate는 약 4.20→5.62 req/s였다. 이 값에는 다른 열린 탭들의 요청도 포함돼 있으므로 차이 전체를 주기 변경만의 효과로 해석하지 않는다.
- **예상과 달랐던 화면:** 새로 만든 메시지 없는 방 #11은 목록 맨 아래가 아니라, 메시지가 있는 방들 아래이면서 메시지가 없는 방 중 ID 역순 맨 앞에 보였다. 실제 정렬은 `last_message_id`를 먼저 본다. 보완 여부는 여전히 미결정이다.
- **장애 재현 (F28):** 사용자 #15의 탭 두 개 중 하나에서 방 #10을 나갔다. 열린 다른 탭은 0.5초마다 403을 받으며 폴링을 계속했고, 패널 오류 수는 0→22, 같은 사용자·방의 `ACCESS_DENIED` 감사 로그 누계는 4→26건이 됐다. 확인 뒤 폴링을 일시정지했다. 여러 비멤버의 파일·색인 규모 영향은 측정하지 않았다.
- **최종 자동 검사:** `npm test` 11개 파일·59개 테스트 통과, `npm run lint` 통과, `npm run build` 통과, `npm run e2e` Chromium 2건 통과. 백엔드 `./gradlew test`도 성공했으며 Gradle은 기존 테스트 작업을 `UP-TO-DATE`로 판정했다.
- **남은 일:** 계획 5의 부하·장애 실험. 닉네임 서식 문자(F26)는 작성자를 ID로 표시해 아직 검증하지 않았다. 목록 정렬 개선 여부와 폴링 주기의 최종값은 별도로 결정한다.

## 계획 5a: 정합성·경쟁 실험

- **한 일:** `@Tag("experiment")` 서비스 계층 실험을 만들고 MySQL 기본/READ COMMITTED, PostgreSQL 기본 조건에서 커밋 순서 역전(F22), 시각 커서(F2), 입장 경계(F18), 퇴장과 전송(F23), 실험용 방 삭제(F19)를 결정적으로 재현했다. 자연 동시 실행 건수는 [계획 5a 보고서](../reports/2026-10-07-plan5a-consistency.md)에 둔다.
- **결정:** ADR-088 ~ ADR-099로 실험 범위·측정 방법을 기록했다. 입장 경계는 시각의 유출·유실을 확인해 `joined_message_id`를 유지하고 `joined_at` 제거는 5b 이후 별도 마이그레이션에서 다루기로 했다(ADR-100).
- **예상과 달랐던 점:** MySQL의 5초 자연 실행에서는 작성자 50명이 10명보다 번호 커서의 누락이 적을 때도 있었다. PostgreSQL 기본 조건에서는 누락이 수천 건으로 컸다. 짧은 자연 실행의 빈도는 일정한 발생률로 해석하지 않는다. 실험용 방 삭제와 입장의 FK 위반은 현재 저장소에서 401로 변환돼 ADR-019의 설명과 달랐다.
- **다음:** 계획 5b에서 k6 HTTP 부하와 DB 선택 규칙, 스키마 A/B, 풀 고갈, 방 삭제 부하를 측정한다. F22·F23 해결책은 후속 정합성 강화에서 비교한다. 운영 코드의 장애는 이번 단계에서 고치지 않았다(ADR-034).

## 계획 5b: 부하·DB 비교

- **한 일:** 기존 `chat-db` 볼륨을 보존하고 별도 `chat-bench` Compose에서 MySQL-A/B와 PostgreSQL-A의 50만·500만 건 W1~W5 기준선을 실행했다. 15초 워밍업, 30초 3회 반복의 원시 k6 JSON·CSV와 DB·Hikari 카운터를 보관했다. 추가로 VU 10/50/200, 인기 방 쓰기, DB 재시작, 폴링 주기, 깊은 offset, 인덱스 제거·복원, 2만 5천 건 방 삭제를 측정했다. 세부 조건·수치·원자료는 [계획 5b 보고서](../reports/2026-10-07-plan5b-load-db-comparison.md)에 있다.
- **판정:** MySQL B는 500만 건 W2·W3·W4 각각의 p99 30% 개선 조건을 충족하지 못해 A를 유지한다(ADR-105). PostgreSQL-A의 혼합 W5 p99는 MySQL-A보다 15.4% 낮고 RPS는 높았지만, 사전 등록한 20% 문턱에 못 미쳐 DB 선택을 보류한다(ADR-106). 양쪽 200 VU 오류율은 0%였다.
- **장애 관찰:** 200 VU 무대기 폴링은 Hikari 풀 10개를 채우고 대기를 만들었지만 타임아웃은 없었다(F1). 깊은 offset은 같은 페이지의 ID 커서보다 느렸고(F15), 인덱스 제거는 W2 p99를 두 DB 모두 약 12초로 늘렸으나 실제 계획은 기본키 스캔이었다(F16). 인기 방 쓰기는 MySQL-A 처리량을 약 51% 낮췄고, PostgreSQL 방 정렬값 인덱스는 HOT 갱신 비율을 크게 낮췄다(F20). 방 1 메시지 25,000건 삭제는 세 구성 모두 잔여 행 0을 확인했고 PostgreSQL은 직후 dead tuple 25,000개였다(F19).
- **측정 한계:** Docker VM 공간 부족으로 실패한 적재는 격리 볼륨을 버리고 미사용 빌드 캐시를 정리한 뒤 재실행했다. 최초 탐색 W5의 방 선택 오류도 공식 결과에서 제외했다. 구성별 반복은 동일 스냅샷 복원이 아니라 쓰기를 누적했고, 호스트 파일 캐시는 DB 재시작으로 비워지지 않았다. CPU·메모리·디스크 I/O의 반복별 연속 기록은 없다. 이 한계를 DB 선택의 사전 문턱과 별도로 보고한다.
