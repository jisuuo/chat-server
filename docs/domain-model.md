# 도메인 · 데이터 모델 (V1)

> 출처: Notion `03. 도메인 · 상태 · 데이터`, `09. API · DB 상세 설계` (설계 확정)
> 정책(`docs/policy.md`)을 보존하기 위해 필요한 상태/데이터만 정의한다. 데이터 모델 판단 순서: **도메인 의미 → 정확성/불변식 → 상태의 명확성 → 이력 보존 → 조회/변경 비용 → 복잡도**. 성능은 보통 첫 번째 판단 근거가 아니다.

## 엔티티

```
ChatRoom
- id              BIGINT PK
- name            VARCHAR(100) NOT NULL
- createdBy       VARCHAR(255) NOT NULL   -- 외부 회원 시스템 userId, FK 없음
- createdAt       TIMESTAMPTZ NOT NULL
- closedAt        TIMESTAMPTZ NULL        -- NULL=활성, NOT NULL=마지막 멤버 퇴장 후 영구 닫힘
- lastMessageAt   TIMESTAMPTZ NULL        -- Message.createdAt에서 비정규화

ChatRoomMember
- id              BIGINT PK
- chatRoomId      BIGINT FK -> chat_room.id
- userId          VARCHAR(255) NOT NULL   -- 외부 회원 시스템 userId
- joinedAt        TIMESTAMPTZ NOT NULL
- leftAt          TIMESTAMPTZ NULL        -- NULL=활성 멤버, NOT NULL=퇴장 이력 보존

Message
- id              BIGINT PK (Identity/Sequence)
- chatRoomId      BIGINT FK -> chat_room.id
- senderId        VARCHAR(255) NOT NULL
- content         VARCHAR(2000) NOT NULL
- createdAt       TIMESTAMPTZ NOT NULL
```

관계: `ChatRoom 1 — N ChatRoomMember`, `ChatRoom 1 — N Message`. `User`는 Chat Server가 소유하지 않는다 (아래 "외부 사용자 경계" 참고).

## 핵심 불변식

- 활성 membership은 `(chatRoomId, userId)` 기준 **최대 1개**다. DB partial unique index로 최종 강제한다.
- 재입장 시 과거 membership row를 덮어쓰지 않고 새 row를 만든다 (참여 이력 보존).
- `closedAt != NULL`인 방은 영구적으로 닫히며 재입장할 수 없다.
- `활성 Membership > 0 ⇔ ChatRoom.closedAt = NULL` (Join/Leave가 같은 `ChatRoom` row lock으로 직렬화되어 이 invariant를 보장).
- `lastMessageAt`은 한 번 증가한 뒤 더 과거 시각으로 감소하지 않는다 (단조 증가).
- Message/ChatRoomMember → ChatRoom 참조는 FK로 보호한다. ChatRoom은 물리 DELETE하지 않는다 (닫힘 상태로만 전환).
- Message의 식별/정렬/cursor/catch-up 기준은 항상 증가하는 `Message.id`다. `createdAt`은 표시용일 뿐 정렬/식별 기준이 아니다 (동시 처리 시 값이 같을 수 있음).
- `messageId`는 gapless sequence가 아니다. `101 → 103`처럼 값이 비어 있어도 유실로 판단하지 않는다.

## `ChatRoom.lastMessageAt` 비정규화

- `lastMessageAt`은 `Message.createdAt`에서 계산 가능한 값을 채팅방 목록 정렬을 위해 한 번 더 저장한 비정규화 데이터다.
- Message INSERT와 `lastMessageAt` 갱신은 **같은 DB 트랜잭션**으로 처리한다 (판단 기준: "여러 작업 중 일부만 성공해도 비즈니스적으로 정상인가?" → NO면 같은 트랜잭션).
- 갱신 SQL은 단조 증가를 위해 `GREATEST`를 사용한다:
  ```sql
  UPDATE chat_room
     SET last_message_at = GREATEST(COALESCE(last_message_at, :messageCreatedAt), :messageCreatedAt)
   WHERE id = :roomId
  ```
- Redis Publish / WebSocket 전달은 이 트랜잭션의 성공 조건에 포함하지 않는다 (DB 저장 성공 = 메시지 전송 성공 정책과 일치).

## PostgreSQL DDL

```sql
CREATE TABLE chat_room (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name            VARCHAR(100) NOT NULL,
    created_by      VARCHAR(255) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL,
    closed_at       TIMESTAMPTZ NULL,
    last_message_at TIMESTAMPTZ NULL
);

CREATE TABLE chat_room_member (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    chat_room_id BIGINT NOT NULL,
    user_id      VARCHAR(255) NOT NULL,
    joined_at    TIMESTAMPTZ NOT NULL,
    left_at      TIMESTAMPTZ NULL,
    CONSTRAINT fk_chat_room_member_room
        FOREIGN KEY (chat_room_id) REFERENCES chat_room(id)
);

CREATE TABLE message (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    chat_room_id BIGINT NOT NULL,
    sender_id    VARCHAR(255) NOT NULL,
    content      VARCHAR(2000) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL,
    CONSTRAINT fk_message_room
        FOREIGN KEY (chat_room_id) REFERENCES chat_room(id)
);
```

- 외부 회원 시스템의 실제 `userId` 타입이 확정되면 `VARCHAR(255)` 부분만 그 타입에 맞춘다. Chat Server 내부에 User FK는 두지 않는다.
- ChatRoom을 물리 삭제하지 않으므로 FK 삭제 동작은 기본 `NO ACTION/RESTRICT`를 유지한다.
- 시간 컬럼은 전부 `TIMESTAMPTZ`로 통일한다 (지역 벽시계 시간이 아니라 절대 시점 저장, 지역 시간 변환은 표현 계층 책임).
- Chat Server 내부 소유 엔티티의 PK/FK는 전부 `BIGINT`로 통일한다. 외부 `userId`는 이 규칙 대상이 아니다.

## 인덱스

```sql
-- 활성 membership 최대 1개 invariant + roomId+userId 활성 조회
CREATE UNIQUE INDEX uq_chat_room_member_active
ON chat_room_member (chat_room_id, user_id)
WHERE left_at IS NULL;

-- "내가 현재 참여 중인 방 목록" 조회 시작점 (선두 컬럼이 user_id라 위 인덱스로는 못 탐)
CREATE INDEX ix_chat_room_member_active_by_user
ON chat_room_member (user_id)
WHERE left_at IS NULL;

-- 방별 messageId cursor pagination / catch-up 조회
CREATE INDEX ix_message_room_id
ON message (chat_room_id, id);
```

학습 포인트: 복합 인덱스는 포함 컬럼뿐 아니라 **선두 컬럼과 실제 조회 시작 조건**이 중요하다. 같은 테이블도 조회 방향이 다르면 별도 인덱스가 필요할 수 있다. 필요 이상의 인덱스는 만들지 않는다 (INSERT/UPDATE 비용 + 저장 공간 트레이드오프).

## 동시성 처리 (구현 시 이렇게 짠다)

**Join / Leave 트랜잭션** — 같은 `ChatRoom` row를 잠가 방 lifecycle을 직렬화:

```
BEGIN
  SELECT ChatRoom FOR UPDATE            -- JPA: PESSIMISTIC_WRITE
  → room 존재 / closed 여부 확인
  → Join: active membership 있으면 성공 수렴, 없으면 새 Membership INSERT
  → Leave: active membership 없으면 성공 수렴, 있으면 leftAt 기록
  → Leave 후 active member 0명이면 같은 lock 안에서 closedAt 기록
COMMIT
```

**메시지 저장 트랜잭션**:

```
BEGIN
  active Membership 확인
  Message INSERT
  UPDATE chat_room SET last_message_at = GREATEST(...) WHERE id = :roomId
COMMIT
-- Redis publish / WebSocket 전달은 COMMIT 이후, 실패해도 롤백하지 않음
```

## 외부 사용자 경계

- Chat Server는 `User` 테이블을 직접 소유하지 않는다. 인증/회원 시스템이 사용자를 관리하고, Chat Server는 인증 경계에서 전달된 `userId`를 신뢰해 사용한다.
- `senderName`처럼 표시용 사용자 정보가 필요하면 `MemberDisplayNamePort` 같은 읽기 포트로 외부 회원 시스템 adapter를 통해 얻는다. 메시지 목록처럼 여러 sender가 필요하면 per-message 원격 호출을 금지하고 senderId를 모아 batch resolve한다.
- 실제 회원 API 규격(transport, timeout, cache TTL)은 아직 미확정이므로 이 문서에서 임의로 고정하지 않는다.
