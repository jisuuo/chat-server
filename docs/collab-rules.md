# 협업 규칙

> 이 프로젝트를 함께 진행하는 방식. 누적 문서이며 규칙이 바뀌면 갱신한다.

## 진행 방식

**결정 → 구현 → 장애 재현 → 원인 분석 → 해결 → 기록**을 반복한다.

1. 단계마다 결정 하나만 의논한다. 선택지 2~3개와 트레이드오프를 보고 직접 결정한다.
2. 결정은 "결정 기록(ADR)"에 남긴다. 무엇을 골랐고 무엇을 포기했는지 적는다.
3. 점진적으로 진화시킨다. 각 단계마다 **일부러 장애를 낸다.**

## 기술 제안 형식과 장애 대응 규칙

**앞으로의 기술 제안 형식** (사용자가 확정)
1. 한 줄 요약: 무엇을 바꾸자는 제안인지
2. 해결하려는 문제: 현재 사용자가 겪는 문제를 구체적인 예로
3. 사용 화면의 변화: 적용 후 달라지는 것, 기대와 다르게 보일 수 있는 경우
4. 추천안과 이유: 다른 방법과 비교할 때 중요한 차이만
5. 비용과 위험: 성능, 정합성, 동시성을 쉬운 말로
6. 기술적 근거: 용어, SQL, DB별 동작, 실험 항목. 용어는 처음 나올 때 짧게 설명
7. 지금 결정할 사항: 이미 결정된 것과 새로 결정할 것을 구분. 추천안의 한계와 확인 필요 사항 포함

- 중요한 조건을 생략하거나 결과를 단정하지 않는다. 비슷하지만 다른 경우를 구분한다 (예: "메시지가 없는 방"과 "현재 멤버가 없는 방").
- DB 종류나 설정에 따라 달라지는 동작은 조건을 밝힌다.
- 예상되는 문제와 실제로 측정·검증한 결과를 구분한다.
- F번호, ADR번호, Step 번호는 맥락을 풀어쓴 뒤 괄호에 표시한다.
- 전체 흐름을 먼저, 깊은 구현 설명은 뒤에.

**장애 대응 규칙** (사용자가 확정, ADR-034 보완)
- 예상되는 문제는 장애 실험 목록에 가설로 **기록만** 한다.
- 문제가 터지기 전에 코드나 설계로 **미리 고치지 않는다.**
- 문제가 실제로 재현되면 함께 들여다보고 분석하며 고친다. 이때 기록을 참고한다.
- 이미 ADR로 결정된 사항은 그대로 구현한다. 구현 중 새 위험을 발견하면 가설로 기록하고 알리기만 한다.

## 기록 방식 (ADR-035)

- 원본은 로컬 `docs/`이고, 노션은 사용자가 요청할 때 한 번에 반영하는 사본이다.
- **누적 문서**(계속 갱신): `README.md`(프로젝트 소개, 현재 상태), `failure-lab.md`(장애 실험), `collab-rules.md`(협업 규칙), `design/`(설계)
- **결정 기록**(날짜별, ADR-043): `adr/YYYY-MM-DD.md`. 그날 내린 결정만 담고, 번호는 날짜와 상관없이 이어서 매긴다.
- **일지**(날짜별, 그날 기록하고 거의 바꾸지 않음): `journal/YYYY-MM-DD.md`. 한 일, 내린 결정(ADR 번호 + 한 줄), 막힌 점, 배운 점, 다음 할 일을 짧게 쓰고 자세한 내용은 누적 문서로 링크한다.
- **결과 보고서**(요청 시): `reports/`. 자동 테스트와 수동 확인의 실제 결과를 남긴다.
- **CS 지식 목록**(날짜별, 요청 시): `cs/YYYY-MM-DD.md`. 그날 작업에 나온 꼭 알아야 할 개념과 이 프로젝트에서 필요한 이유를 적는다.

## 커밋

- **자동 커밋 금지.** 작업이 끝나도 커밋하지 않고, 사용자가 요청할 때만 커밋한다 (2026-10-07 사용자 결정).

## 코드 주석

- **주석은 "왜 이렇게 했는지"를 남긴다.** 코드만 봐도 알 수 있는 "무엇을 하는지"는 쓰지 않는다. 결정이나 실험과 관련된 이유면 ADR·F 번호를 함께 적는다 (2026-10-07 사용자 결정).
