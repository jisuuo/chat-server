# 계획 5b: 부하·DB 비교

> 2026-10-07 시작. 계획 5a의 F22·F23 결과를 이어받는다. 기존 `chat-db` 볼륨은 보존하고 `chat-bench` 프로젝트에서만 초기화한다. 운영 코드는 장애 선행(ADR-034)에 따라 고치지 않는다. 커밋하지 않는다.

## 목표

HTTP 요청 W1~W5를 MySQL-A, MySQL-B, PostgreSQL-A에 같은 데이터와 자원으로 실행한다. F1(폴링과 풀), F15(깊은 offset), F16(인덱스), F20(방 정렬 갱신), F19(대량 삭제)를 측정한다. A/B 스키마는 ADR-014의 사전 기준으로 판정하고, DB 선택은 측정 전 확정한 별도 정량 규칙으로 판정한다. 예상과 측정을 구분해 보고한다.

## 확정된 조건

- DB: MySQL 8.4.11, PostgreSQL 18.6. 각각 CPU 2개·메모리 1GB, 캐시 설정 256MB, 내구성 설정 일치(ADR-040).
- 데이터: 방·사용자 각 10,000, 멤버 68,000, 메시지 500,000 / 5,000,000건. 분포 50/30/20(ADR-059·060).
- 스키마: MySQL A/B와 PostgreSQL A. 스키마나 데이터 크기를 바꿀 때 별도 벤치 볼륨만 초기화(ADR-041).
- 부하: 로컬 설치 k6 2.1.0, API 직접 호출. `backend` 앱은 `bench` 프로필이다.
- 판정: 각 조건을 워밍업한 뒤 3회 실행, p99·TPS·오류율의 중앙값을 사용한다. A→B는 큰 데이터에서 읽기 p99 30% 이상 개선과 쓰기 p99 악화 10% 이내를 동시에 충족해야 한다(ADR-014).
- 각 조건의 `run-id`, 입력, 실행 순서, 원시 k6 JSON, 요약 CSV, DB 자원과 잠금·캐시 카운터를 함께 남긴다.

## 측정 전 판정 규칙 (ADR-101~103)

1. DB 선택의 주 지표는 큰 데이터·VU 50의 W5 p99이며 20% 이상 차이, TPS 10% 이내 열세, 오류율 0.1% 이하를 동시에 요구한다. VU 200 오류율은 1% 이하로 제한한다. 조건에 못 미치면 선택을 보류한다. F22·F23은 별도의 정합성 위험으로 기록한다(ADR-101).
2. PostgreSQL 격리 DB에 비교용 `room_members(user_id)` 인덱스를 더하고 앱 CPU도 2개로 제한한다(ADR-102).
3. 전체 곱집합 대신 기준선과 한 축씩 바꾸는 매트릭스를 쓴다. 15초 워밍업, 30초 × 3회로 측정한다(ADR-103). 사용자 선호가 도착하면 공식 측정 전에 이 규칙을 갱신한다.
4. 500만 건에서 MySQL B의 읽기 p99 개선은 W2·W3·W4 모두 30% 이상이어야 하고 W1 p99 악화는 10% 이내여야 한다(ADR-104). 이 해석은 50만 건 예비 기준선 뒤, 500만 건 측정 전에 고정했다.

## 측정 매트릭스

전체 곱집합은 중복이 많아 아래처럼 한 번에 한 축을 바꾼다. 각 행은 세 구성과 해당 데이터 크기에서 워밍업 후 3회 측정한다.

| 묶음 | 데이터 | 부하 | 비교 |
|---|---|---|---|
| 기준선 | 50만·500만 | W1~W5, VU 50 | C1, DB/스키마 차이 |
| 동시성 | 500만 | W5, VU 10/50/200 | C2, p99·오류·TPS·Hikari 대기 |
| 인기 방 | 500만 | W1, VU 50, 분산/방 1개 | C3, `last_message_id` 행 갱신 경합 |
| 재시작 | 500만 | W2·W4, DB 재시작 직후/안정 후 | C4, 캐시·회복 시간. 호스트 OS 캐시는 제거하지 못함 |
| 폴링 | 500만 | W4, VU 10/50/200, 주기 0.5/1/2/5초와 대기 없는 최대 부하 | F1, 풀 10 연결 기준 |
| 페이지 | 50만·500만 | W3 API 커서와 DB 직접 offset | F15, 깊은 offset 비용 및 실행 계획 |
| 인덱스 | 500만 | W2~W4 인덱스 전후 | F16, 격리 DB에서만 인덱스를 제거·복원 |
| 갱신 인덱스 | 500만 | PostgreSQL W1 인기 방, `rooms.last_message_id` 인덱스 전후 | F20, HOT 갱신·p99·크기 |
| 대량 삭제 | 500만 | 마지막 멤버의 방과 메시지 삭제 SQL | F19, 트랜잭션 시간·MySQL undo·PostgreSQL dead tuple |

## 실행 순서

1. `infra/compose.bench.yml`로 격리 DB와 앱을 띄운다. 기존 `infra/compose.db.yml`의 볼륨을 지우지 않는다. `backend/`의 bootJar를 한 번 만든 뒤 동일 SHA-256의 `load/artifacts/chat-bench.jar` 복사본을 컨테이너에 읽기 전용으로 연결한다. 다른 세션의 계획 6 소스 편집이 후속 조합의 앱 바이트를 바꾸지 않게 한다.
2. 앱 Flyway가 빈 스키마를 만든 뒤 앱을 잠시 멈추고 `db/bulk/`의 base와 해당 메시지 SQL을 적재한다. 불변식 I1~I7과 분포를 확인한 뒤 앱을 다시 시작한다.
3. k6 스크립트의 HTTP 상태·본문 파싱을 작은 시범 실행으로 확인한다. 실패율·트랜잭션 상태가 맞지 않으면 측정을 중단하고 원인을 기록한다.
4. 측정 전 DB 선택 규칙을 ADR에 확정한다. 기준선과 조건 실험을 실행한다. 각 run은 워밍업과 측정 결과를 분리한다.
5. 실험마다 원시 JSON과 요약 CSV를 보관하고 3회 중앙값을 계산한다. DB 카운터는 측정 전후 차이를 기록한다. 데이터 크기/스키마를 바꿀 때만 격리 프로젝트 볼륨을 초기화한다.
6. F1·F15·F16·F19·F20의 장애 상태와 한계를 failure-lab에 기록한다. DB와 PK 선택 ADR, 결과 보고서, 설계·일지·README를 갱신한다. `./gradlew test`와 스크립트 구문 검사를 실행한다.

## 공정성과 한계

- `local` 프로필의 TRACE 로그는 쓰지 않고 `bench` 프로필로 실행한다. k6 클라이언트와 앱·DB는 같은 머신의 Docker VM 자원을 공유한다. 반복 순서는 DB별로 번갈아 배치하고 실행 순서 자체를 기록한다.
- W1·W5는 데이터를 바꾼다. 재실행 사이에 데이터 크기가 달라지므로, 비교 전용 방을 지정하거나 각 반복을 동일 스냅샷에서 시작한다. 별도 방의 쓰기 누적량도 기록한다.
- DB 재시작만으로 호스트 OS 파일 캐시가 비워지지 않으므로 C4는 엄밀한 cold cache가 아니라 재시작 회복 측정이다.
- 200 VU는 동시 클라이언트 수이지 DB 연결 200개가 아니다. Hikari 풀은 별도 지표로 관찰한다.
- 5a에서 PostgreSQL의 자연 폴링 누락이 크게 측정됐지만, 하드웨어 제한이 없는 Testcontainers의 짧은 실행이었다. 5b에서 correctness를 성능 점수와 혼동하지 않고 별도 위험으로 기록한다.
