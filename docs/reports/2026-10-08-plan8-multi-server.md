# 계획 8 결과: 서버 2대와 nginx

2026-10-08 · Step 3 · 계획 8 작업 0~8. 앱 2대는 같은 MySQL을 사용하고 nginx가 HTTP와 WebSocket을 라운드로빈으로 분배한다. 장애를 먼저 재현한 뒤 nginx 핸드셰이크 설정(F8)과 클라이언트 재연결 대기(F17)를 보완했다. 서버 간 실시간 전달 누락(F7)은 재현·분석까지만 했다. 결정은 [ADR-147~159](../adr/2026-10-08.md#계획-8-서버-2대와-nginx)에 있다.

## 구성과 판정 범위

`infra/compose.cluster.yml`의 nginx `:18090`, app1 `:18081`, app2 `:18082`, 별도 MySQL `:33306`을 사용했다. 기본 nginx 설정은 `chat`이고 앱 프로필은 `local,mysql`이다. 부하 실험은 `bench,mysql`로 실행했다. 클러스터 앱은 공용 DB를 보지만 WebSocket 세션과 push 큐는 각 JVM에만 있다. `@Tag("experiment")` 실험은 일반 `./gradlew test`에서 제외된다.

| 장애 | 재현 조건과 측정 | 보완·현재 상태 |
|---|---|---|
| F8, nginx 뒤 WebSocket 연결 | `naive`·`f8-upgrade`·`f8-host`에서 각 10회 모두 403. 원래 예상한 단순 400이나 기본 HTTP/1.0 문제와 달랐다. | `chat`에서 10/10회 101. `Upgrade`·`Connection`, 원래 `Host`, `X-Forwarded-Proto`·`Port`를 전달한다(ADR-158). 60·120·180초 유휴 연결 유지, 읽기 제한 5초 대조는 5.088초에 종료. |
| F7, 다른 앱의 수신자에게 push 누락 | 두 Spring 컨텍스트가 같은 DB에 각각 1건을 저장해도 각 수신자는 자기 앱의 메시지만 push로 받았다. nginx 경유 20건은 앱별 10건씩 저장됐고, 수신자 20명 모두 자기 연결 앱의 10건만 5초 안에 받았다(3회). | 미해결. 브라우저의 60초 주기 재조회가 지연 표시할 뿐 즉시 전달하지 못한다. Redis Pub/Sub은 계획 9에서 다룬다. |
| F17, 고정 1초 재연결 집중 | 앱 1의 약 500개 소켓을 끊자 재접속과 연결 직후 복구 조회가 몰렸다. 작업 6의 첫 통제 표본에서 정상 재시작 1초 시도 501건·조회 p99 1,061ms, 강제 종료 504건·1,114ms였다. | 전체 지터 `floor(random × min(30초, 1초 × 2^연속실패횟수))`를 브라우저에 적용했다(ADR-159). 아래 같은 조건 비교에서 100ms 구간 시도 정점이 줄었다. |

## F8: 핸드셰이크와 유휴 연결

nginx 1.30.5에서 프록시 HTTP/1.1은 이미 기본값이다. 단계별 헤더 대조 결과, 업그레이드 헤더만 추가하거나 포트 없는 `Host`를 주면 Spring의 같은 origin 검사에서 403이었다. 외부 포트 18090을 `X-Forwarded-Port`로 명시한 `chat` 설정에서 101이었다. 브라우저 두 탭이 같은 앱에 연결된 조건에서도 메시지 1건이 즉시 표시됐다. `X-Forwarded-For`는 nginx가 본 클라이언트 주소로 덮어써서 브라우저가 보낸 위조 값이 앱 접근 로그에 들어가지 않도록 했다. 로컬 Docker에서 기록된 `192.168.65.1`이 실제 원격 사용자의 IP까지 정확하다는 검증은 아니다. 직접 공개한 앱 포트는 nginx의 헤더 처리를 거치지 않는다. 공개 포트를 바꾸면 nginx의 `X-Forwarded-Port` 값도 바꿔야 한다.

## F7: 저장 성공과 실시간 수신의 차이

두 컨텍스트 실험에서 DB 조회에는 양쪽 메시지가 모두 있었고, 각 앱의 REST 전달 성공 지표는 1씩 늘었으며 실패 지표는 0이었다. 그러나 반대 앱의 소켓에는 push가 없었다(F53). 성공 지표는 해당 JVM의 전송 완료를 뜻하며 방 전체 멤버의 실시간 수신을 증명하지 않는다.

최종 Chrome 확인에서는 같은 앱에 붙은 A·B 사이의 메시지가 즉시 보였다. B를 다른 앱에 연결하자 A의 메시지는 B의 열린 소켓에 push되지 않았고 패널은 `연결됨`, 재연결 0, 받은 프레임 0이었다. 앱 전송 로그 `11:52:45.570 UTC`에서 B의 주기 조회 로그 `11:53:35.498 UTC`까지 약 49.93초 뒤 새로고침 없이 표시됐다. 이는 조회 요청 시각 간격이며 화면 그리기의 밀리초 시각은 측정하지 않았다. 작업 5의 독립 브라우저 표본에서도 약 43.5초 뒤 표시됐다. 조회 타이머 위상에 따라 지연 시간은 달라진다.

## F17: 재연결 정책 비교

Java 클라이언트 1,000개를 앱별 약 500개씩 연결하고, 각 조건 전에 nginx를 새로 띄워 초기 분배를 맞췄다. 정상 종료 재시작과 강제 종료 뒤 시작에서 고정 1초와 전체 지터를 한 번씩 비교했다. 각 클라이언트는 연결 뒤 최신 메시지 한 페이지를 조회했다.

| 조건 | 정책 | 처음 app1/app2 | 재접속 시도 최대/100ms | 최대/1초 | 복구 조회 p99 | 전원 연결까지 |
|---|---|---:|---:|---:|---:|---:|
| 정상 재시작 | 고정 1초 | 501/499 | 351 | 501 | 148ms | 6.801초 |
| 정상 재시작 | 전체 지터 | 501/499 | 57 | 404 | 25ms | 6.750초 |
| 강제 종료 | 고정 1초 | 495/505 | 390 | 495 | 1,040ms | 10.536초 |
| 강제 종료 | 전체 지터 | 492/508 | 55 | 435 | 38ms | 7.670초 |

네 조건 모두 연결·조회 실패 0, nginx worker 연결 한도 오류 0, 1초 간격 Hikari 대기 표본 최대 0이었다. 60초 뒤 세션은 모두 app1/app2 `0/1,000`으로 남았다. 지터는 시도 시각을 나눴지만 열린 연결을 두 앱으로 다시 나누지는 않았다(F54). 1초 최대값의 감소가 100ms 최대값보다 작은 것은 첫 실패의 지터 범위가 여전히 0~1초이기 때문이다. 브라우저에서는 app1 재시작 후 B 탭이 종료 코드 1006에서 `연결됨`으로 돌아오고 재연결 1회를 표시했다. 여러 탭의 서버 접속 로그 시각은 같지 않았고 nginx 로그에는 앱 재시작 중 502 재시도도 남았다. 이 소규모 브라우저 확인을 1,000개 실험의 정량 결과로 취급하지 않는다.

## 회귀와 한계

- 백엔드 `./gradlew test`: 77개 suite·447건, 실패·오류·건너뜀 0.
- 프론트 `npx vitest run`: 23개 파일·118건. `npx tsc -b`, `npm run lint`, `npm run build` 통과.
- Playwright Chromium `npm run e2e`: 8건 통과. 종료 때 Vite proxy의 기존 `EPIPE` 경고가 있었지만 테스트 실패는 없었다.
- `CLUSTER_PROFILE=local docker compose -f infra/compose.cluster.yml up -d --wait` 뒤 앱 2개·MySQL·nginx가 healthy였다. Chrome은 빌드된 `index-XeGhUy-a.js`를 nginx에서 받았다.

부하 결과는 한 로컬 머신에서 조건별 한 차례 얻었다. 조회 p99 개선폭을 일반적인 성능 보장으로 읽을 수 없다. Java 클라이언트는 브라우저의 재연결 정책과 연결 직후 최신 한 페이지 조회만 흉내 냈고, 추가 페이지가 없는 조건이었다. 실제 브라우저 수천 개나 새 메시지가 쌓인 복구는 측정하지 않았다. 1초 간격 Hikari 표본은 짧은 대기를 놓칠 수 있다. 복구 뒤 연결 쏠림(F54), 다른 서버 push 누락(F7), 그 누락을 성공으로 세는 지표(F53)는 남아 있다.
