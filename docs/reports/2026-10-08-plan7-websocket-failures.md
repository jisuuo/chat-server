# 계획 7 장애 재현: 단일 서버 WebSocket (2026-10-08)

계획 7 작업 9~12를 MySQL 스키마 A·JDBC 기본 저장소에서 실행했다. 백엔드 실험은 `@Tag("experiment")`로 일반 테스트와 분리했고, 결과 CSV는 `backend/build/experiment-results/`에 생성된다. 코드 리뷰 뒤 다시 측정한 최종 해석에 사용한 파일은 `ws-session-registry-verified.csv`, `ws-slow-consumer-timed.csv`와 `ws-slow-consumer-timed-rows.csv`, `ws-half-open.csv`와 `ws-half-open-push.csv`, `ws-reconnect-loss.csv`다. 아래 수치는 관찰값이다. F3은 원래의 장애 재현 뒤 보완했고, 아래에 전후 결과를 나눠 기록한다. F4~F6의 수치는 F3 보완 전 코드에서 측정했으며, 해결 코드는 아직 적용하지 않았다.

## F3. 세션 저장소 동시성

`SessionRegistryExperiment`는 별도 저장소에 8개 스레드가 10초 동안 추가·삭제·순회를 반복한다. 예외 객체를 무제한 수집한 첫 시도는 테스트 JVM의 힙을 소진해 제외했다. 이후 예외를 종류별 건수로 집계하고 반복마다 1ms 쉬도록 부하를 제한했다. 직접 실험에서 생긴 잔여 세션이 실제 연결 실험의 게이지에 섞이지 않도록 저장소 인스턴스도 분리했다. 실제 연결 실험은 200개 클라이언트의 `close()` 작업 결과와 클라이언트 종료 이벤트 수를 따로 확인한 뒤 서버 게이지를 읽었다.

| 반복 | 직접 연산 | 직접 예외 | 추가 직후 유실 | 직접 실험 잔여 | 실제 연결 200개: 연결 뒤 부족 / 종료 뒤 잔여 | 종료 작업 오류 / 클라이언트 종료 이벤트 |
|---:|---:|---|---:|---:|---:|---:|
| 1 | 60,157 | CME 27, NPE 7,480 | 392 | 2,720 | 2 / 1 | 0 / 200 |
| 2 | 60,398 | CME 38, NPE 7,508 | 552 | 3,395 | 0 / 0 | 0 / 200 |
| 3 | 57,472 | AIOOBE 3, CME 41, NPE 7,110 | 386 | 1,044 | 3 / 0 | 0 / 200 |

CME는 `ConcurrentModificationException`, NPE는 `NullPointerException`, AIOOBE는 `ArrayIndexOutOfBoundsException`이다. 실제 연결 시험의 클라이언트 접속 오류는 세 번 모두 0건이었다. 직접 실험의 잔여 수는 반복 중 실패한 조작이 누적된 값이므로 실제 운영에서 세션이 그만큼 쌓인다는 추정값이 아니다. 실제 연결의 게이지 불일치는 연결 직후 2/3회, 종료 5초 뒤 1/3회 관찰했다. 클라이언트 종료 이벤트 200개를 확인했지만 서버 종료 콜백의 실행 시각을 직접 기록하지 않아 종료 뒤 잔여 1개의 원인을 세션 저장소만으로 단정하지 않는다. 직접 실험의 예외·유실은 `HashMap`·`ArrayList` 동시 수정 결함을 보여 주며 브라우저의 앞선 CME 관찰과 같은 계열이다.

### F3 보완 뒤 재측정 (ADR-142)

`HashMap`·`ArrayList`를 `ConcurrentHashMap`·동시성 집합으로 바꾸고, 같은 사용자 ID의 추가는 `compute`, 삭제는 `computeIfPresent`로 원자적으로 처리했다. 실험 코드는 바꾸지 않고 같은 MySQL 조건에서 세 번 반복했다. 새 회귀 테스트와 전체 백엔드 `./gradlew test`도 통과했다.

| 반복 | 직접 연산 | 직접 예외 | 추가 직후 유실 | 직접 실험 잔여 | 실제 연결 200개: 연결 뒤 부족 / 종료 뒤 잔여 | 종료 작업 오류 / 클라이언트 종료 이벤트 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 58,393 | 0 | 0 | 0 | 0 / 0 | 0 / 200 |
| 2 | 58,978 | 0 | 0 | 0 | 0 / 0 | 0 / 200 |
| 3 | 59,685 | 0 | 0 | 0 | 0 / 0 | 0 / 200 |

원래 직접 실험은 세 번 모두 예외와 추가 직후 유실이 있었고, 실제 연결 시험은 2/3회에서 접속 뒤 게이지가 부족했다. 수정 뒤 같은 관찰 항목은 모두 0이었다. 그러나 동시 추가·삭제 중 순회의 탭 포함 여부는 약한 일관성이며, 서버 종료 콜백 시각을 계측하지 않았으므로 모든 종료 경로가 안전하다는 증명은 아니다. 같은 세션 동시 쓰기(F43)는 별도 문제다.

## F4. 느린 수신자와 커밋 후 전송 실패

`SlowConsumerExperiment`에서 방 멤버 ID 순서를 발신자 → 읽지 않는 수신자 → 빠른 수신자로 만들었다. 수신자가 읽지 않는 소켓의 수신 버퍼는 4KiB다. 약 3KiB 메시지 50건을 정상 조건으로 보낸 뒤, 읽지 않는 소켓을 붙여 최대 400건을 전송했다. REST 응답이 2초를 넘으면 10건을 더 보낸 뒤 멈췄다. 빠른 수신자의 프레임 ID와 REST 응답의 메시지 ID를 비교했고 DB 저장 건수를 별도로 셌다. 프레임 도착 시간은 클라이언트 수신 콜백의 `System.nanoTime()`으로 기록했다.

| 반복 | 조건 | 메시지 | REST p50 / 최대 | 실제 빠른 수신 최대¹ | push 타이머 최대 | REST 201 아닌 응답 | 빠른 수신자 ID 누락 | DB 저장 증가 |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | 정상 | 50 | 11 / 36ms | 33ms | 2.0ms | 0 | 0 | 50 |
| 1 | 읽지 않음 | 162 | 7 / 20,076ms | 14ms | 20,062.3ms | 0 | 1 | 162 |
| 2 | 정상 | 50 | 12 / 44ms | 41ms | 2.3ms | 0 | 0 | 50 |
| 2 | 읽지 않음 | 162 | 9 / 20,083ms | 30ms | 20,065.0ms | 0 | 1 | 162 |

¹ 프레임을 받은 건만 대상으로 한 최대값이다. 누락 1건의 도착 시간을 뜻하지 않는다.

두 반복 모두 읽지 않음 조건의 152번째 전송(index 151)은 REST 201이었고 DB에도 저장됐지만, 빠른 수신자에게 해당 ID의 프레임이 오지 않았다. 서버 테스트 출력에는 `TransactionSynchronization.afterCompletion threw exception`과 `SocketTimeoutException: Write timeout`이 남았다. 동기 fan-out에서 앞 순서의 소켓 쓰기가 약 20초 막힌 뒤 예외가 나자 뒤 수신자의 push가 건너뛰어진 것이다. 성공한 전달만 기록하는 `chat.delivery.total`의 최대 19.0/29.9ms는 이 실패한 20초를 포함하지 않으므로 REST 최대 시간과 직접 비교할 수 없다. 이 재현은 F44와 F50의 전송 실패 경로도 확인한다. 같은 세션에 여러 스레드가 동시에 쓰는 F43은 이 실험 조건에 포함되지 않았다.

## F5. half-open 연결

`HalfOpenExperiment`의 TCP 프록시는 연결을 유지한 채 양방향 전달을 멈췄다. 코드 리뷰 뒤에는 클라이언트의 EOF가 freeze 중에 도착해도 서버 쪽 출력 스트림을 닫지 않게 고쳤다. 수정 전후 두 번의 실행에서 모두 클라이언트가 닫힌 뒤 서버 세션 게이지는 0·10·30·60초 기준보다 1 높았다. 이후 3KiB 안팎의 메시지 30건을 보냈고 모두 REST 201이었다. 이 양으로는 서버 송신 버퍼가 차거나 전송이 멈추는 현상까지 관찰되지 않았다. 프록시 종료 때 소켓을 닫으므로 그 뒤의 세션 수는 이 결과에 포함하지 않는다.

## F6. 재연결 누락

`ReconnectLossExperiment`에서 첫 연결을 닫고 메시지 ID 1을 저장한 다음 재연결했다. 재연결 뒤 메시지 ID 2를 저장했을 때 수신 프레임 ID는 `[2]`였다. ID 1은 push에 없고 REST 최신 조회에는 있었다. 종료 뒤 세션 게이지의 기준 대비 증분은 0이었다.

Playwright Chromium에서도 WebSocket을 닫고 재연결을 막은 동안 REST 201로 메시지를 저장했다. 재연결 뒤 화면에는 그 메시지가 없었고, 이후 전송한 메시지는 나타났다. 새로고침 뒤에는 누락된 메시지가 REST 조회로 보였다. 재연결 중 따라잡기 조회가 없는 현재 화면의 동작을 브라우저에서도 확인했다.

## F49. 최초 조회와 소켓 구독 사이

추가 브라우저 실험에서 B의 방 화면을 내린 뒤 App 수준 WebSocket 연결은 유지했다. B가 다시 방을 열 때 최신 조회 응답을 Playwright로 먼저 받아 고정했다. 그 응답을 화면에 전달하기 전에 A가 REST 201로 새 메시지를 저장했고, B 브라우저가 **해당 메시지 ID의 WebSocket 프레임을 실제 수신한 것**을 확인했다. React StrictMode가 시작한 두 조회에는 같은 이전 스냅샷을 전달했다. B가 `ready` 상태로 돌아온 뒤 앱의 `받은 프레임` 수 증가도 확인하고 짧은 렌더링 여유 뒤에 새 메시지가 화면에 없는지 검사했다. 응답 고정을 해제하고 새로고침하자 보였다. 최초 조회와 구독 사이의 누락 경로를 통제해 재현한 것이다. 나가기 직후 재입장 경주는 별도로 측정하지 않았다.

## 보완 제안 (F3 적용, 나머지 결정 전)

1. **한 줄 요약:** F3에는 사용자별 세션 집합과 키 단위 원자적 갱신, F4에는 수신자별 전송 격리, F5에는 연결 생존 확인, F6·F49에는 조회와 실시간 수신 사이의 누락 복구가 필요하다.
2. **문제:** 동시 세션 수정은 예외·유실을 만들고, 느린 소켓은 REST를 20초 지연시키며 뒤 수신자의 프레임을 누락시켰다. 조용히 끊긴 연결은 60초 남았고 재연결과 최초 조회 사이에서도 저장된 메시지가 화면에서 빠졌다.
3. **사용 화면의 변화:** 다른 탭의 실시간 수신이 안정되고, 한 수신자의 지연이 방 전체로 번지지 않으며, 재연결 뒤 누락 메시지가 자동으로 보이게 된다.
4. **추천과 이유:** F3 저장소는 `ConcurrentHashMap<Long, Set<WebSocketSession>>`으로 바꾸고 추가·삭제를 각각 `compute`·`computeIfPresent`로 처리했다(ADR-142). 다음으로 수신자별로 제한된 송신 큐·시간 제한을 검토한다. 끊긴 연결은 ping/pong 또는 heartbeat로 정리한다. 재연결 시 누락 조회·병합을 검증하고, 최초 조회 중에는 push를 버퍼에 담아 조회 결과와 병합하는 방안을 검토한다.
5. **비용과 위험:** 집합 순회는 약한 일관성이며 같은 세션 동시 쓰기(F43)는 따로 다뤄야 한다. 큐는 메모리 상한·드롭 정책·순서 정의가 필요하다. heartbeat는 네트워크 비용과 오탐 가능성이 있다. ID 커서만으로 따라잡으면 커밋 순서 역전(F22)을 놓칠 수 있어 조회 범위와 중복 병합을 함께 설계해야 한다.
6. **기술 근거:** 재현 당시 저장소는 `HashMap`·`ArrayList`였다. fan-out은 커밋 뒤 같은 스레드에서 멤버 ID 순서로 전송한다. 화면은 재연결 때 메시지 조회를 호출하지 않는다. `computeIfAbsent(...).add(...)`는 삭제와 추가를 한 키 안에서 원자적으로 묶지 못하므로 F3 보완 때 추가도 `compute` 안에 뒀다.
7. **결정할 사항:** F3 변경은 적용했다. F4의 큐·시간 제한과 실패 알림 정책, F5의 생존 확인 방식과 임계값, F6의 조회 시점·범위·허용 표시 지연, F49의 초기 버퍼링·병합 방식을 정해야 한다.

원래 장애 재현 뒤 검증: 백엔드 `./gradlew test` 통과. 프론트 `npx tsc -b`, `npm run lint`, Playwright E2E 7건 통과. E2E 종료 과정에서 Vite의 `EPIPE` proxy 경고가 반복됐으나 테스트 실패는 없었다. F3 보완 뒤에는 백엔드 전체 테스트와 F3 실험 3회만 다시 실행했다.
