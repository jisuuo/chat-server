# 계획 5a 정합성·경쟁 실험 결과

> 2026-10-07. `backend/src/test/java/jissuo/chat/experiment/`의 JUnit 실험을 `./gradlew experimentTest`로 실행했다. 원자료는 `backend/build/experiment-results/*.csv`이며, 빌드 정리 뒤에도 확인할 수 있도록 [CSV 스냅샷](2026-10-07-plan5a-results/)을 함께 보관했다.

## 조건과 판정

- `mysql-rr`: MySQL 8.4.11 기본 `REPEATABLE READ`; `mysql-rc`: MySQL 8.4.11 `READ COMMITTED`; `pg-rc`: PostgreSQL 18.6 기본 `READ COMMITTED`.
- 모두 메시지 스키마 A, Testcontainers, 서비스 직접 호출, 테스트 전용 Hikari 최대 연결 64개를 사용했다. PostgreSQL 별도 격리 수준과 스키마 B는 측정하지 않았다.
- 결정적 재현은 저장소 호출 직후 경쟁 상대가 끝날 때까지 멈춰 가능한 장애인지 확인했다. 빈도 실험은 별도로 자연 동시 실행했다. 빈도 수치는 시도 횟수와 함께 읽어야 하고 확률의 안정된 추정치는 아니다.
- F18의 전역 번호는 호출 직전과 반환 직후를 표시한다. 두 구간이 겹치면 커밋 선후를 판정하지 않는다. 자연 실행의 실시간 폴링과 사후 목록 비교는 입장 근처 id 창에서만 했다.

## 해석과 다음 단계

입장 경계는 `joined_message_id`를 유지한다(ADR-100). 시각 기준은 시계 차이와 동일 마이크로초에서 결정적으로 유출·유실을 보였다. ID 기준도 `after` 폴링의 커밋 순서 역전(F22) 문제를 해결하지는 않는다. `joined_at` 삭제는 재현 자료를 보존하고 5b 뒤의 마이그레이션으로 검토한다.

F22·F23의 운영 코드와 실제 방 유지 정책은 이번 실험에서 바꾸지 않았다(ADR-034·037·012). F19는 방 삭제를 넣을 경우의 실험이며 현재 API에는 방 삭제가 없다. F22·F23 해결책은 후속 정합성 강화에서 비교한다. 5b는 k6로 HTTP 부하, DB 선택 규칙, 스키마 A/B, 풀 고갈과 삭제 부하를 측정한다.

Testcontainers에는 Compose의 DB별 CPU 2개·메모리 1GB 제한을 적용하지 않았다. Mac Docker 위의 절대 처리량과 빈도는 운영 환경으로 일반화할 수 없고, 스케줄링에 따라 매번 달라진다.
