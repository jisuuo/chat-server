# 계획 5b 부하·DB 비교 결과

> 2026-10-07. 사전 규칙은 ADR-101~104, 실행 계획은 [계획 5b](../superpowers/plans/2026-10-07-plan5b-load-db-comparison.md)에 둔다. 표의 수치는 공식 실행의 원시 k6 JSON·CSV에서 집계했다. 1~3초 시범 실행은 결과에서 제외한다.

## 환경

- MySQL 8.4.11 / PostgreSQL 18.6, DB별 Docker CPU 2개·메모리 1GB, 캐시 256MB, 내구성 설정 일치.
- 앱 Spring Boot 4.1.1 `bench` 프로필, Docker CPU 2개·메모리 1GB, Java 21, Hikari 기본 최대 10개, 접근 로그 OFF.
- 앱 바이트는 `load/artifacts/chat-bench.jar`로 고정했다(SHA-256 `ac826aeb7bb100383693fe224b3f19171f3b75c9cac38eb27989c14ed515f432`). 초기 조합의 원본 `backend/build/libs` JAR도 같은 해시이며, 후속 조합은 고정 복사본을 마운트한다.
- k6 2.1.0(darwin/arm64)은 호스트에서 API `http://localhost:18080`을 호출했다. 앱과 DB는 격리된 `chat-bench` 프로젝트를 사용했다. 기존 `chat-db`의 볼륨과 데이터는 보존했다.
- 데이터: 방·사용자 각 10,000, 멤버 68,000, 메시지 500,000 또는 5,000,000건. 각 구성은 빈 벤치 볼륨에서 재적재하고 I1~I7과 분포를 검증한다.
- 각 조건 15초 워밍업 뒤 30초 × 3회. 표에는 중앙값을 적고 반복 범위를 함께 둔다. W1·W5의 데이터 누적은 별도 기록한다.
- 기존 모니터링·local DB 컨테이너는 측정 동안 중지하고 종료 뒤 원상 복구한다. 컨테이너와 호스트의 CPU·메모리·디스크가 같은 Mac Docker VM을 공유한다.
- 500만 건 첫 MySQL 적재는 Docker VM 여유 공간 1.3GB에서 `ERROR 1114 (table is full)`로 실패했다. 오래된 미사용 Docker 빌드 캐시 9.5GB를 정리해 VM 여유 공간을 16GB로 늘렸고, 실패한 격리 볼륨을 버린 뒤 500만 건을 처음부터 재적재했다. 실패 적재는 성능 자료에 포함하지 않는다.
- 최초 탐색 기준선의 W5는 폴링할 때마다 방을 바꿔 최초 조회를 반복했다. 이 실행은 `exploratory-*`로 분리하고 판정에서 제외했다. 폴링 방을 VU별로 고정한 뒤 3초 검증에서 요청 비율 W1:W2:W3:W4 = 540:1628:1616:1616(약 10:30:30:30)을 확인하고 공식 기준선을 새 적재에서 재실행했다.
- 계획서의 DB별 번갈아 반복과 매 반복 동일 스냅샷 복원은 적용하지 못했다. 재적재 비용 때문에 구성별로 세 반복을 묶었고, 쓰기는 누적시켰다. 기준선 전체의 메시지 수는 MySQL-A 5,000,000→5,220,365건, MySQL-B 5,000,000→5,228,075건, PostgreSQL-A 5,000,000→5,535,454건이었다. 이 차이와 실행 순서로 인한 호스트 상태 변화는 인과 해석의 한계다.

W1은 전송, W2는 최신 50건, W3은 인기 방 1의 과거 50건, W4는 VU별 고정 방의 `after` 폴링이다. W5는 이 네 요청을 10:30:30:30으로 섞는다. 방 선택은 50/30/20 분포이고, W4의 주기 조건은 응답 뒤 해당 초만큼 쉰다. 각 시나리오의 실행 순서는 고정이며, W1·W5의 쓰기는 반복 동안 쌓인다. 따라서 `dataset_start/end.json`의 크기 변화와 반복 범위를 함께 해석한다. W1~W4 p99는 해당 요청의 k6 Trend, W5 p99는 전체 HTTP 요청 지표다.

## C4: DB 재시작 뒤 회복

| 구성 | 회복 시간 중앙값 | W2 재시작 직후 / 안정 p99 | W4 재시작 직후 / 안정 p99 | DB 내부 읽기 카운터 증분 중앙값(직후 / 안정) |
|---|---:|---:|---:|---|
| MySQL-A | 약 6.7초 | 76.5 / 70.3ms | 46.9 / 47.4ms | W2 261,866 / 239,350, W4 1,688 / 0 버퍼풀 읽기 |
| MySQL-B | 약 6.7초 | 72.6 / 70.5ms | 47.2 / 46.7ms | W2 68,003 / 56,532, W4 619 / 0 버퍼풀 읽기 |
| PostgreSQL-A | W2 약 5.9초, W4 약 5.7초 | 58.3 / 59.0ms | 42.6 / 42.1ms | W2 105,686 / 80,112, W4 1,447 / 2 `blks_read` |

DB 컨테이너 재시작은 호스트 OS 파일 캐시를 비우지 않는다. 따라서 이 구간은 엄밀한 cold cache가 아니라 DB 재시작 회복 측정이다. MySQL `Innodb_buffer_pool_reads`와 PostgreSQL `blks_read`는 정의가 다른 카운터여서 DB 간 절대값을 비교하지 않는다. `blks_read`는 OS 파일 캐시에서 읽은 블록도 포함할 수 있다.
각 구성에서 W2·W4를 각각 세 번 재시작하고, DB와 앱 건강 상태가 UP이 된 시점부터 30초 실행한 뒤 바로 안정 구간 30초를 실행했다. MySQL-A/B와 PostgreSQL-A의 첫 W2 재시작 직후 p99는 각각 175.5/169.0/105.4ms로 다음 두 반복보다 높았으나, 표의 세 반복 중앙값에는 이 일회성 상승이 작게 반영된다. 모든 구간의 HTTP 오류는 0건이었다.

### F15 깊은 offset과 cursor

|---|---:|---:|---:|---:|---:|

### F16 인덱스 유무

500만 건 새 적재에서 `(room_id, id)` 인덱스를 둔 채 W2·W3·W4를 3회씩 측정하고, 격리 DB의 인덱스를 제거해 같은 조건을 3회 반복한 뒤 복원한다. API는 커서 쿼리를 그대로 사용한다.

| 구성 | 인덱스 | W2 p99 / RPS | W3 p99 / RPS | W4 p99 / RPS | 오류율 |
|---|---|---|---|---|---:|
| MySQL-A | 있음 | 71.7ms / 2,652/s | 60.1ms / 3,285/s | 48.5ms / 6,242/s | 0% |
| MySQL-A | 없음 | 11,590ms / 12/s | 207.2ms / 629/s | 53.8ms / 4,008/s | 0% |
| PostgreSQL-A | 있음 | 58.7ms / 3,790/s | 57.7ms / 4,146/s | 43.0ms / 8,023/s | 0% |
| PostgreSQL-A | 없음 | 11,734ms / 15/s | 97.0ms / 1,604/s | 42.8ms / 5,694/s | 0% |

MySQL-A의 W2는 인덱스 제거 뒤 p99가 약 162배, W3는 약 3.4배 늘었다. PostgreSQL-A의 W2는 약 200배, W3는 약 1.7배 늘었다. W4 p99는 MySQL에서 약 11% 늘고 PostgreSQL에서 거의 같았지만 두 DB 모두 처리량은 줄었다. `EXPLAIN ANALYZE`에서 MySQL W2·W3는 보조 인덱스 대신 `PRIMARY`를 역방향 또는 범위 스캔해 방 조건을 거르고, W4는 인덱스 유무와 관계없이 `PRIMARY`의 `id > after` 범위 스캔을 썼다. PostgreSQL도 제거 뒤 세 쿼리 모두 `messages_pkey`를 스캔해 방 조건을 걸렀다. 따라서 **인덱스 부재로 성능 저하는 재현됐지만 테이블 전체를 풀스캔한다는 원래 가설은 이 입력에서 틀렸다.** 전후 실행 순서와 캐시 상태도 영향을 줄 수 있으며, 단일 SQL 계획 시간과 동시 HTTP 부하 p99는 같은 지표가 아니다.

### F20 방 정렬값 갱신 경합

PostgreSQL-A에서 방 1에만 W1 전송을 VU 50으로 3회 수행했다. 처음에는 `rooms.last_message_id` 인덱스가 없고, 다음에는 격리 DB에 인덱스를 추가했다. 실험 뒤 추가 인덱스는 제거했다.

| 방 정렬값 인덱스 | W1 p99 중앙값 [범위] | RPS 중앙값 | HOT 업데이트 / 전체 `rooms` 업데이트 | `rooms` 전체 크기 변화 |
|---|---:|---:|---:|---:|
| 없음 | 59.3ms [54.3,59.6] | 2,132/s | 76,544 / 77,228 (99.1%) | 1.93→2.11MB |
| 있음 | 56.8ms [52.7,57.3] | 2,242/s | 768 / 89,325 (0.9%) | 2.35→4.83MB |

인덱스를 추가하자 HOT 갱신 비율이 크게 줄고 측정 구간의 `rooms` 총 파일 크기가 더 늘었다. 반면 이 30초 반복의 p99·RPS는 악화되지 않았다. 인덱스 없는 구간을 먼저 실행해 캐시·테이블 상태가 달랐고 자동 vacuum도 동시에 일어날 수 있으므로, p99의 작은 차이를 인덱스 효과로 단정하지 않는다. 이 실험의 인덱스는 현재 운영 스키마에는 없다. C3의 인기 방 처리량 감소와 인덱스에 따른 HOT·크기 영향은 서로 다른 관찰이다.

### F19 대량 삭제

빈 벤치 DB에 500만 건을 적재한 뒤 방 1의 기존 멤버 50명 중 49명을 먼저 지웠다. 마지막 멤버 1명, 메시지 25,000건, 방 1개를 한 트랜잭션에서 삭제하고 클라이언트가 완료를 받기까지의 시간을 1회 측정했다. 세 구성 모두 남은 메시지·멤버·방은 0건이다.

| 구성 | 삭제 트랜잭션 | 전후 내부 지표 | 메시지 테이블+인덱스 크기(삭제 전) |
|---|---:|---|---:|
| MySQL-A | 3.267초 | InnoDB history list 2→3 | 1,040MB |
| MySQL-B | 0.215초 | InnoDB history list 7→8 | 1,384MB |
| PostgreSQL-A | 0.403초 | dead tuple 0→25,000, `messages` 파일 886MB 그대로 | 1,201MB |

MySQL의 history list는 purge가 동시에 진행되는 시점 값이므로 생성된 undo 레코드 수나 삭제 비용을 직접 나타내지 않는다. PostgreSQL은 삭제 직후 dead tuple 25,000개가 남고 파일 크기도 즉시 줄지 않았다. 삭제 시간은 구성별 1회·서로 다른 물리 저장 구조의 결과여서 반복 분포가 없으며 일반적인 DB 우열의 근거로 쓰지 않는다. 크기는 각 DB가 보고한 메시지 테이블·인덱스 범위로, WAL·undo 파일을 포함한 전체 디스크 사용량과 다르다.

## 판정

- **MySQL은 스키마 A 유지.** B의 500만 건 읽기 p99는 W2 92.5ms(대비 A 68.9ms), W3 79.1ms(61.9ms), W4 51.4ms(49.5ms)로 모두 A보다 높다. B의 W1은 70.2ms(대비 A 88.6ms)로 빨랐지만, ADR-014·104의 읽기 세 경로 각각 30% 개선 조건을 충족하지 못했다.
- **DB 선택은 보류.** 500만 건·VU 50 W5 p99는 PostgreSQL-A 52.9ms(반복 범위 51.5~56.7), MySQL-A 62.5ms(60.7~68.8)로 PostgreSQL이 약 15.4% 낮고 RPS는 약 47.8% 높았다. VU 200 오류율은 두 DB 모두 0%였지만, ADR-101의 p99 20% 개선 문턱에는 못 미친다. 사전 규칙을 그대로 적용한 [`official-decision.json`](2026-10-07-plan5b-results/official-decision.json)의 선택 후보도 없다. 5a에서 재현한 F22·F23 정합성 결함은 선택 결과와 별개로 남긴다.
