### 0. 설명 방식 회고 (협업 규칙)

방 목록 정렬 설명이 이해되지 않았던 원인을 함께 분석했다.
- 원인 4가지 모두 해당: 모르는 용어(HOT, loose index scan 등), 한 번에 개념 과다(약 13개), 핵심(결론)이 안 보임, 번호 참조(F2, ADR-015 등)
- 근본 원인: 결론이 먼저 보이지 않아서, 모든 세부 용어가 다 중요해 보였다.
- 두 번째 설명(안내판 비유, 한 줄 요약 먼저, 개념 1개, 번호 없음)은 이해되었다.

**앞으로의 기술 제안 형식** (사용자가 확정)
1. 한 줄 요약: 무엇을 바꾸자는 제안인지
2. 해결하려는 문제: 현재 사용자가 겪는 문제를 구체적인 예로
3. 사용 화면의 변화: 적용 후 달라지는 것, 기대와 다르게 보일 수 있는 경우
4. 추천안과 이유: 다른 방법과 비교할 때 중요한 차이만
5. 비용과 위험: 성능, 정합성, 동시성을 쉬운 말로
6. 기술적 근거: 용어, SQL, DB별 동작, 실험 항목. 용어는 처음 나올 때 짧게 설명
7. 지금 결정할 사항: 이미 결정된 것과 새로 결정할 것을 구분. 추천안의 한계와 확인 필요 사항 포함

- 중요한 조건을 생략하거나 결과를 단정하지 않는다. 비슷하지만 다른 경우를 구분한다 (예: "메시지가 없는 방"과 "현재 멤버가 없는 방").
- DB 종류나 설정에 따라 달라지는 동작은 조건을 밝힌다.
- 예상되는 문제와 실제로 측정·검증한 결과를 구분한다.
- F번호, ADR번호, Step 번호는 맥락을 풀어쓴 뒤 괄호에 표시한다.
- 전체 흐름을 먼저, 깊은 구현 설명은 뒤에.

| DB 가설 | "(A)면 PostgreSQL이 유리해 보인다"는 가설 제기 | 구조적으로 맞는 가설. "같은 스키마 비교"와 "각자 최선 비교"로 나눔 |

| 모니터링 | Elasticsearch, Kibana, Grafana, 로그와 헬스 체크 필수, local TRACE, 운영 감사 로그 | Prometheus 추가 제안을 수용 (ADR-021 ~ 023) |
| 데이터 접근 | `JdbcClient`로 시작하되 JPA로 변환·확장 | 인터페이스 + 구현체 2개, 실험 후 전환 (ADR-024, 025) |

| 계획 분할 | 계획 5개 분할과 순서에 동의 | ADR-033 |

#### 막힌 지점과 해소 방법
| 막힌 지점 | 무엇이 어려웠나 | 해소 |
|---|---|---|
| 방 목록 정렬 첫 설명 | 모르는 용어(HOT, loose index scan 등), 개념 과다(약 13개), 핵심(결론)이 안 보임, 번호(F2, ADR-015) 참조 | 안내판 비유와 한 줄 요약으로 재설명. **설명 형식 7단계 규칙**을 함께 정함 (0. 설명 방식 회고) |
| 왜 폴링부터? | 최종 해법도 아닌데 왜 만드는지 | "비교 기준선 + DB 부하 생성기 + 재연결 복구 로직의 원형"으로 이해 |
| 인가와 `joined_message_id` | 경계값이 있으면 멤버로 판단하는 것인지 | 기준은 "값"이 아니라 "행의 존재". 인증(누구인가)과 인가(해도 되는가) 구분 |
| PK 측정 기준 | 더 빨리 찾는 쪽으로 가면 되는지 | 복합 PK는 읽기 대신 쓰기를 희생. 지표 5가지와 판정 규칙 |
| `after`/`before` | 스크롤 기준이 무엇인지 | 화면 맨 위(가장 오래된) = before, 맨 아래(가장 최신) = after. 커서 방식의 이유 |
| 성공 응답 "그대로" | 무슨 뜻인지 | 포장 없음과 포장 있음의 예시 비교 |
| bench 환경 | 무엇인지 | 부하 실험할 때 켜는 active profile |
| TRACE와 DEBUG | TRACE면 모든 DEBUG가 보이는지 | 같은 패키지 안에서만. 레벨은 패키지마다 따로 적용 |
| 외부 라이브러리 범위 | 어디까지인지 | 우리 패키지 바깥 전부. 실험에 필요한 SQL, HikariCP, 트랜잭션만 골라 열기 |
| 감사 로그 저장 방식 | 로그 기반 별도 저장소의 장점 | DB 부담 없음, 측정 오염 없음, Kibana 검색, 보관 기간 분리. 단 유실 가능 |
| origin과 proxy | 같은 주소 서비스와 proxy의 의미 | 안내 데스크 비유. 브라우저는 한 주소하고만 대화, 서버끼리 전달 |
| Vite와 nginx | 왜 개발과 운영이 다른지 | 작업실(고친 걸 바로 보기)과 매장(완성품을 빠르게 많이) |
| 사용자 생성 API와 401 | API로 만들면 인증 실패를 못 하는지 | 두 방식 모두 401 가능. 지금 401은 "그런 사용자 없음"에 가깝고 진짜 인증은 JWT부터 |

#### 배운 점
- 결론이 먼저 보이지 않으면 세부 용어가 전부 중요해 보여서 막힌다. 한 줄 요약 → 문제 → 화면 변화 → 추천 → 비용 → 기술 근거 → 결정 사항 순서가 효과적이었다.
- 비유(안내판, 안내 데스크, 작업실과 매장)와 그림이 이해를 크게 도왔다.
- 추천안에 반박하거나 질문했을 때 결정이 더 좋아졌다 (방 목록 최근 대화순, 사용자 생성 API, DB 실측 비교).

### 1. 과제 원문 요약

- HTTP 폴링: 클라이언트가 주기적으로 서버에 요청. 구현이 쉽지만 실시간성이 떨어지고, 주기를 짧게 하면 서버에 부담이 된다.
- WebSocket: 개념 공부 및 구현
- 채팅 서버 HTTP API
  - 메시지 전송: 컨트롤러 수신 → DB 저장 → 채팅방 유저 id 조회 → 실시간 전송 (Redis, Hash 활용)
  - 메시지 리스트 조회
  - 채팅방 생성 / 목록 / 입장 / 나가기

### 4. 진행 방식

**결정 → 구현 → 장애 재현 → 원인 분석 → 해결 → 기록**을 반복한다.

1. 단계마다 결정 하나만 의논한다. 선택지 2~3개와 트레이드오프를 보고 직접 결정한다.
2. 결정은 "결정 기록(ADR)"에 남긴다. 무엇을 골랐고 무엇을 포기했는지 적는다.
3. 점진적으로 진화시킨다. 각 단계마다 **일부러 장애를 낸다.**

### 5. 장애 실험 (Failure Lab) 목록

각 실험은 아래 템플릿으로 기록한다.

> **가설** → **재현 방법** → **관찰한 현상/지표** → **근본 원인** → **해결책** → **트레이드오프**

#### 폴링 / 조회
- **F1. 폴링 폭주로 DB 커넥션 풀 고갈**: 짧은 주기로 다수 클라이언트가 폴링하면 HikariCP 풀(기본 10개)이 고갈되어 요청이 타임아웃된다.
- **F2. "새 메시지" 조회 시 누락/중복**: `createdAt > 마지막 시각` 조건에서 같은 시각의 메시지가 누락되거나 중복된다.
- **F15. offset 페이지네이션 성능 저하**: 메시지 100만 건에서 뒤쪽 페이지 조회가 급격히 느려진다.
- **F16. 인덱스 부재로 인한 풀스캔**: `(room_id, id)` 인덱스 없이 조회하면 풀스캔이 발생한다.

#### WebSocket
- **F3. 세션 저장소 동시성 버그**: `HashMap`에 세션을 보관하면 동시 접속/해제 시 예외가 나거나 세션이 유실된다.
- **F4. 느린 클라이언트(slow consumer)**: 동기 전송 루프에서 한 명이 느리면 방 전체의 전송이 지연된다.
- **F5. half-open 좀비 연결**: 네트워크가 끊겼는데 서버는 모른다. ping/pong이 없으면 세션이 계속 쌓인다.
- **F6. 재연결 시 메시지 유실**: 끊겨 있던 동안 온 메시지를 받지 못한다.

#### 다중 서버
- **F7. 다른 서버에 연결된 유저에게 메시지 미전달**: 서버 2대 + 로드밸런서 환경에서 재현한다.
- **F8. 로드밸런서 뒤 WebSocket 연결 실패/끊김**: nginx에 `Upgrade`/`Connection` 헤더 설정이 없으면 handshake가 실패하고, 기본 idle timeout(60초)이 지나면 연결이 끊긴다.
- **F17. 배포/재시작 시 재연결 폭주 (thundering herd)**: 서버 재시작으로 수천 개의 연결이 동시에 재접속한다.

#### Redis
- **F9. Pub/Sub 메시지 유실**: Pub/Sub은 at-most-once라서 구독자가 잠깐 끊기면 메시지가 사라진다. (Streams와 비교)
- **F10. Redis 다운**: 실시간 전송 전체가 마비된다. fallback 전략이 필요하다.
- **F11. 멤버 캐시 정합성**: 방을 나간 뒤 캐시가 갱신되지 않아 나간 유저에게도 메시지가 간다.

#### 정합성
- **F12. 유령 메시지**: 트랜잭션 안에서 전송한 뒤 롤백되면, DB에는 없는데 유저는 메시지를 받은 상태가 된다.
- **F13. 재시도로 인한 중복 메시지**: 클라이언트 타임아웃 후 재전송하면 같은 메시지가 두 번 저장된다. (멱등성 키)
- **F14. 메시지 순서 역전**: 동시 전송이나 서버 간 시계 차이로 순서가 뒤바뀐다.
- **F18. 재입장 경계 오판**: 재입장 시점 경계를 시각(`joined_at`)으로 잡을 때와 메시지 id(`joined_message_id`)로 잡을 때, 동시 쓰기 중 유출/유실이 발생하는지 비교한다. (설계는 아래 "입장 경계 실험 설계")
- **F20. 방 목록 정렬 컬럼 갱신 경합**: 방 목록을 최근 대화순으로 정렬하기 위해 메시지마다 `rooms.last_message_id`를 갱신한다(ADR-016). 예상 문제(미검증): (1) 인기 방에서 같은 `rooms` 행을 고치려는 전송들이 행 락(한 행을 고치는 동안 다른 요청이 못 고치게 막는 잠금) 때문에 줄을 선다 (2) MySQL + `room_members` FK + 입장 알림 메시지가 겹치면 FK 공유 잠금과 UPDATE 배타 잠금이 엇갈려 데드락(서로의 잠금을 기다리며 둘 다 멈춤)이 날 수 있다 (PostgreSQL은 `FOR KEY SHARE`라 덜 발생할 것으로 예상) (3) PostgreSQL에서 `last_message_id`에 인덱스를 걸면 HOT 업데이트(인덱스를 건드리지 않는 갱신 최적화)가 불가능해져 테이블이 팽창한다. 측정: 동시 전송 수에 따른 전송 p99, DB별 데드락 발생 여부, PostgreSQL 인덱스 유무별 테이블 크기. Redis 이전(Step 4) 후 before/after를 비교한다.
- **F21. `JdbcClient`와 JPA 성능 비교**: JPA 전환(ADR-025) 후 같은 서버에서 설정 값으로 구현체만 바꿔 메시지 저장(W1)과 조회(W2~W4)를 측정한다. JPA의 쓰기 지연, IDENTITY 전략의 배치 저장 제약, 영속성 컨텍스트 비용이 수치로 얼마나 차이 나는지 확인한다. 측정 조합(DB × PK 스키마 × 기술)이 크므로 실행 시 조합을 줄일 수 있다.
- **F19. 마지막 나가기와 입장의 경쟁 (TOCTOU)**: 실제 기능은 방 유지(ADR-012)지만, "마지막 멤버가 나가면 방 삭제"를 실험용으로 구현해 경쟁을 재현한다. 마지막 멤버가 "멤버 수 확인 → 방 삭제"를 하는 사이에 다른 유저가 "방 존재 확인 → 입장"하면, 삭제된 방에 입장하거나(FK 에러) 존재하지 않는 방의 멤버가 생긴다. 해결 방법(비관적 락, 조건부 DELETE, 상태 컬럼, FK 제약)을 비교한다. 대량 메시지 삭제 시 긴 트랜잭션 부하(MySQL undo log, PostgreSQL dead tuple)도 함께 관찰한다.

#### 실험 도구 후보 (미정)
- 부하: k6 / nGrinder
- 네트워크 장애 주입: Toxiproxy, `docker pause`, `tc`
- 환경: Docker Compose (앱 x2, nginx, DB, Redis)
- 관측: Spring Actuator + Prometheus/Grafana, 로그

### 6. DB 비교 실험 설계 (ADR-003)

#### 워크로드 (실제 요청)
| ID | 요청 | 실제 상황 | SQL 형태 |
|---|---|---|---|
| W1 | 메시지 저장 | 메시지 전송 API | `INSERT` (동시 다발) |
| W2 | 최근 메시지 조회 | 채팅방 입장 | 방별 최신 50건 (cursor) |
| W3 | 과거 메시지 스크롤 | 위로 스크롤 | 깊은 페이지: offset과 cursor |
| W4 | 폴링 | Step 1 폴링 | `WHERE room_id=? AND id > lastId` |
| W5 | 혼합 | 실제 트래픽 | 읽기 90% / 쓰기 10%, 인기 방에 쏠림 |

데이터: 방 1만 개, 메시지 수백만~1천만 건, 방별 분포를 고르지 않게(소수 인기 방 집중).

#### 운영 조건
| ID | 조건 | 목적 |
|---|---|---|
| C1 | 데이터가 메모리에 다 들어갈 때와 넘칠 때 | 성능이 꺾이는 지점 확인 (컨테이너 메모리 제한으로 재현) |
| C2 | 동시 커넥션 10 / 50 / 200 | 어느 쪽이 먼저 무너지는지 |
| C3 | 인기 방 하나에 쓰기 집중 | 인덱스 끝부분 쓰기 경합 |
| C4 | DB 재시작 직후 (cold cache) | 정상 성능까지의 회복 시간 |

#### 검증 지표
- 사용자 관점: TPS, 응답 시간 p50 / p95 / p99, 에러율
- DB 내부: 실행 계획(`EXPLAIN ANALYZE`), 버퍼 캐시 적중률, 락 대기
- 자원: CPU, 메모리, 디스크 I/O, 테이블과 인덱스 크기

#### 공정성 규칙
- 두 DB에 같은 CPU와 메모리 제한 (Docker)
- 내구성 설정 일치: MySQL `innodb_flush_log_at_trx_commit=1`, PostgreSQL `synchronous_commit=on`
- 메모리 설정 비율 일치: `innodb_buffer_pool_size`와 `shared_buffers`
- warm-up 후 3회 측정, 중앙값 사용
- 한계: Mac Docker는 VM 위에서 동작하므로 절대 수치가 아니라 상대 비교로만 해석한다.

### 7. 인증 구조 (ADR-005, 006)

```
             [1. 추출: 통로별]                 [2. 판별: 단 한 곳]           [3. 전달: 사용처별]
HTTP 요청  → AuthFilter (X-User-Id 헤더)    ┐                              → @CurrentUser AuthUser
                                            ├→ Authenticator.authenticate()
WebSocket  → HandshakeInterceptor           ┘   지금: HeaderUserIdAuthenticator → WebSocketSession attributes
             (query/cookie, Step 2에서 결정)     나중: JwtAuthenticator

[인가] "이 유저가 이 방의 멤버인가?"는 인증 층이 아니라 도메인 서비스(RoomMemberService)가 판단한다.
```

- `Authenticator`는 `HttpServletRequest`에 의존하지 않는다. 문자열 credential만 받는다.
- 반환 타입은 `Long`이 아니라 불변 값 객체 `record AuthUser(long id)`이다.
  - `roomId`와 `userId`가 뒤바뀌는 버그를 컴파일 단계에서 막는다.
  - JWT 확장 시 필드(토큰 ID, 디바이스 ID 등)만 추가하면 되고 컨트롤러 시그니처는 바뀌지 않는다.
  - 닉네임 등 표시용 정보는 넣지 않는다 (토큰 만료 전까지 stale해지는 문제).
- 존재 여부를 DB로 확인하지 않는다. 폴링 요청마다 쿼리가 추가되면 F1(커넥션 풀 고갈)을 앞당긴다. 형식만 검증한다.
- ThreadLocal 대신 파라미터로 명시적으로 넘긴다. 비동기 전송(Step 2, F4 해결)에서 ThreadLocal 값이 사라지는 문제를 피한다.
- 브라우저 WebSocket API는 커스텀 헤더를 보낼 수 없다. WebSocket 인증 방식은 Step 2에서 다시 의논한다.

### 8. 입장 경계 실험 설계 (F18, ADR-008, 009)

#### 배경
재입장한 유저에게는 재입장 이후 메시지만 보인다 (ADR-008). 경계를 무엇으로 저장할지 실험으로 결정한다.
- `joined_at` (시각): 직관적이지만 F2와 같은 함정(같은 시각, 정밀도, 서버 간 시계 차이)이 예상된다.
- `joined_message_id` (입장 시점의 마지막 메시지 id): 조회 조건이 `id > joined_message_id`가 되어 폴링과 같은 `(room_id, id)` 인덱스를 탄다. 단, id는 INSERT 시점에 발급되고 다른 트랜잭션에는 COMMIT 시점에 보인다는 차이가 있다. 이 차이의 영향은 실험으로 확인한다.

#### 판정 기준 (ADR-009: 커밋 순서 기준)
- 입장이 커밋된 **뒤에** 커밋된 메시지는 반드시 보여야 한다. 안 보이면 **유실**.
- 입장이 커밋되기 **전에** 커밋된 메시지는 보이면 안 된다. 보이면 **유출**.
- 입장과 **동시에 진행 중이던** 메시지는 어느 쪽이든 허용한다. 단, 목록 조회와 폴링에서 일관되게 보여야 한다. 다르면 **불일치**.

#### 방법
1. 경계 전략을 인터페이스로 추상화하고 `TimeBoundary`, `IdBoundary` 두 구현체를 만든다.
2. 한 방에 여러 스레드가 계속 메시지를 쓰는 동안, 유저 한 명이 나갔다가 재입장한다. 수천 번 반복한다.
3. 매 반복마다 판정 기준에 따라 유출 / 유실 / 불일치를 센다.

#### 지표
| 지표 | 의미 | 심각도 |
|---|---|---|
| 유출(leak) | 입장 전 메시지가 보임 | 프라이버시 문제 |
| 유실(loss) | 입장 후 메시지가 안 보임 | 치명적 |
| 불일치 | 목록과 폴링 결과가 다름 | 사용자 혼란 |
| 조회 성능 | 실행 계획, 응답 시간 | 인덱스 사용 여부 |

#### 바꿔 볼 조건
- 시간 정밀도: MySQL `DATETIME`(기본 초 단위) / `DATETIME(6)`, PostgreSQL `timestamp`
- 시각을 찍는 주체: 애플리케이션(`LocalDateTime.now()`) / DB(`NOW()`)
- 서버 간 시계 차이: `Clock`을 주입해 수십 ms 어긋나게 설정
- 동시 쓰기 스레드: 1 / 10 / 50
- DB: MySQL / PostgreSQL (ADR-003 비교 데이터로도 사용)

### 9. PK 스키마 실험 설계 (F15, F16, ADR-013, 014)

#### 비교 대상
- (A) 단일 PK `id` + 보조 인덱스 `(room_id, id)`: 새 메시지는 항상 B-tree 오른쪽 끝에 추가된다 (쓰기 지역성 좋음).
- (B) 복합 PK `(room_id, id)`: MySQL InnoDB에서 같은 방 메시지가 물리적으로 연속 저장된다 (읽기 지역성 좋음). 대신 쓰기 위치가 활성 방 수만큼 흩어진다 (페이지 분할, 메모리 압박, 랜덤 I/O).
- 즉 (B)는 읽기를 빠르게 하는 대신 쓰기를 느리게 만드는 거래다. 읽기 속도만으로 결정하지 않는다.

#### 가설: (A)에서는 PostgreSQL이 구조적으로 유리하다
- PostgreSQL 보조 인덱스는 행의 물리적 위치(TID)를 직접 가리킨다.
- MySQL 보조 인덱스는 PK 값을 가리키므로 PK B-tree를 한 번 더 탄다.
- 메모리에 다 들어가면 차이는 작고, 메모리를 넘칠 때(C1) 커질 것으로 예상한다.
- (A)로만 비교하면 MySQL의 최대 무기(B)를 뺀 비교가 된다. 그래서 DB 비교를 두 종류로 나눈다.
  - 같은 스키마 비교: MySQL(A)와 PostgreSQL(A)
  - 각자 최선의 스키마 비교: MySQL(B)와 PostgreSQL(A)

#### 측정 매트릭스
| 구성 | 메모리에 들어갈 때 | 메모리를 넘칠 때 (C1) |
|---|---|---|
| MySQL (A) | ✓ | ✓ |
| MySQL (B) | ✓ | ✓ |
| PostgreSQL (A) | ✓ | ✓ |

PostgreSQL (B)는 clustered 효과가 없어서 제외한다 (확인용으로 한 번만 실행 가능).

읽기/쓰기 비율은 두 가지로 측정한다.
- 폴링 시점 (Step 1): 읽기 위주
- WebSocket 시점 (Step 2 이후): 폴링 조회가 사라져 쓰기 비중 증가

#### 지표
| 관점 | 지표 | 측정 방법 |
|---|---|---|
| 읽기 | W2(최근), W3(과거 스크롤), W4(폴링)의 p99 | k6 |
| 쓰기 | W1의 TPS와 p99, C3(인기 방 쏠림) 포함 | k6 |
| DB 내부 | 쿼리당 읽은 페이지 수, 디스크 읽기 횟수, 페이지 분할 수 | MySQL `Innodb_buffer_pool_reads`, `INNODB_METRICS` page split / PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` |
| 저장 공간 | 테이블과 인덱스 크기 | `information_schema` / `pg_relation_size` |
| 개발·운영 비용 | JPA 복합키 매핑, AUTO_INCREMENT 제약, DB별 스키마 분기 | 정성 평가 |

평균이 아니라 p99를 본다. 사용자가 체감하는 건 "가끔 멈칫하는 순간"이다.

#### 판정 규칙 (ADR-014, 측정 전에 확정)
> **(B)를 채택하는 조건**: 메모리를 넘치는 조건(C1)에서 읽기 p99가 **30% 이상 개선**되고, 동시에 쓰기 p99 악화가 **10% 이내**일 때. 둘 중 하나라도 못 미치면 (A)를 유지한다.

### 10. API 명세 (ADR-017)

모든 요청에 `X-User-Id` 헤더 필요. 없거나 형식이 틀리면 401 (ADR-005).

| 기능 | Method & URL | 성공 | 주요 실패 |
|---|---|---|---|
| 방 생성 (+ 생성자 자동 입장) | `POST /rooms` `{name}` | 201 | 400 |
| 방 목록 (최근 대화순, ADR-016) | `GET /rooms?cursor=…&size=20` | 200 | |
| 방 입장 | `POST /rooms/{roomId}/members` | 201 | 404 방 없음, 409 이미 멤버 |
| 방 나가기 | `DELETE /rooms/{roomId}/members/me` | 200 (`data: null`, ADR-020) | 403 멤버 아님 |
| 메시지 전송 | `POST /rooms/{roomId}/messages` `{content}` | 201 | 403 멤버 아님 |
| 메시지 조회 | `GET /rooms/{roomId}/messages` + `?after=` 또는 `?before=` (둘 다 없으면 최신) | 200 | 400 둘 다 지정, 403 멤버 아님 |

#### 설계 포인트
- **방 생성자 자동 입장**: 방 생성과 생성자 입장을 한 트랜잭션으로 처리한다. "방은 있는데 만든 사람이 멤버가 아닌" 상태를 막는다.
- **입장/나가기 = 멤버 리소스 추가/삭제**: 동사형 URL(`/join`, `/leave`) 대신 쓴다. 입장 = 멤버 가입(ADR-007), 나가기 = 행 삭제(ADR-010)가 URL에 드러난다.
- **메시지 조회는 엔드포인트 하나 + 커서 방향**:
  - 인자 없음: 최신 N개 (방 입장 시)
  - `after={화면 맨 아래, 가장 최신 메시지 id}`: 그보다 새로운 메시지 (폴링)
  - `before={화면 맨 위, 가장 오래된 메시지 id}`: 그보다 과거 메시지 (위로 스크롤)
  - 클라이언트는 자기가 가진 가장 오래된 id와 가장 최신 id 두 개만 기억하면 된다.
  - 세 경우 모두 `(room_id, id)` 인덱스와 재입장 경계 조건(`id > 재입장 경계`, ADR-008, 011)을 공통으로 쓴다.
- **커서 기반 페이지네이션**(페이지 번호 대신 "여기서부터 이어서"를 가리키는 메시지 id를 쓰는 방식)을 쓴다. 보는 중에 새 메시지가 와도 중복/누락이 없고, 뒤로 갈수록 느려지는 offset 방식의 문제(F15)를 피한다.
- **응답 순서는 항상 오래된 것 → 최신 순**으로 통일한다. `before` 결과도 화면 위에 그대로 붙일 수 있다.
- **`hasMore`(더 있음) 표시**를 응답에 포함한다. `before` 결과가 `false`면 방의 처음 또는 재입장 시점에 도달한 것이다.
- 방 목록 커서는 정렬 기준 `(last_message_id, id)` 두 값을 함께 담는다 (메시지 없는 방은 `last_message_id`가 NULL). 인코딩은 구현 시 결정.

#### 구현 시 정할 세부사항
- 메시지 조회 페이지 크기 기본값(50)과 최대값
- 응답 JSON 구체 형태와 에러 형식 (다음 결정 항목)

### 11. 공용 응답과 모니터링 구성 (ADR-020 ~ 023)

#### 공용 응답 `ApiResponse` (ADR-020)
```json
// 성공 (HTTP 201)
{ "success": true,  "data": { "id": 1001, "content": "안녕" }, "error": null }
// 실패 (HTTP 409)
{ "success": false, "data": null,
  "error": { "code": "ALREADY_MEMBER", "message": "이미 이 채팅방의 멤버입니다." } }
```
- HTTP 상태 코드는 실제 결과대로 유지한다 (201, 403, 409, 500). 실패에 200을 주면 Grafana 에러율과 k6 판정이 실패를 성공으로 센다.
- `success`는 `ApiResponse.ok(data)`, `ApiResponse.fail(code)` 두 생성 방법으로만 만든다. 상태 코드와 `success`가 어긋날 수 없게 한다.
- 본문이 없던 방 나가기는 204 대신 200 + `{success: true, data: null}`로 모양을 통일한다.
- 에러 코드는 ADR-018의 목록을 그대로 쓴다. 예외 변환은 `@RestControllerAdvice` 한 곳에서 한다.

#### 모니터링 구성도 (ADR-021)
```
          ┌─ 로그(JSON, ECS) ─→ Filebeat ─→ Elasticsearch ─→ Kibana (로그 검색)
          │    ├─ 일반 로그 → app-* 저장소 (짧게 보관)
채팅 서버 ─┤    └─ 감사 로그 → audit-* 저장소 (길게 보관)
          ├─ 메트릭 ←── Prometheus가 /actuator/prometheus 주기 수집 ─→ Grafana (그래프)
          └─ /actuator/health (헬스 체크: 앱, DB, 이후 Redis)
```
- 메트릭: Micrometer가 요청 수, 응답 시간, HikariCP 커넥션 사용량을 자동 수집한다.
- 로그: JSON 구조화 로그(ECS, Spring Boot 3.4 이상). 요청마다 추적 ID를 붙여 한 요청의 로그를 모아 본다.
- 모니터링 도구는 메모리를 많이 쓰므로 Docker Compose를 나눠 필요할 때만 켠다. 부하 측정과 동시에 돌리면 측정값이 흔들릴 수 있다.

#### 환경(profile)과 로그 레벨 (ADR-022)
| 환경 | 우리 코드 | root(외부 전부) | 따로 여는 외부 로그 | 감사 로그 | `/actuator/loggers` |
|---|---|---|---|---|---|
| local | TRACE | INFO | SQL과 바인딩 값, HikariCP(DEBUG), 트랜잭션(DEBUG) | 콘솔에도 출력 | 공개 |
| bench | INFO | WARN | 없음 | 켬 | 공개 |
| prod | INFO | WARN | 없음 | 켬, 별도 보관 | 비공개 |

- bench: 부하 실험할 때 켜는 active profile. 운영처럼 로그를 줄여 측정 왜곡을 막고, 실험용 DB에 연결하고, 메트릭은 켠다.
- 레벨은 패키지마다 따로 적용된다. 우리 코드가 TRACE여도 외부 라이브러리의 DEBUG는 root(INFO)를 따라 보이지 않는다. 필요한 것만 골라 연다.
- `/actuator/loggers`로 재시작 없이 실행 중 레벨을 바꿀 수 있다 (local, bench만 공개).
- SQL 로그 패키지: `org.springframework.jdbc.core` (DEBUG: SQL, TRACE: 바인딩 값). JPA 전환 시 Hibernate 로그로 바뀐다 (ADR-024).

#### 감사 로그 (ADR-023)
- 대상: 방 생성, 입장, 나가기, 인증/인가 실패. **메시지 전송은 제외** (본문은 개인정보, 양도 많음).
- 내용: 누가(userId), 언제, 무엇을(동작), 어디서(roomId, IP), 결과(성공/실패 코드).
- 방식: `AUDIT` 전용 로거 → Filebeat → `audit-*` 별도 저장소. 일반 로그와 보관 기간, 접근 권한을 따로 둔다.
- 트랜잭션 커밋 후에 기록한다 (`@TransactionalEventListener`). 롤백된 작업이 성공으로 기록되는 것을 막는다.
- 한계: (1) 서버가 갑자기 죽으면 아직 옮겨지지 않은 로그가 유실될 수 있다 (법적 증거 수준이 필요하면 DB 테이블로 바꿔야 함) (2) userId는 JWT 도입 전까지 헤더를 그대로 믿으므로(ADR-005) 신뢰할 수 없는 값이다.

### 12. 저장소 구조와 같은 주소(origin) 서비스 (ADR-027 ~ 029)

#### 폴더 구조 (모노레포)
```
chat-server/
 ├─ backend/      Spring Boot 4.1.1, Java 21, Gradle Kotlin DSL, 기본 패키지 jissuo.chat
 ├─ frontend/     Vite + React + TypeScript (/api 요청은 backend로 proxy)
 ├─ infra/        docker compose (DB, 모니터링, 이후 nginx/Redis)
 ├─ db/           다른 환경에서도 쓸 수 있는 테스트용 SQL
 └─ docs/         진행 기록, ERD
```
- Flyway 스키마 스크립트는 서버가 읽어야 하므로 `backend/src/main/resources/db/migration/{mysql,postgresql}`에 둔다.

#### 같은 주소(origin)로 서비스하는 이유
- origin = 프로토콜 + 호스트 + 포트. 하나라도 다르면 브라우저는 다른 주소로 본다.
- 화면(5173)과 API(8080)가 다른 주소면 브라우저가 보안 규칙(CORS)으로 요청을 막는다. 서버가 허락(CORS 설정)해도, 커스텀 헤더(`X-User-Id`)가 있으면 요청마다 확인 요청(preflight, `OPTIONS`)이 먼저 나가서 폴링 요청이 사실상 두 배가 된다.
- 그래서 브라우저가 한 주소하고만 대화하게 하고, 그 주소가 `/api` 요청을 백엔드로 대신 전달(proxy)한다. 서버끼리의 요청은 CORS 대상이 아니다.

```
개발: 브라우저 → Vite 개발 서버(5173) ─┬─ 화면: 직접 응답 (실시간 변환, 저장 즉시 반영 HMR)
                                      └─ /api: 8080으로 전달
운영: 브라우저 → nginx ─┬─ 화면: 빌드된 정적 파일 (vite build 결과)
                       └─ /api: Spring 백엔드로 전달 (Step 3에서 서버 2대로 분배)
```
- 개발은 Vite: 고친 코드를 바로 보는 것이 중요하다 (작업실).
- 운영은 nginx: 완성 파일을 빠르게 많은 사용자에게 주고, 여러 서버로 분배하고, WebSocket과 HTTPS를 처리한다 (매장). Vite 개발 서버는 공식적으로 운영용이 아니다.
- 한계: proxy를 거치면 백엔드가 보는 요청 IP가 proxy의 IP가 된다. 감사 로그(ADR-023)에 실제 IP를 남기려면 `X-Forwarded-For`를 읽도록 설정한다. WebSocket 전달은 Step 2에서 `ws: true` 설정을 추가한다. k6 부하 테스트는 브라우저가 아니라 CORS와 무관하며 백엔드에 직접 요청한다.

### 13. 테스트와 실행 환경 (ADR-030)

#### Docker Compose (용도별 분리)
```
infra/
 ├─ compose.db.yml           MySQL 8.4.11 + PostgreSQL 18.6 (항상)
 └─ compose.monitoring.yml   Elasticsearch, Kibana, Filebeat, Prometheus, Grafana (필요할 때만)
```
- 이미지 버전은 패치 번호까지 고정한다. 측정 중 버전이 바뀌면 결과를 비교할 수 없다.
- 로컬 설치 DB와 포트가 겹치지 않게 한다 (예: MySQL 13306, PostgreSQL 15432).
- 두 DB에 같은 CPU/메모리 제한과 내구성 설정을 준다 (DB 비교 공정성 규칙).
- 2026-10-06 확인: Docker Hub에 mysql 9.7.2, 8.4.11, 8.0.46과 의미를 확인하지 못한 `26.7` 태그가 있다. postgres 최신은 18.6.

#### 테스트용 SQL (`db/`, 앱 없이 다른 환경에서도 실행 가능)
```
db/
 ├─ README.md                   다른 환경에서 실행하는 방법
 ├─ seed/{mysql,postgresql}/    소량 샘플 데이터 (화면 확인용)
 ├─ bulk/{mysql,postgresql}/    대량 데이터 생성 (부하 측정용, 인기 방 쏠림)
 └─ queries/{mysql,postgresql}/ 확인용 쿼리 (실행 계획, 테이블/인덱스 크기, 캐시 적중률)
```
- 테이블 생성 SQL은 Flyway 폴더에 한 벌만 둔다. 다른 환경에서는 README 안내대로 그 파일을 순서대로 실행한다.
- 대량 데이터 생성 문법은 DB별로 다르다 (PostgreSQL `generate_series`, MySQL 재귀 CTE).

#### 자동 테스트 (3종류)
| 종류 | DB | 언제 실행 | 예시 |
|---|---|---|---|
| 단위 | 없음 | 항상 | `AuthUser` 검증, 커서 파싱 |
| 통합 | Testcontainers (MySQL, PostgreSQL 모두) | 항상 | 저장소 계약 테스트, API 테스트 |
| 실험 | Testcontainers | 따로 실행 (`@Tag("experiment")`, `./gradlew experimentTest`) | 입장 경계(F18), 마지막 나가기와 입장 경쟁(F19) |

- profile은 환경과 DB를 조합한다. 예: `--spring.profiles.active=local,mysql`
- 메모리 DB(H2)는 잠금과 커밋 동작이 실제 DB와 달라 쓰지 않는다.

| 010 | **나가기 = `room_members` 행 삭제 (hard delete)**. 재입장은 새 행 INSERT, `UNIQUE (room_id, user_id)`로 중복 입장 방지 | 멤버십 이력 요구사항이 없다(YAGNI). "나갔습니다"는 시스템 메시지로 남긴다. soft delete는 `left_at IS NULL` 조건 누락 시 나간 유저에게 메시지가 가는 사고 위험이 있다 | 멤버십 이력(감사). 필요해지면 이력 테이블 추가로 확장 |
